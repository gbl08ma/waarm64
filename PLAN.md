# webpc — implementation plan

A whole-system AArch64 emulator for the browser. Guest code is JIT-compiled to
WebAssembly. It runs unmodified arm64 Linux distributions. Chromium is the
primary target.

## 1. Locked-in decisions

| Area | Decision |
|---|---|
| Guest ISA | ARMv8.0-A AArch64 with FP and AdvSIMD (NEON), no AArch32. LSE atomics (v8.1) added early. The crypto extensions (AES, PMULL, SHA1, SHA2) come in M6.5, and stay unadvertised until then (and after it, unless they beat the NEON-only paths guests use without them). No SVE/SME, PAC, BTI or MTE: leave them unadvertised, and their hint-space encodings run as NOPs |
| Privilege | EL0 and EL1 only. No EL2/EL3 and no secure state |
| MMU | Stage 1 only, 4K granule, 48-bit VA, TTBR0/TTBR1, ASIDs, software-managed access flag |
| Platform | GICv2 (a GICv3 subset later), generic timer, PL011 UART, PSCI over HVC (the core answers calls that need no host and exits to the host for SYSTEM_OFF, SYSTEM_RESET and, from M7, CPU_ON; decided in M3), virtio-mmio v2, and a DTB generated from the VM config |
| Boot | Direct kernel boot (arm64 `Image` + initrd + DTB). No UEFI. For distro disk images, the kernel and initrd are extracted and booted directly |
| Core language | Rust compiled to `wasm32` (the same crate also builds natively for tests). Host glue is in TypeScript |
| Guest memory | **Layout A (decided in M0.5, `bench/spike/memory/REPORT.md`):** one shared wasm32 memory: core state first, then guest RAM (≤ ~3.5 GiB, sized against host RAM at VM start). The Rust core targets wasm32. Every >4 GiB layout cost more than the 5% threshold on x86_64 Chromium: C (memory64) +6–20% in JIT code and +11% in the core, B +12–14%, D +19–28%. On arm64 (M4, macOS Chromium 153) they cost C +17–19% in JIT code (its wasm64 core is free there), B +31–40% and D +26–32%. The guest physical address map is independent of placement, because the TLB translates. Every guest RAM access in generated code goes through one lowering function. TLB tag bits 3–11 are reserved for a memory index, so "A + spill memories" (extra wasm32 memories as NUMA nodes, same fast path as A for memory-0 pages) can be added later without changing A's code |
| License | MIT (or MIT OR Apache-2.0, the Rust-ecosystem default, which also adds a patent grant). Nothing in §6 requires GPL |

Deferred: SVE, EL2, 16K/64K granules (needed for RHEL-family kernels), virtio-pci/MSI, GICv3 ITS.

## 2. Architecture overview

```
┌──────────────────────── Worker (one per vCPU) ─────────────────────────┐
│  core.wasm (Rust)                                                      │
│   ├─ A64 decoder (table-driven)                                        │
│   ├─ interpreter (tier 0; reference semantics; JIT fallback helpers)   │
│   ├─ JIT (tier 1+): guest block/region → wasm bytes → Module           │
│   ├─ MMU walker + per-vCPU software TLB                                │
│   ├─ exceptions, system registers, generic timer, GIC CPU interface    │
│   └─ perf counters (in shared memory)                                  │
│  jit modules: import memory + core helpers, exported via a table       │
└────────────────────────────────────────────────────────────────────────┘
            │ shared linear memory (CPU state, guest RAM, device rings)
┌──────────────────────── Device worker / main thread (TS) ──────────────┐
│  virtio-mmio transports + virtqueues (Rust, in core)                   │
│  backends (TS): block (HTTP ranges, OPFS overlay), net (pluggable →    │
│  your WebRTC network), 9p, console, input, framebuffer → canvas        │
└────────────────────────────────────────────────────────────────────────┘
```

Key design points. The spike in M0 will confirm or adjust each of these.

- **Gadget-style JIT, as in v86.** Tier 1 inlines simple ops (ALU, branches, loads and stores through the inline TLB fast path) and calls core helpers for everything else. Tier 2 widens what gets inlined, forms multi-block regions and turns guest loops into real wasm `loop`s.
- **Guest registers live in wasm locals inside a compiled region.** They're written back to the CPU state struct on region exit, on helper calls that need them, and on exceptions.
- **Lazy NZCV.** Only `S`-suffixed instructions and `CMP`/`CCMP`/`TST` produce flags, so dead flags are eliminated per region.
- **Software TLB.** It's direct-mapped per vCPU with separate read and write entries. The fast path adds the host offset (QEMU-style addend) and takes about 6–8 wasm instructions. MMIO and unmapped pages take the slow path.
- **Faults from JIT code.** A helper records the exception and returns a status. The generated code stores the statically known PC and returns to the dispatcher. No wasm exception handling.
- **Code invalidation driven by `IC IVAU`/`IC IALLU`**, with `CTR_EL0.DIC=0` advertised so guests issue those instructions. A debug-only "stale translation checker" hashes guest code at block entry during tests.
- **Interrupt and exit checks** read an atomic flag on every region exit and loop back-edge. The atomic also stops V8 from hoisting guest spin-loop loads out of the loop.
- **Timers have two modes.** *Deterministic* mode derives virtual time from the instruction count, for tests, benchmarks and reproducible bugs. *Realtime* mode uses `performance.now()`.
- **SMP readiness from day one.** No mutable globals in core: all vCPU state sits behind a per-vCPU pointer. Exclusives and LSE atomics use wasm atomics even in single-core builds. `TLBI …IS` and `IC IVAU` are broadcast operations on ARM, so the design must allow another vCPU to raise a request that a `DSB` waits on.

### Host ABI for a whole VM (ABI 5, approved in M3)

Devices M3 has (GICv2 distributor and CPU interface, generic timer, PL011) live in the Rust core, so native and wasm share them and M3 needs no device-access exits. An access to an unmapped PA stays an external abort. The EL0 exports (`vcpu_new`, `mem_new`, `interp_run*`) stay for the corpus and benchmarks.

- `vm_new(ram: *mut u8, ram_size: u64, cfg: *const VmConfig) -> *mut Vm`. RAM is placed by the host after the core's heap (layout A) and appears at guest PA `0x4000_0000`. `VmConfig` (`repr(C)`, new fields at the end): RAM size, deterministic flag, `CNTFRQ` (default 62.5 MHz, QEMU's), timer ticks per retired instruction (default 1). `vm_free(vm)`.
- `vm_cpu(vm) -> *mut Cpu`: registers at the existing offsets (PC at 256, …).
- `vm_boot(vm, kernel_pa, initrd_pa, initrd_len, cmdline_ptr, cmdline_len)` (M3 step 5): the host copies the Image and initrd into RAM; the core writes the DTB and sets x0 = DTB, PC = entry, per booting.rst.
- `vm_run(vm, budget: u64) -> u32` exit kind; details in `vm_exit(vm) -> *const ExitInfo` = {kind, instructions retired, value, x0–x3}. Kinds: 0 budget used up; 1 PSCI call for the host (SYSTEM_OFF, SYSTEM_RESET, later CPU_ON; PC already past the HVC, the host writes x0 if it resumes); 2 idle (WFI with nothing pending; realtime mode only, `value` = deadline; deterministic mode instead jumps virtual time to the next timer deadline); 3 console TX ring full (drain, resume); 4 unimplemented instruction (`value` = Op index); 5 stop requested.
- PSCI in the core: VERSION (1.0), FEATURES, AFFINITY_INFO, MIGRATE_INFO_TYPE, and NOT_SUPPORTED for the rest.
- Console: two SPSC byte rings (TX, RX, 4 KiB each, atomic head/tail) at `vm_console(vm) -> *const Rings`. The PL011 writes TX; the host drains it after each `vm_run`, fills RX from any thread, then sets the signal word.
- Signal word `vm_signal(vm) -> *const AtomicU32`: bit 0 stop request, bit 1 RX data. The core checks it every 1024 instructions and on WFI (the interpreter's form of the §2 exit-check flag).
- Counters `vm_counters(vm) -> *const Counters`: a `repr(C)` block of u64s written with relaxed atomic stores and read with `Atomics.load`: instructions retired, exceptions by EC (64), IRQs, TLB hits/misses/walks/flushes, and the current PC for the sampling profiler. The layout is fixed in step 4 and filled in step 8 (TLB hit counting gets measured before it's turned on).
- Deferred: SMP (`CPU_ON`, M7). Realtime mode landed in M4 step 3 (ABI 7, below).

### Device backends (ABI 6, approved in M4 step 1; landed in M4 step 2)

- **Split:** virtio-mmio v2 transports, feature negotiation, status/reset and split virtqueues (indirect descriptors included) run in the core on the vCPU thread; our own split-ring code, not rust-vmm `virtio-queue`. On a queue notify the core walks the new descriptor chains, checks each buffer lies in RAM and writes it as a flat segment list (linear-memory offset, length, writable) to a per-device **request ring** in shared memory. TypeScript never parses virtio rings, only the device protocol (e.g. the virtio-blk header). A buffer outside RAM puts the device in NEEDS_RESET.
- **Notify = exit:** exit kind 6 `DEVICE` (`value` = transport index and event bits: queue notify, config-space write, status change). The vCPU worker wakes the device worker and chooses to wait or resume, so the core has one path and native runners handle it inline.
- **One dedicated device worker** holds every backend (OPFS sync access handles exist only in workers; the main thread can't block). The main thread keeps UI, canvas and input and forwards events to it.
- **Completions → IRQs:** the backend writes guest buffers directly, appends {queue, head, bytes written} to the device's **completion ring**, sets signal bit `SIGNAL_DEVICE` and `Atomics.notify`s. At the next chunk boundary (≤ 1024 steps) the core drains completion rings, fills used rings, sets InterruptStatus and drives the transport's line. Transport *i*: `0x0a00_0000 + 0x200·i`, SPI 16+i (INTID 48+i), QEMU `virt`'s window of 32.
- **Determinism:** in deterministic mode the vCPU worker `Atomics.wait`s on each `DEVICE` exit until the device worker has completed everything posted, so completions land at a fixed step and boots keep one exact step count natively and in Chromium (backend latency only lengthens the wait). In async mode it resumes at once, and idles on the signal word.
- **Config:** `VmConfig` gains a pointer and a count of device entries (u64s: virtio device ID, offered features, queue count, max queue size, config-space bytes); array index = transport slot, one `virtio,mmio` DT node each. Host side: `{devices: [{type: 'blk', backend: 'http', url, readonly: true}, …]}`, sent to the device worker, which builds the backends.
- **Concrete layouts (M4 step 2, `core/src/virtio.rs`, `web/devices.ts`):**
  - `VmConfig` gains `devices` (address of the entries) and `ndevices` (≤ 32). `DeviceEntry` = 5 u64s: device ID, offered features (the transport masks the reserved bits 24–40 and adds `VERSION_1` and `INDIRECT_DESC`), queue count (≤ 8), QueueNumMax (power of 2, ≤ 1024), config length (≤ 256); every chain that can be in flight must fit the completion ring (queues × size × 2 ≤ 4096 words). `vm_new` returns null on an invalid entry.
  - `vm_device(vm, i) -> *const DevShared`: events (u32, `EV_REQUEST` 1, `EV_CONFIG` 2, `EV_STATUS` 4; the host takes them with a swap) at 0, device status at 4, negotiated features (two u32s) at 8, reset epoch at 16, config space (256 bytes, written by the host after `vm_new`; guest writes land there with `EV_CONFIG`) at 24, request ring at 280, completion ring at 16672. Each ring is SPSC u32 words: head, tail (words written/read, wrapping), 4096 words.
  - **Request record:** `w0` = head | queue << 16 | epoch << 24; `w1` = readable count | writable count << 16; then (offset from the start of guest RAM, length) per buffer, readable first (the spec's order; a readable buffer after a writable one is NEEDS_RESET). Offsets are RAM-relative rather than linear-memory addresses so the words stay u32 natively too; the host adds its RAM base. **Completion record:** `w0` as posted, bytes written. The epoch counts device resets (mod 256): the backend skips records from an older epoch, and the core drops their completions, so a reset never lets a stale request complete into a reused ring.
  - Chains that don't fit the request ring stay available and are posted after the next completions (a `DEVICE` exit from the completion drain). A guest that makes more chains available than the queue holds, or an available index more than a queue ahead, gets NEEDS_RESET.
  - Exit `DEVICE` = 6, `value` = slot | events << 8 (informational: every device's events are in its `DevShared`); the PC is past the register access. Signal bit `SIGNAL_DEVICE` = 4. `ABI_VERSION` 6.
  - **Host glue:** `web/vm.ts` handles `DEVICE` exits inside `run` (one budget, as the native runner does, so chunk boundaries and step counts match). In a worker it runs `web/device-worker.ts`: a doorbell pair of i32s in the host's scratch page, word 0 rung by the vCPU (`Atomics.notify`), word 1 the last value the device worker handled (`Atomics.waitAsync` there, `Atomics.wait` on the vCPU in deterministic mode). Where the thread can't block (Node, a page's main thread) the same `Devices` class runs inline; the bench pages run their suites in a worker, so they use the device worker. Console output reaches the vCPU side as messages, with a flush round trip at the end.
  - **Disk images (M4 step 4):** a blk backend reads raw or **qcow2** v2/v3 (detected by the magic): header, L1/L2 tables, refcounts ignored (read-only), unallocated and zero-flag clusters as zeros, compressed clusters as raw deflate (`DecompressionStream('deflate-raw')` in the browser, `miniz_oxide` in the native test runner, a dev-dependency). Refused at open: encryption, backing files, external data files, extended L2 entries, zstd, unknown incompatible features. `web/qcow2.ts` and `core/tests/common/qcow2.rs`, both checked against `qemu-img` fixtures (`tests/qcow2/`). The capacity is the qcow2 virtual size (else the file size), from the file's first bytes. Decompression is asynchronous, so a backend may answer with a promise; `Devices.poll` completes requests in order and the device worker acks the doorbell only after all of them, so deterministic mode keeps one step count.
  - **Writable disks (M4 step 5):** `{type: 'blk', url, overlay: '<name>'}` makes the disk writable through a copy-on-write overlay in the OPFS directory `<name>` (`web/overlay.ts`): 4 KiB blocks; `data` holds written blocks in first-write order, `map` a u32 per disk block (0 = base, n = slot n − 1), `base` the image's URL path and size (a mismatch refuses to open). A block's slot is written before its map entry, so a crash leaks a slot but never maps garbage. The device worker opens the files with synchronous access handles (so requests stay synchronous and deterministic mode exact) and closes them on `close`, before ending. The device then offers `FLUSH` (bit 9) instead of `RO` and answers `OUT` and `FLUSH` (which flushes both files); without an overlay nothing changes. Natively, `core/tests/common` `Overlay` keeps 512-byte sectors in memory and can be shared by several boots in one process.
  - DT: one `virtio,mmio` node per entry, slot order, `dma-coherent`, **level-high** interrupt (QEMU `virt` says edge-rising; our line follows InterruptStatus, so level is what it is).
- **Step 6 devices (M4 step 6, ABI 8)**: no core change for the three virtio devices (each is a `DeviceEntry`, a config layout and a backend in `web/devices.ts`, twinned natively in `core/tests/common`); `DeviceSpec` gains `net`, `9p` and `input`. Ports in specs are transferred to the device worker with them (`specPorts`).
  - **virtio-net** (ID 1, features `MAC` and `STATUS`, receiveq and transmitq of 256; config: MAC, default `52:54:00:12:34:56`, status `LINK_UP`): the host sees Ethernet frames only (§7 M4). Each transmitted chain is one frame with the 12-byte `virtio_net_hdr_v1` stripped; a chain of 12 bytes or less, or over 12 + 1518 (a 1500-byte MTU, the Ethernet header and a VLAN tag), is dropped. Frames for the guest wait for receive buffers (held by the backend) and get a zero header with `num_buffers` 1; past 256 waiting the oldest is dropped, and a frame larger than the next buffer is dropped. **Adapter interface** (`web/net.ts`): `NetAdapter = {send(frame), close?()}`, made with the `receive(frame)` it calls from any async context. `{type: 'net', adapter: 'loopback'}` runs the loopback test adapter in the device worker; `{type: 'net', adapter: port}` puts the adapter on the page behind a `MessagePort`, one frame per message as a transferred `ArrayBuffer` each way; `v86Bus(port)` gives that end v86's bus shape (`register('net0-send', …)`, `send('net0-receive', …)`), so a v86 adapter runs unchanged. The **loopback adapter** plays 10.0.2.2 at `52:55:0a:00:02:02` and answers ARP requests and ICMP echo requests for it, synchronously (a TX's replies complete before the device worker acks the doorbell, so deterministic mode stays exact); frames from a page adapter arrive whenever they arrive, which is realtime-mode behavior. The link is always up (changing it under a running driver needs the config-change API in M9).
  - **virtio-9p** (ID 9, feature `MOUNT_TAG`, one queue of 128; config: tag length and tag): our own `9P2000.L` server (`web/9p.ts`, twin `core/tests/common/p9.rs`), **not a port of v86's** (decided in step 6: v86's `lib/9p.js` is written against its `FS` class, `lib/filesystem.js`, a large inode store with lazy HTTP loading, and the native runner needs a Rust twin anyway; ours is ~350 lines of TypeScript written from the protocol as Linux's v9fs speaks it, with v86 and TinyEMU read as references, no code copied). One T-message per chain (readable buffers), the R-message into the writable ones (Linux's zero-copy split of read and write payloads is undone by concatenation). Messages: version (msize ≤ 1 MiB), attach, walk, lopen, lcreate, read, write, readdir (with `.` and `..`, offsets are entry indices), getattr, setattr, mkdir, symlink, mknod, readlink, link, renameat, unlinkat, remove, clunk, flush, fsync, statfs, lock (always granted), getlock (always unlocked); xattrs and the rest answer `EOPNOTSUPP`, malformed messages `EINVAL`. **The host side is an in-memory tree** seeded from the spec (`{type: '9p', tag, files: {path: text}}`); node ids (qid paths) are handed out in creation order, and in deterministic mode every timestamp is 2026-09-01 (`EPOCH`), so native and Chromium boots give the guest the same bytes. OPFS or HTTP-served trees come later (M9).
  - **virtio-input** (ID 18, eventq and statusq of 64; config: `select`, `subsel`, `size`, the 128-byte answer): `{type: 'input', kind: 'keyboard' | 'tablet', port?}`. The keyboard has keys 1–248, the Num/Caps/Scroll Lock LEDs and `EV_REP` (the kernel autorepeats); the tablet `BTN_LEFT/RIGHT/MIDDLE`, `REL_WHEEL` and `ABS_X/Y` over 0–32767. A guest write of `select`/`subsel` is a config event; the backend writes the answer before the vCPU resumes: **a `DEVICE` exit with `EV_CONFIG` waits for the device worker in realtime mode too** (the driver reads `size` right after). Events come from the port as arrays of [type, code, value] (one message per report, `web/input.ts` `attachInput` makes them from DOM keyboard, pointer and wheel events over an element, keys by `KeyboardEvent.code`); they wait for event buffers (the oldest dropped past 1024). Status events (LEDs) go to the port as one [type, code, value] each.
  - **Framebuffer** (`simple-framebuffer`, ABI 8): `VmConfig` gains `fb_width` and `fb_height` (0: none). The framebuffer is x8r8g8b8 with packed rows (stride 4 × width) in guest RAM, in a region of whole 2 MiB units just below the DTB's 2 MiB (`boot::framebuffer`; `vm_new` refuses one over half of RAM, `vm_boot` an initrd over it). The DT describes it as `/chosen/framebuffer@…` (`compatible = "simple-framebuffer"`, `reg`, `width`, `height`, `stride`, `format`; `/chosen` gets `#address-cells`, `#size-cells` and an empty `ranges` so `reg` translates) and reserves the region under `/reserved-memory` with `no-map` (the driver maps it). `vm_framebuffer(vm)` returns its PA (0: none); `bootVm(…, {framebuffer: {width, height}})` returns its address in the shared memory, and the page draws it (`web/display.ts`: every animation frame converts it into an `ImageData`, opaque, and puts it on a `<canvas>`; the vCPU worker posts the memory to the page).
- **Realtime mode** (M4): the clock is a core import (`performance.now()` in the browser, `Instant` natively), read once per chunk and on timer-register reads; the idle exit carries a deadline and the host `Atomics.wait`s on the signal word until then. Tests and boot tests stay deterministic; **I/O benchmarks run in realtime mode** (guest-timed `dd`/`fio` are meaningless in instruction-count time).
  - **As built (M4 step 3, ABI 7):** the core imports `env.now_ms() -> f64` (`web/vm.ts` `coreImports`: `performance.now`); every host that instantiates the core passes it. `VmConfig.deterministic` = 0 selects realtime; the counter is (host ns since `vm_new`) × CNTFRQ. Chunks aren't cut at deadlines (steps don't measure time), so a timer fires at the first chunk boundary past it (≤ 1024 steps late). A WFI with no interrupt signaled returns `IDLE` with the PC on the WFI and `value` = **nanoseconds to the next timer deadline** (u64::MAX: none), and re-executes on resume. `web/vm.ts` `run` sleeps in `Atomics.wait(signal, 0, 0, ms)` when the signal word is 0 (whoever sets a signal bit must `Atomics.notify` it, as the device worker does for completions), except on a page's main thread, which gets the exit. `DEVICE` exits don't wait for the device worker; the rng uses `crypto.getRandomValues`. Deterministic mode is unchanged and stays the default.

### JIT ABI (ABI 9, approved in M5 step 1)

The translator lives in the Rust core (`core/src/jit/`: decoder, `Cpu` layout, TLB and helpers are shared) with its own minimal wasm encoder (`jit/wasm.rs`, no dependency). The host only turns bytes into a module and puts its functions into a table.

- **Table plumbing:** the core is linked with `--export-table --growable-table`, so its function table (`__indirect_function_table`) is an export, and Rust function pointers are indexes into it. JIT functions live in the table after the core's own entries: `coreImports(memory)` (`web/vm.ts`) returns `{env, jit}`, and after instantiating, the host calls `jit.bind(instance)`, which records `base` = the table's length then. The core owns **slot** allocation (slot *s* is table index `base + s`), so eviction reuses slots and the table stops growing at the code cache's size.
- **Install:** the core imports `env.jit_install(ptr, len, slot) -> i32`. The host copies the bytes out of the shared memory, compiles and instantiates them **synchronously** (`new WebAssembly.Module`/`Instance`, in the vCPU worker; spike §1), grows the table if needed, sets each export `f0, f1, …` at `base + slot + k`, and returns `base + slot` (−1 before `bind`: the core then only interprets). A module that doesn't compile is a JIT bug: the exception propagates and the run fails. A module's imports come from `env`: `memory` (the core's shared memory, limits 0–65536 pages), `table` (the core's table), and **any core export by name**: helpers are ordinary `extern "C"` exports named `jit_*`, called as imports of another instance (2.2 ns, spike §3), no JS in between.
- **Where it runs:** in the vCPU worker and in Node, the same code (`jitHost` in `web/vm.ts`). Natively there's no wasm engine: `jit::install` returns `None` and the run loop interprets; `cargo test` covers the translator's structure (block formation, liveness, the encoder's bytes), and the JIT's behavior is tested on the wasm core in Node (corpus, lockstep, boots) and Chromium. Hosts that never call `bind` (old tests, tools) keep running on the interpreter.
- **Block functions** are internal to the core (both sides are core code, so their shape isn't host ABI and changes without a bump): `block(vcpu) -> retired`, with `vcpu` the `Vcpu` pointer (the `Cpu` at 0, the TLB after it, then a per-vCPU JIT block: the RAM handle, the pending exit, counters). **A call is equivalent to `interp::steps(…, n)` for the block's length `n`:** it returns how many instructions retired, and if one didn't (an exception, a fault, WFI, a platform register, an exit the interpreter reports), the pending `Exit` is in the JIT block and the PC is on that instruction, so the run loop's `handle` completes it exactly as for the interpreter. Helpers return a status (0 retired, 1 exit pending) and the generated code returns at once on 1; the PC it stores is the statically known one, as an offset from the PC at block entry (blocks are keyed by PA, so one block runs at every VA that maps its page: shared libraries, the kernel's linear map). No wasm exception handling. While a block runs, the run loop holds no Rust reference into the `Vcpu` or `Mem` (the block and its helpers reach them through the raw pointer).
- **Helper imports** (step 2 onwards): `jit_exec_flat(vcpu, insn: i32, pc: i64) -> i32` and `jit_exec_mmu(…)` run one instruction through the interpreter's `exec` on the bus the block was compiled for (`Flat` or `Mmu`; `interp::exec_at`, shared with the interpreter's `step_bus`), with `pc` = the entry PC + 4·*i*; later steps add narrower ones (loads/stores on a TLB miss, flags, system instructions, FP). A helper that hits a non-RAM PA reports `Exit::Fault(Bus)`, and the run loop re-executes that instruction through `vm::Io` as today.
- **Step accounting (exact):** a block knows its instruction count *n*; the run loop enters it only if the chunk has ≥ *n* steps left, and otherwise interprets. Blocks end at branches, exception-generating and system instructions, WFI, page boundaries and a size cap. So **a deterministic run takes exactly the same steps with or without the JIT**: every boot's step count and console must match the interpreter's, and lockstep comparison works at every chunk boundary. IRQs, the signal word and timer deadlines are still checked between chunks; regions (step 8) add the exit check (an atomic load) and the step budget on loop back-edges.
- **Block keying:** by the **guest PA** of the first instruction plus the regime bits that change what the code means (EL, and `SCTLR_EL1.M`/`.A`, which pick `Flat` or `Mmu`). The run loop translates the PC through the instruction TLB before the lookup (a hit is the interpreter's fetch cost). Chosen over VA + ASID because it is what the architecture's PIPT instruction cache promises: the guest's own maintenance (`IC IVAU` after writing code, which Linux does when it maps an executable page) is exactly what invalidates blocks, remapping or `TLBI` needs nothing, and processes that share a physical page (BusyBox, libc) share its translations. Chaining (step 7) re-checks a target's translation unless it lies in the same guest page.
- **Invalidation:** `IC IVAU` and `IC IALLU(IS)` leave the interpreter with an internal exit (retired, like `Resync`), and the run loop drops the blocks of that physical page (IVAU; a per-page "has code" bit keeps the common case cheap) or all of them (IALLU). The code cache has a capacity in blocks; when it's full everything is flushed (slots freed, modules left to the GC). A debug checker (on in JIT-stress) hashes each block's guest code when it's compiled and again at every entry, and fails the run on a mismatch. **As built (step 3):** the exit is `Exit::Invalidate(pa)` (`u64::MAX` for IALLU; `Bus::maint` returns the PA it translated); the "has code" structure is a map from physical page to the block keys filed under it (every key the cache knows, compiled or not), so IVAU on a page without code costs one lookup; the checker is `jit::Config::check` (a panic, which traps the wasm run), on in `STRESS`. `jit_new` gained `check` (ABI 11).
- **Compiling:** a hotness counter per block key; at the threshold the block joins a pending batch, and the batch is emitted as one module when it holds `B` blocks (spike: ≥ 16–64; tuned in step 2) or at a chunk boundary after a timeout in steps, so a lone hot block doesn't wait forever. Every function is named after its guest PC in the name section.
- **Config and counters:** `VmConfig` gains `jit` (0 interpreter only, the default for now; 1 JIT; 2 JIT-stress: threshold 0, batch 1, a tiny cache and the stale-code checker). `vm::Counters` (append-only) gains: blocks compiled, modules, wasm bytes, compile time (ns, measured around `jit_install`), steps in JIT code (so interpreted = steps − that), block calls from the run loop (dispatches), invalidations, cache flushes; `web/vm.ts` `Counter` follows. A helper-call histogram by `Op` comes with the helpers that need it (step 9) and is on only when asked for. **Landed in step 2c (ABI 10):** `VmConfig.jit` is the ninth u64; `Counters.jit` is eight u64s after `pc` (`jit::Stats`: blocks, modules, bytes, compile ns, steps in JIT code, dispatches, invalidations, flushes; `web/vm.ts` `Counter.JIT_*`, `stats().jit`). JIT-stress is threshold 0, batch 1 and a 4-block cache; the stale-code checker joins it in step 3. **ABI 12 (step 4):** `jit::Stats` (and `Counters.jit`, now eleven u64s) appends instructions compiled inline, instructions compiled as helper calls, and inline instructions run (each dispatch adds its block's inline count, capped at the instructions that retired, so it's exact unless a block stops early); `Counter.JIT_INLINE`, `JIT_HELPERS`, `JIT_INLINE_STEPS`. **ABI 13 (step 6):** `jit::Stats` (and `Counters.jit`, now sixteen u64s) appends static counts over the compiled code: lazy flag setters whose NZCV is stored somewhere and never (elided), and conditions (B.cond, CSEL & co, CCMP, ADC's carry) computed directly from a lazy setter's operands, from its NZCV computed in registers, and from NZCV in memory; `Counter.JIT_FLAGS_STORED`, `JIT_FLAGS_ELIDED`, `JIT_COND_DIRECT`, `JIT_COND_COMPUTED`, `JIT_COND_MEMORY`. **ABI 14 (step 7, chaining):** block functions are `block(vcpu, acc, left) -> acc + retired` (core-internal): a block whose successor is static (a direct branch, both sides of a conditional one, or the fall-through when it stops at its cap, a page end or before an exception) and compiled tail-calls it (`return_call`) with `acc + len` and `left − len` when `left` covers both, so a chain retires exactly what the dispatcher would have run and never outruns the chunk; the dispatcher passes `acc` 0 and `left` = the steps left. Successors in the same batch are direct calls; already-compiled ones are imports from the module **`t`, named by table index**, which `jit.install` resolves with `table.get` (the host change behind the bump). With the MMU on, a successor in another page is chained behind a check that its VA hits the instruction TLB of the block's EL and maps to the host address of the PA it was compiled for (else the block returns to the dispatcher); with the MMU off, any. The cache records which blocks chain to which, and dropping a block (`IC IVAU`) drops the blocks chained to it, transitively; flushes drop everything. With the stale-code checker on, chained entries call `jit_check(vcpu, key)` first. `Stats.inline_steps` is now JIT steps minus the steps helpers retired (counted in the helpers), exact with chains. Blocks ending on a system instruction that can't change the regime (ISB, CLREX, YIELD/SEV, DC other than ZVA) chain to the next instruction when its helper retired; since M6 loop 1, MRS, DMB/DSB and DC ZVA don't end a block at all (inline, or a helper call that returns from the block mid-way when it doesn't retire), and since loop 7 neither do the MSRs that can't change what a block assumes (`interp::sys::msr_continues`: DAIFSet, and DAIF, SP_EL0, SPSR/ELR_EL1, the TPIDRs; an unmasking DAIF write leaves through its helper's `Exit::Resync`). **Through the jump cache (step 7.3):** a successor that isn't compiled when its predecessor is (the common case: blocks compile in hotness order) is probed in the jump cache at its static key's entry, and BR/BLR/RET translate their target through the instruction TLB (MMU on) into a key and probe it the same way; a hit that fits `left` is tail-called with `return_call_indirect` through the core's table (modules import it as `env.table`). The jump cache is `#[repr(C)]` {key u64, table index u32, length u32} at a fixed address for the cache's life, now 65,536 entries; it only ever holds compiled blocks, and invalidation and flushes clear it, so these links need no bookkeeping. The default code cache holds **65,536 blocks** (was 16,384; **262,144 since M6**, for Debian's boot, below): Alpine's boot compiles 56,772, so it no longer flushes (14 flushes before; Node 32.4 → 24.8 s). Relinking (compiling a block again once a successor it returned through is compiled) was tried and dropped: on Alpine it doubled the blocks compiled and the flushes for 9% fewer dispatches. **ABI 15 (step 8, regions):** the unit the cache compiles is a **region**: the hot block (its head, which keys it) and the blocks reachable from it by static edges within the head's guest page (so it depends on one page, and `IC IVAU` on it drops it), up to 16 blocks, in reverse postorder, one function. **As built (step 8.2):** a region's members are only the blocks the dispatcher has seen (any, with a threshold of 0) that lead back to the head: the head's loop; without one the region is the head alone (a region of every seen successor duplicated each block into ~5 regions and cost Buildroot 25–40%). Back-edges to the head are branches to a wasm `loop` around the members, under the same budget check as every internal edge, and the head's register state is loaded once before the loop. **The back-edge exit check is the budget alone**, not also an atomic load of the signal word as planned: `left` is at most the run loop's chunk (≤ 1024 steps, cut at deadlines), so a loop never outruns the chunk and the run loop checks the signal and IRQs between chunks as before; an atomic load there would add nothing the run loop would act on sooner. With the stale-code checker on, back-edges call `jit_check` as chained entries do. ABI 16 appends the static count of back-edges (`Counter.JIT_BACK_EDGES`). **ABI 17 (step 8.3, tier-up):** a head whose region is a loop is first compiled **alone**, with a hot word (one u32 per code-cache slot, at a fixed address): its prologue counts entries down from `region_after` (`jit::Config`, 1000 by default; 1 in JIT-stress; 0 compiles regions at once, as the forced mode and the differential tests do), and the entry that takes it to 0 calls the core export `jit_hot(vcpu, key, pc)`, which compiles the loop region then and there (in its own module; never with a flush, since JIT code is on the stack: without room the head stays alone) and stores `1 << 31 | the region's table index` in the word. From then on the head's prologue tail-calls the region through the table (`return_call_indirect`, same arguments: the region's head is the same block), so blocks linked to the head before the region existed reach it too; the key's entry and its jump-cache entry name the region. Members that are candidate heads themselves stop counting. Regions of the whole loop at the first threshold cost the boots 10–14% (compiling ~930 lukewarm loops of ~6 blocks in Buildroot: `bench/interp/REPORT.md` "M5 step 8"). `jit_new` takes `region_after` as a fifth argument; `jit::Stats` appends the tier-ups (`Counter.JIT_TIER_UPS`). **Flags across edges (step 8.4):** a member starts with its flags lazy when every edge into it carries the same setter (kind and size: the flag locals are the function's), in memory, or dead when a setter comes before any condition, helper or possible exit in it (`emit::Func::touched`); the head's are in memory or dead. An edge stores NZCV only into a member that needs it in memory, and the store before a block's branch (step 6) is skipped when every successor is a member that doesn't; exits store lazy flags as always. Entry states settle with the register states; if an edge still carries lazy flags its member doesn't start with, the region is emitted again with flags in memory. **The PC on the way out (step 8.5):** a block whose successors are all members doesn't store the next PC at its branch (`emit::Func::defer_pc`: a conditional branch keeps its outcome in `TAKEN`); the path that returns when `left` doesn't cover the edge stores it. **ABI 18 (step 10):** the helpers count their calls by instruction class (`Op`), and the export `jit_helper_report(vcpu) -> *const u8` returns them as NUL-terminated `<Op> <calls>` lines, most frequent first (a `jit_new` vCPU, or a VM's through `vm_cpu`); `web/vm.ts` `helperReport`, recorded by the interp and boot benchmarks: the helper-call histogram M6 starts from. The members are nested wasm `block`s; an edge to a later member is a `br` taken when `left` covers both blocks, adding the block's length to `acc` and taking it from `left` (so a region retires exactly what the dispatcher would have run), with register locals kept across it: each member starts in a fixed register state (the merge of what its edges carry, found by a first emission: valid or dirty on any edge), and every edge conforms to it (writes back what the member doesn't have dirty, loads what it has valid). Other edges leave through step 7's tails. The stale-code checker hashes all of a region's blocks. `jit::Stats` (and `Counters.jit`, now seventeen u64s) appends the blocks in the compiled regions (`blocks` counts regions); `Counter.JIT_REGION_BLOCKS`.
- **User mode:** the corpus and the interpreter benchmarks get JIT twins of `interp_run_exit`/`interp_run` over a per-vCPU JIT state (`jit_new`, and `jit_flush` for hosts that rewrite guest code between runs, as the corpus runner does).
- **Measured (step 1, x86_64 Chromium 152, `bench/jit/`):** emitting and installing a one-block module 46–47 µs, then 3.3 µs for its first call (V8 compiles lazily with Liftoff), in line with the spike's ~60 µs per module, so batching stands. A call from the core through its table to a JIT block: **3.5 ns** from one call site to one block, **13–16 ns** cycling over 16 (three runs; spike: 2.2 ns for a direct import call, 11 ns for a polymorphic `call_indirect`). One dispatch per block costs about as much as interpreting one instruction (11–18 ns at 55–88 MIPS), so linking (step 7) is what makes short blocks pay.

### CPU features: switchable crypto extensions (ABI 19, M6.5 loop 2; approved 2026-09-27: UNDEFINED when off)

- **`VmConfig.features`**, a u64 appended after `jit` (the tenth field): bit 0 `FEATURE_CRYPTO` = FEAT_AES (with PMULL), FEAT_SHA1 and FEAT_SHA256. 0, the default, is today's CPU. Other bits stay reserved (0) for M9's unadvertised extensions (FP16, DotProd, SHA3, …): `vm_new` refuses a VM with a reserved bit set.
- **What it changes:** `ID_AA64ISAR0_EL1` gains AES = 2, SHA1 = 1, SHA2 = 1 (bits 7:4, 11:8, 15:12); Linux derives the hwcaps (`AES`, `PMULL`, `SHA1`, `SHA2`), `/proc/cpuinfo` and its CE driver choice from it, and userspace (OpenSSL's `getauxval`) from the hwcaps. **Off, the instructions are UNDEFINED**, as on a CPU without the feature: guests that probe by SIGILL (the `hwcap` kselftest) see what the ID register says, and every step constant returns to its pre-M6.5 value (loop 1 moved `LTP_STEPS` because they executed unadvertised). The user-mode entry points (`vcpu_new`, `jit_new`: corpus, differential tests, `bench/interp`) always have the feature, since the golden corpus records the M4's behavior.
- **Where it lives:** a `features` u64 appended to `Cpu` (offset 1056; `Cpu` grows to 1072 bytes, 16-byte aligned), set by `vm_new` (all ones for the user-mode vCPUs), read by `MRS ID_AA64ISAR0_EL1` and by the crypto handlers (one test per instruction). The JIT reads it at compile time: it's fixed for a VM's life, so block keys don't change; a block with a crypto instruction on a VM without the feature ends with the UNDEFINED exception, as today's unallocated words do.
- **Host side:** `web/vm.ts` `BootOptions.crypto?: boolean` (and `Counter`/offset constants that follow `Cpu`'s size); the native runners (`core/tests/common`) likewise; `ABI_VERSION` 18 → 19. The benchmarks get `alpine_crypto_ce_jit` (feature on) next to `alpine_crypto_jit` (off), and the test kernel of loop 3 boots with it on.

### FP semantics (a known hard spot)

- Wasm arithmetic is round-to-nearest-even only. Other `FPCR.RMode` settings and `FZ` go through a software slow path: `core/src/fp.rs`, our own implementation written from the ARM pseudocode (FPRound with tininess before rounding, FZ, DN, the ARM NaN order) over one generic u128 unpack/round/pack for half, single and double. It was chosen over porting SoftFloat in M2, being smaller and ARM-specific; TestFloat 3e validates it. Single and double add/sub/mul/div/sqrt take host arithmetic in round-to-nearest-even when inputs are normal and the result is normal above the smallest binade, with the Inexact flag computed exactly.
- Wasm NaN payloads are nondeterministic. After each FP op, a rarely taken branch fixes up NaNs to ARM propagation rules (or to the default NaN when `FPCR.DN=1`).
- Core wasm has no scalar FMA. `FMADD` and friends use the exact software FMA in `fp.rs`, validated against TestFloat.
- Cumulative exception flags in `FPSR` are computed lazily or on demand.
- **The JIT's FP fast paths (M6 loops 5–6; design before code, as the kickoff asked).** Scalar and vector FP arithmetic is inline only where the result and the flags are exactly the interpreter's, and the helper runs the instruction otherwise:
  - *Block guard.* Before a block's first inline FP arithmetic instruction (after the FPEN check), one test: FPCR.RMode is round to nearest even **and FPSR.IXC is set already**. Both hold for the rest of the block: FPCR and FPSR change only through MSR, which ends a block, and helpers only OR flags into FPSR. If the test fails, the block's FP arithmetic runs through helpers (which set IXC on the first inexact result, so the next run of the block is fast).
  - *Why IXC set is enough.* With normal inputs (no zero, denormal, infinity or NaN) and a result that is normal and above the smallest normal binade, the only exception an add, subtract, multiply, divide, square root, conversion or fused multiply-add can raise is Inexact: no Invalid (no NaN or infinity in), no Divide-by-Zero (no zero divisor), no Overflow (the rounded result is finite), no Underflow (the exact result can't be tiny when the rounded one is above the smallest normal binade, whether tininess is detected before or after rounding), no Input Denormal. A square root also needs a positive operand. So FPSR is unchanged by the instruction when IXC is already set, and the fast path doesn't need to know whether the result was exact. FZ and DN only act on denormals and NaNs, which the fast path never meets; FPCR.AHP only concerns half precision, which it doesn't do.
  - *Per instruction.* The operands' exponent fields decide normality (integer tests on the bits); the host's IEEE operation in round to nearest even gives the ARM result for normal operands; the result's exponent field is checked afterwards (above 1, below all ones), and a failing check sends the instruction to the helper with the operands untouched. Vector forms test every lane and take the helper if any lane fails.
  - *Fused multiply-add.* Single precision: the product of two singles is exact in double; t = RN64(p + c); RN32(t) equals the correctly rounded RN32(p + c) unless t is exactly halfway between two singles (its low 29 fraction bits are 1 followed by zeros), which goes to the helper (if the exact sum were a midpoint it would be representable in double, so t would be it). Double precision has no exact wasm form (no deterministic FMA; relaxed-simd's `madd` isn't one) and stays a helper call.
  - *Conversions.* SCVTF/UCVTF round to nearest even as wasm's converts do, and can't overflow; FCVTZS/FCVTZU (always toward zero, FPCR aside) are inline for in-range, non-NaN operands (else Invalid). FCVT single↔double likewise with normal operands and a fast result.
  - *Always exact:* FABS, FNEG, FMOV and FCSEL are bit operations with no flags, inline without the guard (FPEN only).
  - Validation: the differential test with FP classes seeded with NaNs, denormals, infinities, zeros and FPCR/FPSR states (RMode, FZ, DN, IXC clear and set), and planted bugs in every guard.

### V8 and our code (M6 loop 0)

What V8 makes of the JIT's modules, from its machine code (`tools/v8code.ts`: a guest under the JIT in Node with `--print-wasm-code`, filtered by function name; JIT functions are named `<va>_pa<pa>`) and from Chromium runs (its Linux build has no disassembler: measure there, read code in Node). Numbers: `bench/interp/REPORT.md` "M6 loop 0".

- **No trap handler on Linux arm64.** V8 reserves guard regions but bounds-checks every access explicitly (load the memory size, compare, branch) in Chromium and Node on this host, as on Android; Chrome on macOS and x86_64 uses guard pages instead. Checks are up to 27% of the integer guest's time here (`--no-wasm-bounds-checks`, a diagnostic only). V8 checks a group of accesses to one base once (a function's entry loads), but after a call or across branches it checks each access again, and it has no range analysis for masked indexes (`i32.and`). A constant address below the memory import's declared minimum needs no check, and one below 32 KiB is a single `str x, [membase, #imm]` on arm64; a larger one costs a `movz`/`movk` pair per access. **Tried and not kept (loop 0):** the `Cpu` through its constant address (the heap's, then a low slot below `--global-base` with the stack after static data): placement-averaged over 15 `Vcpu` addresses in Node, integer +6.5%, CoreMark +4%, EL1 MMU off even, MMU on −3.6% (register pressure). Not worth the layout change now; revisit when vector registers move to locals (loop 3) and register pressure changes. **Re-tried after loop 11's branch hints** (the vCPU parameter set from the constant at each function's entry, the import's minimum covering the `Vcpu`; Node, three placements): integer +7%, CoreMark −1 to −10%: still mixed, not kept. In this V8 build, loads through the vCPU base go unchecked (`ldr x, [x5, #imm]`) and stores are checked explicitly, so what a constant base saves is the store checks at block exits. Numbers on this host include checks that users on macOS and x86_64 don't pay.
- **Placement effect (loop 0): where guest data falls relative to the `Cpu` changes a hot loop's speed by up to 40% on the M4**, with byte-identical JIT code: the integer guest runs at ~2500 or ~3750 MIPS depending only on the `Vcpu`'s address or on a sub-page offset of guest RAM (Node; Chromium splits at other placements), CoreMark at ~1200 or ~1500. A hardware aliasing effect (the VM exposes no PMU to say which unit); M5's one-run "slow modes" are plausibly it. **Rule for benchmarks:** the small guests (`bench/interp`'s integer, FP and CoreMark guests, interpreted and JIT) run at eight fixed guest-RAM offsets within a page, each a fresh core, and report one median per placement; never rank two builds on one placement. The boots touch enough data to average it out.
- **TurboFan-only and default tiering agree on steady-state JIT code**: the integer guest runs at 3740–3830 MIPS under both, at HEAD and at step 8.4's commit. Default tiering starts ~10% slower for its first ~20 ms (tier-up), which widens its IQR. The step 8.4 "TurboFan-only −33%" and step 8.5's one-in-four slow mode don't reproduce in 20 runs on the now-dedicated host (both were about half speed for a whole run, as outside load would make them): treat single slow runs as suspect and repeat them. Host load on the Mac doesn't move the VM's vCPUs to slower cores (measured), but the host's clock state moves a run by up to ~8%.
- **The tiering budget (M6, diagnostic):** Alpine's JIT code time is two-thirds Liftoff (a flat tail of ~4000 lukewarm functions, none above 0.03%). V8 tiers a function up after ~13M "bytes executed" (`--wasm-tiering-budget`, charged in machine-code bytes at returns, tail calls and back-edges); lowered to 2M, Alpine boots in 12.3 s instead of 13.4 s in Node, at 0.5M in 12.0 s. Not something we can set for users, and padding functions to spend the budget faster would cost more in code size and Liftoff compiles than it saves. Fewer, larger modules (loop 10.1) is the lever we have.
- **Hint the slow paths (M6 loop 11).** V8's wasm calls have no callee-saved registers, so TurboFan spills every value live across a call, at its definition, if any path calls: the load/store slow paths and helper exits cost the hot path spills. Branch hints (the `metadata.code.branch_hint` section, `wasm::Code::hint`; on by default in Chromium 153) make the cold side deferred code, where the spills go: integer guest +9%, EL1 guests +61–83%, CoreMark +7%. **Rule:** every new `if`/`br_if` around a helper call or a fast-path check gets a hint (likely for fast paths and budget checks, unlikely for helper exits and traps); leave data-dependent branches (`TAKEN`, the guest's own conditions) unhinted.
- **A growable shared memory reloads its size before every checked access (M6, after loop 6).** TurboFan loads the bound from the instance (`ldur x, [instance, #39]`) at each access, since another thread may grow the memory; with a fixed-size memory (initial = maximum, and the importing module declaring the same limits) it loads it once per function, as it does for an unshared one between calls. In CoreMark's hottest region: 29 reloads → 2, code 2192 → 1704 bytes. **Not kept:** it needs the whole memory sized up front, so the core's heap can't grow it (Rust's dlmalloc does) and the host can't grow it for RAM; the experiment (a bump allocator, RAM at the top of a fixed memory, in Node) was dominated by the placement effect (CoreMark flipped between ~1650 and ~2130 MIPS with the heap's layout, whichever memory kind), so no gain could be shown. M9 has it.
- **The jump-cache probes** (step 7.3's 12%) cost nothing measurable at steady state now that hot loops are regions.
- **The FP guest runs 36% faster under TurboFan-only** because V8 inlines compiler-rt's u128 shifts (`__lshrti3`, `__ashlti3`) into `fp.rs` there, and doesn't under dynamic tiering (its inlining follows Liftoff's call-count feedback): 14% of the FP guest's time goes to calls to them. Core code, not JIT code; inline FP (loops 5–6) takes the hot paths out of the helpers.
- The M0 spike on this host (`bench/spike/REPORT.md` "Re-run on arm64"): polymorphic `call_indirect` 2.5 ns (x86_64: 11), so dispatch overhead shows on x86_64 more than here.

## 4. Testing strategy (starts in M0)

Testing is layered. The cheaper layers run on every commit.

1. **Native unit tests** (`cargo test`) cover the decoder, ALU and flag semantics, bitfield/shift/extend helpers, the MMU walker, the GIC state machine and the virtqueue parser.
2. **Instruction differential testing against real hardware (golden corpus).**
   - Generate random or structured instruction sequences plus initial register/memory state, risu-style.
   - A tiny static harness loads the state, executes and dumps the state. It runs on two oracles:
     - **QEMU user mode** (`qemu-aarch64`, via binfmt on any x86_64 dev machine): always available and used for day-to-day corpus growth. QEMU's A64 is itself validated against hardware with risu, but it can still be wrong.
     - **Real hardware:** the M4 Mac mini (`macmini.lan`, macOS 26), in a Linux VM. EL0 code runs natively there. This is the authoritative oracle. The corpus is re-validated on it periodically and whenever QEMU and our emulator disagree.
       - The VM is **Lima** (`vz` backend, Virtualization.framework, plain mode) instance `oracle`: Debian 13 arm64, 4 vCPU, 8 GiB, 60 GiB disk, 4K pages. It was created with `limactl create --name=oracle --vm-type=vz --cpus=4 --memory=8 --disk=60 --plain template:debian-13`. Reach it with `ssh macmini.lan /opt/homebrew/bin/limactl shell oracle <cmd>` (Homebrew isn't on the non-interactive ssh `PATH`).
       - Apple's hypervisor filters the ID registers, so the guest sees v8.x/v9 features that PLAN §1 leaves out: `paca pacg bti` plus `sb flagm2 frint i8mm bf16 afp dit`, and no SVE or SME. PAC hint-space instructions (e.g. `PACIASP`) really sign pointers there, while our emulator treats them as NOPs. The corpus generator must exclude them, or the comparator must skip the registers they affect.
     - Homebrew `qemu` (11.1) on the same Mac provides `qemu-system-aarch64 -accel hvf` for the system-level oracle (item 3).
   - The results are committed as golden files. Every CI run compares the interpreter (native build) and the JIT (in Node/V8) against that corpus. The oracles are only needed again when the corpus grows, so the Mac doesn't need to be always-on.
   - The generator must avoid CONSTRAINED UNPREDICTABLE and IMPLEMENTATION DEFINED cases (for example `LDP` with `Rt==Rt2`, or writeback with `Rn==Rt`). Otherwise the oracles legitimately disagree.
   - **Corpus format (M1, `webpc-corpus 1`):** `tests/corpus/<group>.txt`, line-oriented text. Each test has `code`, a `seed` (splitmix64 expands to X0–X30, SP, NZCV, then the 8 KiB data region, then V0–V31 as low/high u64 pairs; FPCR and FPSR start at 0), `in` overrides, then the oracle's `out` (changed registers), `mem` (changed bytes) and `exit` (`end`, or `sigill`/`sigbus`/`sigsegv`/`sigtrap` with PC offset, `si_code` and fault address). A `note qemu: …` line records a QEMU result that differs from the M4's. New keys are additive (M2 added `v0=0x<32 hex digits>`, `fpcr=` and `fpsr=`); anything else bumps the version. Fixed guest VAs: code at `0x100000` followed by a `brk #0` end marker, data at `0x200000`, harness at `0x400000`.
   - **Tooling:** `tests/harness/harness.c` (static, freestanding, general registers only in C; state loaded by an asm trampoline, including FPCR, FPSR and V0–V31, and dumped from the signal `ucontext` and its `fpsimd_context` record on an alternate stack), `tools/corpus/gen.ts` (deterministic generator), `tools/corpus/run.ts` (runs QEMU and the M4, writes the golden files; `node tools/corpus/run.ts [--oracle qemu|m4|both] [group…]`), and `core/tests/corpus.rs` (the comparator in `cargo test`).
   - **Known oracle behavior** (M1 findings; the generator avoids these):
     - Both oracles implement FEAT_LSE2: misaligned exclusives, `LDAR`/`STLR` and LSE atomics only fault when they cross a 16-byte granule. We don't advertise LSE2 and keep the v8.0 rule (natural alignment or an alignment fault). Wasm atomics need natural alignment anyway, so the check costs nothing extra.
     - QEMU's `max` CPU has MTE (`ADDG`/`SUBG`, `STGP` execute), while the M4 raises SIGILL, as we do. QEMU's `DC ZVA` block is 512 bytes; the M4's is 64, as is ours.
     - The M4 guest also advertises `lrcpc ilrcpc dcpop dcpodp flagm uscat sha3 sha512 asimddp asimdrdm fphp jscvt fcma`, so the generator must not emit those instructions either.
     - M2: beyond v8.0 FP/AdvSIMD the M4 runs FP16 (including FP16 FMOV and the fixed-point conversions with immh = 001x), BF16 (BFCVT is the FCVT encoding with ftype 01, opc 10), FHM, RDM, DotProd, I8MM, FCMA, JSCVT and FRINTTS, plus AES/PMULL/SHA1/SHA2 (M6.5). The generator emits none of them. QEMU agreed with the M4 on every M2 test.
3. **System-level oracles**, for things that can't run at EL0 on real hardware:
   - `qemu-system-aarch64 -M virt` for behavioral comparison (traces of exceptions and system register state).
   - The same QEMU with `-accel hvf` on the Mac: real Apple hardware running EL1 code (MMU, exceptions). The devices are still QEMU's.
   - The Sail ARM model as the authoritative reference for disputed corner cases.
4. **JIT vs interpreter lockstep.** Run the same guest in both and compare architectural state at region boundaries. A "JIT stress" mode sets the compile threshold to 0 and uses a tiny code cache so eviction and invalidation are exercised constantly. **How long (M5 step 9):** the long stress runs (Alpine 4.25 h, LTP 2.9 h) ran once, at M5's end, and found nothing the short runs, the differential test and the exact-step boots hadn't; **since M6 they're not run routinely** (the user, 2026-09-27: hours of stress are unlikely to catch what ~10 minutes don't), only when a change targets eviction or invalidation specifically. For coverage per minute, prefer short stress variants (a tiny cache with the default threshold, compile-on-sight with a big cache, tier-up after one entry) over longer runs.
5. **FP conformance.** TestFloat vectors for every FP op, rounding mode, FZ/DN combination and FMA. `scripts/testfloat.sh` (part of `scripts/ci.sh`) builds TestFloat 3e under `target/testfloat` and runs `core/tests/testfloat.rs`, which checks every case under all four FZ/DN combinations. The golden corpus also runs on the wasm core in Node (`tests/corpus-wasm.test.ts`), because host float behavior is where native and wasm builds can diverge.
6. **Bare-metal system tests.**
   - Small EL1 assembly/C tests report results through PSCI `SYSTEM_OFF` with a code.
   - Run **kvm-unit-tests** (arm64: selftest, psci, gic, timer, mmu-related) unmodified as guests.
   - **Harness (M3):** `tests/baremetal/`: `start.S` (stack, vectors that call `on_exception(frame, vector)`, FP on, `run_el0()` to drop to EL0 and come back through SVC #1) plus one C file per test, built with host clang and lld by `build.sh` into committed flat `.bin`s loaded at `0x4000_0000`. A test passes when it calls PSCI `SYSTEM_OFF` with x1 = 0 (our own convention); x1 is otherwise the number of the failed check, and `power_off` also prints `exit <code>` on the PL011. `core/tests/baremetal.rs` runs them all in `cargo test` on a whole `Vm` and checks the console agrees. `oracle.sh` runs the `-DORACLE` builds (implementation-specific checks such as ID register values left out) on `qemu-system-aarch64 -M virt,gic-version=2` TCG, and `oracle.sh --hvf` the `-DORACLE -DHVF` builds on the Mac, both reading the exit line from the UART. HVF has no GICv2, so tests marked `oracle: needs GICv2` (timer, gic, uart) run on TCG only. Tests must not rely on reset values of registers the architecture leaves UNKNOWN or IMPLEMENTATION DEFINED, and must pick unmapped addresses that are also unmapped on `virt` (its flash covers `0x0`–`0x0800_0000`).
7. **Boot tests.**
   - A deterministic Buildroot kernel + initramfs boots, runs a script, powers off, and its console output is asserted.
   - Later: Alpine and Debian arm64 from virtio-blk.
   - These run natively (headless runner around core) *and* in Chromium through Playwright.
8. **In-guest suites.**
   - Subsets of LTP, the kernel's arm64 selftests (fp, signal, abi), BusyBox tests and language test suites (Python).
   - Guest JITs (Node/V8, LuaJIT) exercise code invalidation.
9. **Memory model and SMP** (from M7): herdtools7 `litmus7` ARMv8 litmus tests run in the guest, with observed outcomes checked against the allowed set. Atomics stress tests too.
10. **Fuzzing.** `cargo-fuzz` on the decoder (never panics and matches the reference disassembler), the virtqueue/descriptor parsing and the DTB/boot loader inputs.
    - **Decoder (M1):** `core/fuzz`, a separate workspace so Capstone never reaches the core's builds. `cargo fuzz run decode` (from `core/`) runs libFuzzer. `cargo run --release --bin sweep` (from `core/fuzz/`) checks all 2³² words in about 2 minutes on 16 threads: every word executes on a scratch vCPU without panicking, and "valid instruction" agrees with Capstone 5.0. `core/fuzz/src/check.rs` lists the expected differences: features we leave out (SVE/SME, MTE, PAC outside the hint space, RCpc, LOR, MOPS, HBC, and since M2 FP16, BF16, FHM, RDM, DotProd, I8MM, FCMA, JSCVT, FRINTTS, SHA3/SHA512/SM3/SM4, and the v8.0 crypto until M6.5), CONSTRAINED UNPREDICTABLE encodings Capstone rejects, and should-be-one fields that the M4 ignores. Since M2 only EL1 system encodings are left out of the comparison as unimplemented; the full sweep was clean again on 2026-09-25. `core/build.rs` relaxes those fields to match the M4, except in CAS/CASP, where the M4 raises UNDEFINED. The fuzzer isn't part of `scripts/ci.sh` (it builds Capstone from C); rerun it when the decoder changes.

**CI:** everything lives in plain scripts (`cargo xtask` or shell) that run the same way locally and in CI. The CI config is a thin wrapper around them, so no particular CI host is required.
- Any Linux machine (x86_64 or arm64): native tests, wasm build, Node JIT difftests, Playwright Chromium boot tests. **Since M5 step 8 the development host is the Lima VM `dev` on the M4 (openSUSE Tumbleweed aarch64; CLAUDE.md "Development environment")**; the x86_64 desktop was the host before, and its numbers aren't comparable with the VM's.
- The M4 Mac (ssh into the Linux VM, or a self-hosted runner for whatever forge you use): growing and re-validating the corpus, native arm64 benchmark baselines, and Chromium on macOS/arm64 benchmarks.

## 5. Performance monitoring and benchmarking (starts in M0)

### Built-in instrumentation

- Counters in shared memory, readable live by an overlay and dumped by the harness:
  - guest instructions retired, split into interpreter vs JIT;
  - regions compiled, compile time, wasm bytes, modules instantiated;
  - TLB hits and misses, page walks;
  - exceptions by class, IRQs;
  - helper calls by opcode (tells you what to inline next);
  - flag materializations, invalidations;
  - dispatcher round-trips vs chained transitions.
- **Guest PC sampling profiler.** Another thread samples the vCPU PC from shared memory, and the samples are symbolized with the guest `vmlinux`/binaries. This shows which *guest* code is slow under emulation.
- JIT modules carry a wasm **name section** naming functions after guest PCs, so DevTools and `perf` profiles are readable.
- `performance.mark`/`measure` around compile, instantiate, device I/O and boot phases, so they show up in DevTools and Perfetto traces.

### Benchmark harness

- A **bench image** (Buildroot) contains the prebuilt workloads and a `/bench/run.sh` that prints `BENCH <name> <value> <unit>` to the serial console. The same binaries also run natively and under QEMU.
- `bench/run.ts` works like this:
  1. Playwright launches a **pinned Chromium**.
  2. The page is served with COOP/COEP headers (needed from M7).
  3. The page boots the bench image in deterministic mode.
  4. The harness parses serial output and repeats N runs.
  5. Median and IQR go to JSON along with the counters and the browser/commit metadata.
- The same harness runs in Node for quick development iteration. **Chromium numbers are the ones that count.**
- Results are stored per commit, with trend charts added once there are enough data points. Shared or virtualized machines are noisy, so use them for trends and a dedicated quiet machine for regression gates (for example, fail on a >5% median regression on a key benchmark).
- Tiering matters: V8 runs new wasm under Liftoff and tiers up to TurboFan later. Always report cold and warm numbers, and compare runs with Liftoff or tier-up disabled through `--js-flags` to understand the effect.
- `perf` with V8's `--perf-prof` (via `--js-flags`) handles native-level profiling of JIT'd wasm on Linux.
- **Benchmark on two host architectures:** Chromium on x86_64 Linux and Chromium on macOS arm64 (the M4). V8 lowers wasm differently on each: register count (16 vs 31 GPRs matters for locals-heavy JIT code), bounds-check strategy and SIMD lowering. Results can diverge.

### Workloads and KPIs

| KPI | Workload |
|---|---|
| Boot time to shell | deterministic Buildroot kernel+initramfs; later Alpine/Debian |
| Integer throughput (guest MIPS) | CoreMark, Dhrystone |
| Mixed / realistic | `7z b`, SQLite `speedtest1`, compiling a C file with GCC in the guest (heavy code/JIT churn) |
| SIMD | `openssl speed` (NEON paths), glibc string/memcpy microbenchmarks |

### Comparison targets

**Since M6's exit (the user, 2026-09-27):** peer comparisons are rare: the M6 exit table measures them once, and they aren't repeated per loop or kept as variants. Performance work and regression checks compare webpc against itself, in Chromium (and Node for iteration).

**qemu-wasm is dropped as a peer (the user, 2026-09-27):** in the M6 exit table it booted Buildroot 4.7× slower than webpc and computed CoreMark wrong (CRC mismatches); it looks like a personal experiment abandoned about a year ago, and its public demo doesn't feel fast either. Don't spend more time comparing against it; its build and artifacts were deleted.

- **Native arm64** (M4 Linux VM). Gives the slowdown factor, the headline number.
- **QEMU TCG** (`qemu-system-aarch64 -M virt`, native, same kernel and image). The practical reference for "good" emulation speed.
- **In-browser peers** running the same workload built for their ISA, in the same Chromium:
  - v86 (i686);
  - TinyEMU/JSLinux (riscv64);
  - WebVM/CheerpX (proprietary, comparison only).

### M0.5 — Memory architecture experiment (decision gate)
**Status:** done 2026-09-25 on x86_64 and arm64 (M4, macOS; machine code from the arm64 Linux VM). See `bench/spike/memory/REPORT.md` §5. **Decision: A, on both hosts.**

This decision shapes the TLB entry format, the core's memory layout and the Rust target, so it's made before M1 writes any of them.
Code lives in `bench/spike/memory/`, and results plus the written decision go in `bench/spike/memory/REPORT.md`.

**Candidates:**

| | Layout | Rust core target |
|---|---|---|
| A | One wasm32 memory: core state + guest RAM (≤ ~3.5 GiB) | wasm32 |
| B | wasm32 core memory + N wasm32 RAM memories (multi-memory, ≤ 4 GiB each). The TLB entry carries a memory index | wasm32 |
| C | One memory64: core + RAM | wasm64 (tier 3, needs build-std, which threads already need) |
| D | wasm32 core memory + one memory64 RAM memory (multi-memory mixing index types). Generated code uses i64 addresses on the RAM memory | wasm32 |

**Capacity experiments.** Run on each host: x86_64 Linux and the M4 Mac, both in Chromium; Firefox as secondary data. Scale sizes to host RAM.
- Maximum size per memory, for wasm32 and memory64, shared and non-shared, and maximum declarable `maximum`.
- Maximum total across many memories in one page, including memories created in dedicated workers. Workers live in the same renderer process, and a `SharedArrayBuffer` can only be shared within one process, so one VM's RAM can't be spread across processes.
- Whether large allocations are lazily committed: reserved vs resident memory after touching only part of the RAM. Also how many large reservations fit in V8's address space.
- How failure shows up: a catchable `RangeError` on allocate/grow, or a tab crash ("Aw, Snap!") when the pages are touched.
- Whether shared memory64 and atomics on non-zero memories are supported.

**Cost experiments.** Kernels shaped like the planned JIT output: inline TLB lookup + load/store, mixed with ALU ops at a realistic ratio (about 1 memory op per 3 instructions). Access patterns: sequential, random (pointer chase), and many pages spread over large RAM. Run under Liftoff and TurboFan, on both hosts.
- A vs C vs D: what the bounds checks cost for memory64.
- B: memory 0 vs memory N used alone, to see whether V8 gives non-zero memories guard pages or explicit checks (**asymmetric** cost). Then the memory-select strategies:
  1. an `if`/`br_table` on the TLB memory index;
  2. a guarded specialization on the memory seen at compile time, with a slow-path exit when it differs;
  3. a helper call.
  Each is measured with a predictable and with an alternating memory index.
- Access from the Rust side (interpreter, virtio DMA). Rust can't address non-zero memories directly, so this means calls into a small hand-written accessor module.
- **Check the machine code, not just the timings.** Use `perf annotate` on V8's `--perf-prof` jitdump output, or a d8 build with the disassembler, to confirm what bounds checks and memory-base loads each engine actually emits.

**NUMA follow-up** (only if B shows asymmetric cost):
- Describe each RAM memory as a NUMA node in the DTB: `numa-node-id` on the memory nodes, plus a `distance-map`.
- vCPUs belong to node 0 and the extra memories are CPU-less nodes. Linux then allocates from the fast memory first and spills over by distance.
- Validated in M3 once Linux boots. It only changes DTB contents, so nothing in this decision depends on it.
- To check then: whether distro arm64 kernels enable `CONFIG_NUMA`, and whether memory tiering/demotion applies to DT-described CPU-less nodes. Disable NUMA balancing: its hinting faults would be expensive under emulation.

**Decision rule** (the threshold can be adjusted):
- Measure the realistic mixed kernel, not the bare access path.
- If a >4 GiB-capable layout (B, C or D) costs **≤ 5%** vs A, adopt it, even if today's browsers can't back more than 4 GiB.
- Otherwise adopt A and record the measured gap, so the decision can be revisited as engines improve. The single lowering point keeps a later switch contained to the emitter and the core allocator.

- **Exit:** `REPORT.md` with capacity tables, cost tables, machine-code evidence and the decision. The §1 "Guest memory" row is updated.

- **Progress:**
  - Step 1 (EL1 state and exception model) done: PSTATE EL/SPSel/DAIF with banked SP, exception entry and ERET (illegal returns take the Illegal Execution State exception), EL0→EL1 traps (`SCTLR_EL1` UCT/UMA/DZE/UCI/nTWI/nTWE, `CPACR_EL1.FPEN`), and the system register table in `core/src/interp/sys.rs`. `interp::run` still hands exceptions to the host (corpus, benchmarks); `interp::run_system` takes them into EL1 and exits only for HVC and unimplemented instructions. `Cpu::default()` is a Linux user process at EL0, `Cpu::reset()` the EL1 boot state. The TLB is the M0 spike's shape: direct-mapped, 4096 × {tag, addend} per (EL, read/write/execute), the tag being the page VA with bits 11:0 all ones (bits 11:3 the inverted memory index), compared with `(va + size - 1) | 0xfff` so page-crossing accesses miss and are split. It holds no ASIDs and is flushed when the effective ASID or `SCTLR_EL1.M` changes (since M6 loop 9, an ASID change and `TLBI ASIDE1` drop only the non-global entries). Faults carry kind, level and access (ESR WnR, CM). `SCTLR_EL1.A` alignment faults, SP alignment faults (`SA`/`SA0`, EC 0x26), and cache maintenance by VA translates and faults like a read (`DC IVAC` like a write). `tests/baremetal/mmu.c` passes natively and on QEMU TCG. Interpreter MIPS with the MMU off: −7% integer on x86_64, −4% on the M4, FP unchanged within noise (`bench/interp/REPORT.md`, M3), after splitting the interpreter into a flat and an MMU copy chosen outside the instruction loop.

  - Step 4 (platform) done: `core/src/vm.rs` (the ABI 5 `Vm` and run loop, §2), `gic.rs`, `pl011.rs`, the timer registers in `interp/sys.rs`.
    - **Run loop:** chunks of at most 1024 steps (32,768 since M6, below) (instructions retired plus exceptions taken), cut at the next timer deadline so timers fire on their exact tick. Between chunks: the signal word, the interrupt lines into the GIC, and IRQ entry (vector +0x80) when `PSTATE.I` is clear. An MSR that clears `PSTATE.I` ends the chunk (`Exit::Resync`) so a pending IRQ is taken right after it; ERET didn't, so an IRQ unmasked by ERET waited up to one chunk, which made the chunk size visible to guests. **Since M6 (user's OK, 2026-09-27)** ERET ends the chunk the same way, deterministic guests take identical steps at any chunk size (checked at 1024–131,072 on every suite), and `CHUNK` is 32,768: hot JIT loops return to the run loop 32× less often (Alpine −14% in Node). The step constants moved once with the ERET fix: Buildroot's boot unchanged (40,909,861), the device test 113,872,868 → 113,841,233, LTP/kselftests 2,737,414,881 → 2,747,263,866, Alpine 3,009,151,562 → 3,009,537,573. Realtime mode pays up to a chunk (~0.1 ms) of signal and timer latency.
    - **Deterministic time:** counter = steps × `ticks_per_insn` + ticks skipped by WFI. Timer registers and `ISR_EL1` leave the interpreter (`Exit::Platform`) and complete in the loop with the exact count. WFI completes when the GIC signals an interrupt (masked or not); otherwise time jumps to the next armed timer deadline, and with none the run returns the idle exit (value u64::MAX), PC on the WFI. WFE completes at once. Realtime mode is not implemented: `vm_new` rejects `deterministic = 0`.
    - **Device MMIO** never touches the interpreter's fast copies: an access to a non-RAM PA faults there, and the loop re-executes that one instruction on a third `Bus`, `vm::Io`, which sends it to the device (handlers read before writing registers, so the retry is exact). A PA with no device is still an external abort. The `Io` copy of `exec` is ~22 KB of cold wasm; the flat and MMU copies are unchanged and interpreter MIPS moved by less than noise.
    - **GICv2** (IHI 0048B, no Security Extensions): 64 INTIDs, all group 0 and IRQ (IGROUPR RAZ/WI), 8 priority bits, BPR group priority for preemption, IAR/EOIR/DIR with `EOImode` split, self-SGIs through `GICD_SGIR`, ICFGR (SGIs edge, read-only), and **`GICD_ITARGETSR` RAZ/WI**, which the spec prescribes for a uniprocessor GIC and QEMU does too (M7 needs real targets).
    - **PL011**: DR, FR, IBRD/FBRD, LCR_H, CR, IFLS, IMSC, RIS/MIS/ICR, DMACR, the PeriphID/PCellID registers; transmit is instant (FR.TXFE always set, TXRIS set per byte and cleared by ICR), RX/RT pending while the RX ring has data; interrupt SPI 1 (INTID 33). A DR write into a full TX ring returns the TX-full exit with the store not retired.

### M6.5 — Crypto extensions
- AES (`AESE`/`AESD`/`AESMC`/`AESIMC`), `PMULL`/`PMULL2` (including the 64-bit form), SHA1 and SHA256, in the interpreter and the JIT. Advertise them in `ID_AA64ISAR0_EL1` (AES = 2 for AES + PMULL, SHA1 = 1, SHA2 = 1) and the hwcaps only once both tiers pass **and** they beat the NEON-only baseline (below). The decoder already has the encodings (`a64.inc`); since loop 1 the interpreter runs them (`core/src/crypto.rs`) whether or not they're advertised, and the decoder sweep expects them (`core/fuzz/src/check.rs`).
- They come after the JIT so the lowering can be designed with it (wasm SIMD128 has no AES or carry-less multiply), and before SMP so they're settled before the concurrency work.
- **Approach (drafted 2026-09-27, during M6; decisions confirmed the same day; kickoff `M6.5-KICKOFF.md`):**
  - *Not the Web Crypto API.* The instructions are single rounds and bare multiplies: `AESE` is one round without a key schedule, `SHA256H` is four rounds of the compression function from the registers' state, and `PMULL` is a carry-less multiply. `crypto.subtle` offers only whole operations (a full cipher with its own key schedule, a digest of a padded message), and only asynchronously, while the vCPU runs synchronously inside one wasm call. A paravirtual crypto device isn't worth it either: userspace would need AF_ALG, which Linux 7.2 deprecated after Copy Fail (CVE-2026-31431).
  - *Interpreter: our own Rust in the core* (`core/src/crypto.rs`), written from FIPS 197, FIPS 180-4 and the Arm pseudocode (nothing ported). It's the reference semantics, the JIT's helpers and the unit-tested layer. Scalar, since the core is built without `simd128` (M9).
  - *JIT, first:* every crypto instruction goes through the generic helper, so the tiers agree from day one and `jit_helper_report` shows what's worth inlining.
  - *JIT, then:* fuse `AESE`+`AESMC` and `AESD`+`AESIMC` on the same register into one round (compilers, OpenSSL and the kernel always emit them adjacent; Arm cores fuse them too), and inline the rounds in SIMD128. SubBytes uses `i8x16.swizzle` (V8 lowers it to one `TBL` on arm64 and to `pshufb` on x86): either the S-box as 16 swizzles of 16-byte slices, or the vector-permute nibble inversion from Hamburg's paper (the technique behind OpenSSL's `vpaes`, implemented from the paper), whichever measures faster. ShiftRows is a constant swizzle; MixColumns is swizzle rotations plus `xtime` with shifts and masks. SHA1 and SHA256 are 32-bit ALU work, inlined only if the histogram asks for it. `PMULL` 64×64→128 stays a helper unless wasm gets a wide multiply (the wide-arithmetic proposal; check what Chromium ships).
  - *Constant time (decided 2026-09-27).* Guests choose the AES instructions because hardware runs them in constant time, and a table-driven emulation would leak cache timing to other code in the same guest. The user expects little security-critical work in this guest, so this is cheap insurance, not a driver: no secret-dependent memory indices or branches in any tier, which rules out T-tables. The swizzle lowerings are table-free by construction; the interpreter uses a bitsliced or arithmetic S-box; `PMULL.1Q` uses integer multiplies with holes (BearSSL's `bmul` idea, reimplemented, credited in `THIRD_PARTY.md`). If constant time costs a lot somewhere, report the number rather than quietly dropping it.
  - *Advertise only if faster (decided 2026-09-27).* Advertising the extensions makes OpenSSL and the kernel leave their NEON-only paths (`vpaes` on `TBL`, GHASH on the 8-bit `PMULL`, the scalar and NEON SHA-256), which have run inline since M6 loop 4. If the emulated instructions aren't faster than those under our JIT, advertising them is a regression, so they stay implemented and tested but unadvertised until they are.
  - *Guest-visible change.* With the hwcaps set, the kernel picks its CE drivers and library code, so boot step counts change once. Record the new counts with that change, and re-baseline the boot benchmarks in the same session.
- **Progress:**
  - Loop 0 (the bar) done: OpenSSL 3.5.8 in the user image, run by `webpc.phase=crypto` in realtime mode (`--only alpine_crypto_jit`; a check line against arm64 hardware's digests and ciphertexts; `webpc.armcap=X` sets `OPENSSL_armcap`); `alpine_user_jit`'s default run and the Alpine boot benchmark unchanged but for the step constant. ### M7 — SMP
- One worker per vCPU on shared memory. PSCI `CPU_ON`, GIC SGIs, WFI → `Atomics.wait`, broadcast TLBI/IC with `DSB` completion, per-worker code caches with cross-vCPU invalidation.
- **The GICv2 model is single-CPU (M3, `core/src/gic.rs`)** and must become per-CPU: banked SGI/PPI state (enable, pending, active, priority) and a CPU interface per vCPU; `GICD_ITARGETSR` implemented (it's RAZ/WI now, as the spec prescribes for a uniprocessor GIC) with SPIs routed by target; `GICD_TYPER.CPUNumber`; SGIs to other CPUs and to all-but-self through `GICD_SGIR`, with the source CPU in `GICC_IAR` bits 12:10 (always 0 now); `GICD_CPENDSGIR`/`SPENDSGIR` (RAZ/WI now). The GIC also moves out of the single `Vm` into state shared by the vCPU workers, with a cross-worker way to raise an IRQ line.
- litmus7 suites and atomics stress. Scaling benchmarks (parallel `make`, `7z b -mmt`).
- **Revisit 128-bit atomics.** Wasm has no 128-bit compare-and-swap, so since M1 `CASP` and 64-bit-pair `LDXP`/`STXP` run under one spinlock in `Mem` (`core/src/mem.rs`, `pair_locked`). The lock only excludes other pair operations: a concurrent 64-bit atomic or plain store from another vCPU to the same bytes can interleave with a locked pair op, which breaks single-copy atomicity. Options: make every atomic that can overlap a pair take the lock (hashed per-line locks to limit contention), or stop the world for pair ops. Decide with litmus tests and a CASP-heavy stress test (e.g. lock-free 128-bit queues).
- **Exclusives are compare-and-swap based:** `STXR` succeeds if memory still holds the value `LDXR` saw (ABA-tolerant, like QEMU). Check that litmus7 and the atomics stress tests accept this.
- **Exit:** a multi-core Debian boot is stable under stress, and the scaling curve is recorded.

### M9 — Loose ends (unscheduled)
Open items that no milestone owns yet. Pick them up when a milestone touches the area or a measurement says they matter; move an item into that milestone when it's scheduled.

- **Interpreter speed** (`bench/interp/REPORT.md`). There's no decoded-block cache yet: each instruction is fetched through `Mem::host` and decoded again (`ponytail:` in `interp::step`). FP runs at about a sixth of the integer rate. `FMLA`/`FMADD` always take the exact software FMA, and vector FP goes lane by lane through an `Fpu` context and `u128` lanes. None of this matters while the interpreter is only the JIT's reference and fallback.
- **`Mem::rmw`** is a generic CAS loop (`ponytail:` in `core/src/mem.rs`). Since M6 loop 7 the JIT does LSE add/clr/eor/set/swp as single wasm `atomic.rmw` ops and the interpreter only sees their slow paths, so it matters again only for the interpreter or for M7's contention.
- **Extensions the M4 has and we leave unadvertised**, in case real workloads benefit: FP16 (scalar and AdvSIMD), DotProd, RDM, FHM, FCMA, JSCVT (JS engines use `FJCVTZS`), FRINTTS, BF16, I8MM, LSE2, RCpc, FlagM, SB, DIT, and after M6.5 SHA512 and SHA3 (OpenSSL uses both; SHA3's `EOR3`/`RAX1`/`XAR`/`BCAX` speed up Keccak and are plain SIMD128 lowerings). Each needs the handlers, golden-corpus groups (the generator already knows how to avoid them), the ID register fields and a decoder-sweep update.
- **Arm AARCHMRS JSON:** its in-package proprietary notice is still unread (`THIRD_PARTY.md`). Read it only if we want to generate decoder tables or coverage checks from it.
- **Corpus depth:** some FP flag paths are thin (only 8 `fp_scalar` tests raise Divide-by-Zero). Add biased forms when touching FP again.
- **MMU loose ends (M3 step 3):**
  - (M6 loop 9 kept the global entries across ASID changes; what's left:) the previous ASID's nG entries are dropped at a switch, not kept for when it's current again (per-ASID stashes of the slots `Tlb::ng` lists, invalidated by TLBI; Alpine's boot refills ~0.3M nG entries). The arrays are direct-mapped: ~0.3M of Alpine's misses are conflicts.
  - No Device-memory alignment faults (misaligned accesses to Device memory, or with the MMU off) and no address size fault for VAs past 40 bits with the MMU off (they fault as external aborts).
  - PRFM with a misaligned SP as its base takes an SP alignment fault, where hardware wouldn't.
  - Interpreter speed with the MMU on (M4 step 1, `bench/interp/REPORT.md`): the MMU copy runs the integer guest 36% (x86_64) and 35% (M4) slower than the flat copy, every access a TLB hit; the 1024-step run loop costs nothing measurable. Every fetch goes through the TLB (no decode cache or per-page fetch pointer). Worth a look only if the interpreter's system-mode speed matters before or beside the JIT.
- **Spectre reporting:** Linux prints "detected: Spectre-v4" and "Spectre-BHB" because our implementer-0 `MIDR` is on none of its safe lists; nothing gets mitigated (no SSBS, no SMCCC 1.1 firmware), so it only reports "Vulnerable". Advertising `CSV2_3` (needs the `SCXTNUM_ELx` registers) or answering SMCCC 1.1 `ARCH_WORKAROUND_*` as not required would make it say "Not affected".
- **Platform loose ends (M3 step 4):**
  - GIC: `GICD_CPENDSGIR`/`SPENDSGIR` and `GICC_APR*` are RAZ/WI; SGI source CPU is always 0; no SGIs to other CPUs (M7).
  - Cache maintenance by VA to a device PA faults as an external abort (it would complete on hardware).
  - The timer, GIC and PL011 tests have no hardware oracle (HVF has no GICv2). A GICv3-free subset of `timer.c` (ISTATUS, TVAL, CNTKCTL traps) could run on hvf.
- **Self-hosted debug:** `ID_AA64DFR0_EL1` advertises the architectural minimum (v8.0 debug, 2 breakpoints, 2 watchpoints, 1 context comparator). ARMv8.0 doesn't allow advertising less, so this is the one deliberate exception to "ID registers advertise exactly what's implemented". The breakpoint and watchpoint registers are RAZ/WI, the OS lock is only state, and no debug exceptions are raised (breakpoints, watchpoints, `MDSCR_EL1.SS` single step). Needed for in-guest `gdb` hardware breakpoints and `ptrace` single step.
- **virtio loose ends (M4 step 2):**
  - `VIRTIO_F_EVENT_IDX` isn't offered; notification and interrupt suppression are the flags only. Offer it when an I/O benchmark shows notify exits or interrupts matter.
  - ConfigGeneration is always 0 and there is no host API to change config space under a running driver yet (console resize, block capacity change need one: bump the generation and raise the config interrupt).
  - In async mode a backend can write a guest buffer just after the driver reset the device (the epoch check and the write aren't atomic), as DMA can on hardware; deterministic mode waits, so it can't happen there.
  - The rng is splitmix64 seeded 0 in deterministic mode (and natively in realtime mode too: std has no CSPRNG); the browser uses `crypto.getRandomValues` in realtime mode.

- **JIT inline loose ends (M5 step 4):** The code cache size is settled in step 7 (65,536 blocks: Alpine compiles 56,791 and no longer flushes) and raised in M6 to 262,144 (Debian's boot compiled 183K regions with two flushes, 110K without: 42.9 → 39.3–40.0 s in Node; the cache's only up-front cost is 4 bytes a slot); per-module eviction instead of whole-cache flushes stays open for guests that outgrow that. Buildroot's warm boot under the JIT has a 10× wider IQR than the interpreter's (V8 tiering hundreds of modules at different points, presumably). The helper-call histogram behind group 6 was ad hoc; the counter by `Op` is step 9. SMULH/UMULH are built from 32-bit halves (wasm has no wide multiply yet); `CRC32*` stays a helper.
- **JIT loads/stores loose ends (M5 step 5):** the JIT guests' two modes are gone with chaining (step 7: the dispatcher's `call_indirect` is no longer hot), and the boots' two modes are explained: V8 reuses a module's compiled code when a module with the same bytes is still alive, deterministic boots emit the same JIT modules each time, so a boot ran fast or slow by whether the previous boot's modules had been collected (Buildroot 710 vs 920 ms; TurboFan-only 630 vs 3000 ms; a per-VM nonce in the modules removes the fast mode; speculative inlining and deopts change nothing). The boot benchmarks now force a GC before each boot (a first boot's behavior); a VM rebooted in the same page does get the reuse. kvm-unit-tests `timer` still runs slower under the JIT than interpreted (short blocks around timer polls). Inline accesses assume `SCTLR_EL1.A` = 0 (the dispatcher interprets otherwise); exclusives, LSE atomics, LDTR/STTR, DC ZVA and FP/SIMD loads and stores are helper calls (step 9's histogram decides which to inline; M6 loops 1, 2 and 7 inlined all but exclusive pairs, CASP, LSE min/max and LD2–LD4/ST2–ST4).
- **rustc/LLVM wasm32 simd128 miscompile (found in M5 step 6; low priority since 2026-09-27, when the planned M5.5 was dropped):** the core is built **without** `simd128` (`.cargo/config.toml`) since M5 step 8.2, after the pinned nightly miscompiled the JIT's register-mask code with it three times; the multi-instruction JIT differential test (`tests/jit-diff.test.ts`) caught all three. **Why it's parked:** nothing needs it. The JIT's wasm SIMD (M6's NEON → SIMD128) comes from our own encoder, not from rustc; the interpreter runs at the same speed without it (M4 VM: 138.1 integer MIPS with, 138.5–138.8 without; `bench/interp/REPORT.md` "M5 step 8"); what would use it is SIMD in the core itself (the interpreter's and helpers' NEON paths, memory and CRC fast paths, LLVM's autovectorizer), and M6 moves the hot NEON out of the helpers. **What's known (2026-09-27, work files in `bench/results/local/m55`, gitignored):**
  - *Case 1, reduced:* a `[u8; 32]` compared lane-wise into a `u32` mask gives `0x24929249` instead of `0x92492492` with `+simd128` (standalone crate: `fn make(p) -> (F, u32)`, `#[inline(never)]`, `F { Vec<u8>, [u8; 32], u32 }`, then `(0..32).filter(|&r| f.uses[r] == 1).fold(0u32, |m, r| m | 1 << r)`); in IR, `icmp eq <32 x i8>` + `bitcast <32 x i1> to i32` under `llc -mattr=+simd128` puts lanes 0–15 in bits 31:16 (the 64-lane form likewise). The JIT's use tracking (`emit::Func::plain`) now uses bit masks instead.
  - *Root cause (upstream's to confirm):* the wide `<32|64 x i1>` → `iN` fallback of the WebAssembly backend's `performBitcastCombine` combines the 16-lane chunks in reverse order; LLVM's own `simd-bitmask.ll` (`bitmask_v32i8`) expects the swapped code, and `llc` 22.1.8 and 23 both miscompile the reduced IR. LLVM 23's middle end (the Rust nightly of 2026-08-06, `7608eb7b0`, rust-lang/rust#158734) is what started vectorizing our Rust into that pattern; stable 1.98.1 and earlier nightlies only stay away from it. **Reported as llvm/llvm-project#226741.**
  - *Cases 2 and 3, not yet explained:* step 8.1 (region per-member register states as `Vec<Option<Regs>>` mapped with `map_or` lost a write-back on one edge; now plain `Regs` merged from the empty state) and step 8.2 (loop back-edges lost the loads of their head's register state). Probably the same pattern, unconfirmed.
  - *Toolchain:* nightly is needed only to rebuild std with atomics (`-Zbuild-std`, `-Zllvm-target-feature=+atomics`; the core has no `#![feature]`), and no toolchain has a correct backend, so switching wouldn't help.
  - **If the core ever wants `simd128`** (a measured need, or a toolchain bump that carries the fix for #226741): rebuild the step 8.1 and 8.2 revisions with `+simd128` and check them for the pattern (`bitcast <32|64 x i1>` in `--emit=llvm-ir`; two `i8x16.bitmask` + `i32.const 16`/`i64.const 16` + `shl` in `--emit=asm`); a scan for the pattern in the core's IR (a CI check until the fix is in the pinned toolchain); then turn it on and pass the corpus, `tests/jit-diff.test.ts`, lockstep and the Node boots with it, and compare the interpreter's MIPS. Until then, any toolchain bump leaves `simd128` off.
- **Compiling off the vCPU thread (M5 step 8; → M6 loop 8; measured in M6 and not built: installs take ≤ 1.3 ms each, and guest progress per 100K steps pauses above 16 ms once per Alpine boot, `bench/interp/REPORT.md` "M6 loop 10"; revisit with a GUI guest in M8):** (M6 loop 10.1: after batching, the synchronous install costs ~0.3 s of Alpine's boot, and V8's native work ~1.8 s of which lazy Liftoff compiles are part; the execution-side gain of fewer modules doesn't depend on where they compile.) the vCPU worker does all of the JIT's compile work itself except TurboFan tier-up (V8's background threads): region formation and emission, `new WebAssembly.Module` (validation; `compileNs`, 0.76 s of an Alpine boot) and V8's lazy Liftoff compile of each function on its first call (charged to `jit::steps` in profiles). None of it has to be synchronous: the dispatcher interprets what isn't compiled, and exact steps don't depend on what is. A compiler worker (a second core instance on the shared memory, like M7's vCPU workers) could form, emit and compile (eagerly) and post the `WebAssembly.Module` to the vCPU worker, which only instantiates it and fills its table. Costs a host ABI, a queue and invalidation of in-flight compiles; measure the main-thread share first (step 8 profiles: Buildroot's boot is compile-bound, Alpine's ~1.5–2 s of 17 s).
- **A fixed-size memory for V8's bounds checks (M6, measured in code, not in time):** see §2 "V8 and our code". Would need the memory sized at creation (RAM plus a heap reservation), our own allocator over the reserved heap (no `memory.grow`), a host ABI to place RAM, and the JIT modules importing the memory with its exact limits. Worth a placement-averaged Chromium measurement if the bounds-check tax becomes the lever left (it's up to 27% of the integer guest on Linux arm64, none on macOS/x86_64).
- **MSR (M6 loop 7 did DAIFSet, DAIF, SP_EL0, SPSR/ELR and the TPIDRs inline, without ending the block):** left as helpers that end a block: DAIFClr and the regime, FP-control, SPSel and NZCV writes; an MSR DAIF that unmasks IRQs is a helper call mid-block (Alpine still makes 0.66M MSR (register) and 0.15M MSR (immediate) helper calls). The differential test can't see an unmasking write done inline (no IRQs in its harness): only a distro boot's steps catch it (Alpine did).
- **Left by M6 (2026-09-27):**
  - Helpers still on Alpine's paths (2.5M helper-retired steps a boot): unmasking MSRs (DAIFClr, MSR DAIF that unmasks), ISB, CASP, exclusive pairs, LSE min/max, LD2–LD4/ST2–ST4, the STR fallbacks (TLB misses, MMIO). None is worth a loop by itself now.
  - Loop 3 (vector registers in locals) wasn't done: no profile asked for it (CoreMark and the boots use little NEON; the FP guest is at 7.9× M5).
  - CoreMark's gap to TCG (69%): the store bounds checks V8 keeps on Linux arm64, register write-backs at block exits, call/return between small regions (§2 "V8 and our code"). Only for real programs, not to fit CoreMark (the user, 2026-09-27).
  - **Guest images on the M4 VM:** the images container is x86_64 (Buildroot's Bootlin toolchains) and runs under qemu-user here, where `unshare` fails, so `images/build.sh alpine` can't rebuild Alpine on this host (its committed image came from the x86_64 desktop; `alpine-user` builds in Alpine's own arm64 container instead). Move alpine to that container too if it ever needs rebuilding here (its bytes would change: a new step constant).
  - `coremark_vm_jit`: CoreMark sizes its run from calibration, which a cold JIT slows, so a run can come out under CoreMark's 10 s rule (valid results, flagged). Passing a fixed iteration count through init's arguments would make it exact.
  - The PC-sampling profiler (`bench/boot/profile.ts`) samples once per chunk, now up to 32K steps.
- **`core/fuzz` hygiene:** `Mismatch::key` is dead code in the libFuzzer target build (a warning, not in CI).

## 8. Risks to watch

- **Wasm module compile/instantiate latency** dominating JIT benefit. The M0 spike quantifies this; batching and tiering thresholds mitigate it.
- **FP exactness** (FMA, NaN payloads, rounding modes) costing more than expected. It's contained to the slow paths, and TestFloat catches regressions.
- **Broadcast TLBI/IC + `DSB` synchronization** across workers under SMP. This is a known ARM cost that shapes the M7 design.
- **Rust + wasm threads** needs nightly with `-Z build-std`, with atomics enabled via `-Zllvm-target-feature=+atomics` (`-Ctarget-feature=+atomics` is being phased out, rust-lang/rust#162235). The toolchain is pinned in `rust-toolchain.toml`.
- **Guest RAM ceiling / memory layout.** Settled in M0.5: layout A, so guest RAM ≤ ~3.5 GiB. The measured gaps to B/C/D are recorded in `bench/spike/memory/REPORT.md`; re-measure them on new Chromium releases. Past 3.5 GiB the path is spill memories as NUMA nodes (the M0.5 NUMA follow-up). Chromium gives no catchable error when host RAM runs out: the renderer is OOM-killed, so guest RAM must be sized against host RAM up front.
- **Cross-origin isolation** (COOP/COEP) is required for `SharedArrayBuffer`. It constrains embedding and third-party resources.
