# Core review, 2026-11-03

A review of the emulator's core (`core/src`, ~48k lines) for correctness defects and performance opportunities, in
eight areas, each read statically and verified wherever the cloud session allowed. The areas: the reference
interpreter and CPU state; the block interpreter, the FP core and crypto; the JIT's integer emitter; its FP and SIMD
emitters; the JIT's runtime (dispatch, caches, invalidation); the MMU, memory, snapshots and lz; the platform (run
loop, parallel SMP, GICv3, timers, the exported ABI, the small devices); virtio and the xHCI.

Finding 1 of the review (an ISB completed in place under the parallel JIT running stale code after another vCPU's
IC) is fixed in the same commit as this file, with `tests/baremetal/isb.c` (docs/jit.md "Fast completions",
docs/platform.md). This file holds the rest.

**Status.** Fixed since, each with a test that failed first: 3, 4, 6, 7, 8, 9, 10, 11, 12, most of 14, and the doc
mismatches (marked below). Open: 2, 5, 13, the rest of 14, and every performance item.

**Verification labels.** *Confirmed (test)*: a test shows the defect (where it lives is said). *Confirmed (oracle)*:
qemu-aarch64 or the Arm pseudocode against our output. *Plausible*: argued from the code, not shown by a run, with
the reason it couldn't be. Performance items carry no numbers from Chromium: the cloud session's x86_64 runner is
not a place to record any (docs/cloud.md). None of the findings below was in docs/backlog.md.

**The verification files** were left in the session's scratchpad, which doesn't outlive the session; each finding
says what the test does, so it can be written again (most are a page of Rust against the `pub` modules).

## Correctness

### 2. An indirect chain longer than the queue size puts the whole virtio device in NEEDS_RESET (medium)

- **Where:** `core/src/virtio.rs:305-308` (`walk_chain`: `count += 1; if count > size { return Err(Bad) }`), with
  the page's GPU queue of 16 (`web/app/worker.ts:245`, `queueSize`).
- **What happens:** the spec (§2.7.5.3.1) says a driver must not make a chain longer than the queue size, but Linux's
  `virtqueue_add_split` doesn't enforce it for indirect descriptors: it allocates `total_sg` entries for the table
  and needs only one free ring slot. virtio-gpu uses indirect descriptors (`elemcnt = 1`), and a vmalloc'd buffer is
  posted one segment per page: SUBMIT_3D's command stream comes from `vmemdup_user` (kvmalloc; virgl's command
  buffer is up to 256 KiB), RESOURCE_ATTACH_BACKING's entry array from kvmalloc (a 4K framebuffer over fragmented
  pages is ~130 KiB of entries). When kvmalloc falls back to vmalloc (fragmented guest memory), any such command of
  more than 14 pages is a chain over 16, the transport sets NEEDS_RESET and the screen freezes for good. QEMU accepts
  indirect tables of up to 1024 entries whatever the queue size (and its GPU queue is 256), so Linux never meets the
  limit there.
- **Fix:** bound an indirect table separately (1024 segments, as QEMU: a record of 2 + 3·1024 words still fits the
  4096-word request ring), or a larger GPU queue (which doesn't help the other devices).
- **Verification:** confirmed (test) for the core: on a 64-entry queue an indirect table of 64 entries is taken and
  65 sets NEEDS_RESET; on a 16-entry queue 17 does (driving `Virtio` as `core/src/virtio/tests.rs` does). Plausible
  for Linux reaching it: it depends on fragmentation, not reproduced in a guest.

### 3. Parallel SMP: CPU_ON leaves a stale timer interrupt line high (low-medium)

**Fixed** in 0e8130d: at CPU_ON `Own::ppi` takes the GIC's timer levels under the lock; `vm::tests::a_cpu_on_lowers_the_timer_lines_left_high_at_cpu_off`.

- **Where:** `core/src/vm/parallel.rs:~358` (`*own = Own { steps, ..Own::default() }` at CPU_ON) with
  `drive_timers` (`parallel.rs:~535-542`).
- **What happens:** `drive_timers` writes a vCPU's timer lines into the GIC only when they differ from `Own::ppi`
  (what it last drove). CPU_ON resets `Own::ppi` to (false, false) and the CPU (its timer disabled) but leaves the
  GIC's PPI 27/30 levels as they were. If the timer line was high at CPU_OFF, it stays high after the restart: the
  vCPU's next check sees low, equal to its record, and drives nothing. The restarted CPU takes a level timer
  interrupt whose CNTV_CTL.ISTATUS reads 0 (Linux's handler returns IRQ_NONE), and after EOI it's pending again: an
  interrupt storm until the timer really fires. Round-robin is unaffected (`lines_at` drives every vCPU's lines every
  iteration).
- **Reachability:** Linux's normal hotplug stops the timer before CPU_OFF. Its crash-stop path
  (`ipi_cpu_crash_stop` → CPU_OFF with the timer running) followed by a kdump kernel on more than one CPU reaches it,
  as would a guest that doesn't stop its timer.
- **Fix:** drive the lines low at CPU_ON, or take `own.ppi` from `gic.level()` as `set_sched_par` does.
- **Verification:** confirmed (test): an integration test powers a vCPU off with its timer's line high, powers it on,
  and finds the PPI still asserted in the GIC (parallel fails, the same sequence in round-robin passes).

### 4. Round-robin: a snapshot between `vm_wake` and the next `vm_run` loses the wake (low-medium)

**Fixed** in 0e8130d: round-robin saves `Platform::start`; `vm::tests::a_round_robin_snapshot_between_wake_and_run_keeps_the_wake`.

- **Where:** `core/src/vm/state.rs:168-174` (round-robin saves `start = None` and never reads `Platform::start`),
  with `wake_suspended` (`core/src/vm.rs:973-985`), which has moved the resume request out of `suspended` into
  `start[c]` already.
- **What happens:** the restored machine has every vCPU off, isn't suspended and has no pending start: it idles
  forever and nothing can wake it.
- **Scope:** round-robin realtime hosts only (Node, the tests); the page runs parallel SMP, whose `sched_par` saves
  `start`.
- **Verification:** confirmed (test): SYSTEM_SUSPEND, `vm_wake`, snapshot, restore, run: exit IDLE, not suspended,
  the vCPU off.

### 5. A JIT flush can run inside `jit_hot` with compiled code on the stack (low likelihood, a crash when it hits)

- **Where:** `core/src/jit/mod.rs:1173` (and `:1183` on the batch-1 path) check `live_bytes < budget()`; then
  `emit_batch → install → alloc` checks `live_bytes >= budget()` again (`:765`) and flushes. `budget()` (`:634`)
  reads `G_LIMIT` without the lock; the machine worker writes it (`web/app/worker.ts:546`,
  `setJitLimit(jitLiveBytes)`, making the budget equal to the live bytes).
- **Interleaving:** a vCPU passes the check in `Cache::tier_up`; the host stores the new limit; `alloc` flushes
  (`drop_all`, the epoch moves on); `Jit::tier_up` then `table.sync`s (new epoch) and installs, and the host's
  install sees slots starting over and nulls the old ones; `jit_hot` returns into the old head, whose transfer-cache
  entries aren't bumped (`xgen`) until the dispatcher, so an indirect transfer `return_call_indirect`s into a null
  slot (a wasm trap: the machine dies) or into a new epoch's function (wrong guest code). The code's own comments
  say "never a flush here".
- **Window:** `plan()` plus the emission, at most once a session (when the host lowers the limit).
- **Fix:** read the budget once and pass it to `alloc`, or have `alloc` refuse rather than flush when called from
  `jit_hot`.
- **Verification:** plausible (a race between the host and a vCPU; not reproduced).

### 6. Deterministic time: a jump to a far timer deadline overflows the counter (low)

**Fixed** in 0e8130d: in deterministic mode a deadline at or past `TIME_MAX` counts as none; `vm::tests::a_deadline_past_the_counters_range_is_no_deadline`.

- **Where:** `core/src/vm.rs:1207` (`skipped += t - now`) and `:1026` (`steps * ticks_per_insn + skipped`).
- **What happens:** when every vCPU waits in WFI, virtual time jumps to the next deadline, which can be anywhere up to
  u64::MAX: a guest writes CVAL near u64::MAX, or a negative TVAL in the counter's first 2^31 ticks (CVAL wraps to
  near 2^64). A few steps after the wake the counter's sum overflows: natively (debug) a panic, "attempt to add with
  overflow"; the release wasm wraps, CNTVCT goes back to ~0 and the timer can fire again at the next idle. And
  `snapshot_restore` refuses a counter ≥ 2^62 as Corrupt, so such a VM saves but can't be restored.
- **Fix:** cap the jump, or ignore deadlines past `TIME_MAX`.
- **Verification:** confirmed (test): deterministic mode, CVAL = u64::MAX - 10, WFI with interrupts masked, a few
  steps: the panic at vm.rs:1026.

### 7. Cache maintenance by VA caches a Device page as Normal: misaligned accesses to it stop faulting (low)

**Fixed** in 96020f4: the read and write arrays take the Device tag whatever filled them; `mmu::tests::cache_maintenance_first_keeps_a_device_page_device`.

- **Where:** `core/src/mmu.rs:861-862` (`device_check = u != Use::Exec && access != Access::Maint`) with `:935-942`
  (`t.fill(array, va, page, w.ng, w.level, device)`, `device` being `w.device() && device_check`).
- **What happens:** `DC CVAC`/`CIVAC`/`CVAU` or `IC IVAU` (read array) or `DC IVAC` (write array) on a page mapped
  with a Device MAIR attribute, before any data access to it, fills the TLB entry **without** its DEVICE tag bit. From
  then on `LDR w0, [va+2]` or a misaligned `STRH` matches the entry and takes the fast path (the interpreter's
  `fast`, `host_in`, the JIT's inline probe: the same tag) and succeeds instead of an Alignment fault (DFSC 0x21).
  A data access that fills the entry first is right (`device_memory_faults_misaligned_accesses` covers that); the
  bug depends on the order.
- **Fix:** fill with `w.device()` alone; keep `device_check` for the immediate alignment test only.
- **Verification:** confirmed (test): after a maintenance op on a Device page a misaligned read returns `Ok(0)` and a
  misaligned write `Ok(())`; the same accesses on an unmaintained Device page fault.
- **Backlog:** next to "DC ZVA to RAM mapped as Device with the MMU on zeroes it" (a different path).

### 8. MDSCR_EL1.TDCC is ignored: EL0 reaches the DCC registers (low)

**Fixed** in 96020f4: EL0 MRS/MSR of the DCC registers trap with TDCC (MSR MDCCSR stays UNDEFINED); `interp::tests::tdcc_traps_el0_dcc`.

- **Where:** `core/src/interp/sys.rs:177-195` (`raz_wi` takes DBGDTR and DBGDTRRXTX), `:439` (`MDCCSR => 0`), `:526`
  (writes ignored), past the EL0 gate at `:274`.
- **What happens:** Linux's `__cpu_setup` sets `MDSCR_EL1.TDCC` (bit 12); then EL0 accesses to MDCCSR_EL0,
  DBGDTR_EL0 and DBGDTRRX/TX_EL0 must trap to EL1 (EC 0x18), which Linux turns into SIGILL. Here they read zero and
  ignore writes: at EL0 with TDCC set, `mrs x0, mdccsr_el0` (0xd5330100), `mrs x0, dbgdtr_el0` (0xd5330400) and
  `msr dbgdtrtx_el0, x0` (0xd5130500) retire. Guest-visible (a program can tell it isn't on hardware), otherwise
  harmless.
- **Fix:** those four at EL0 return `trap_sys(i)` when `c.mdscr_el1 & 1 << 12 != 0`.
- **Verification:** confirmed (test): no exception taken, the PC moves past the MRS.
- docs/cpu.md says a boot writes `TDCC` but not that it's ignored.

### 9. A software step of CASPA/CASPAL reports ESR.EX = 1 (low)

**Fixed** in 96020f4: `load_exclusive` matches the Load-Exclusives only; `interp::tests::stepped_load_exclusives_set_ex`.

- **Where:** `core/src/interp/debug.rs:197-199` (`load_exclusive`: `i & 0x3fc0_0000 == 0x0840_0000`).
- **What happens:** the mask fixes bits 29:22 (L = 1, o2 = 0) and leaves bits 31 and 21 free; CASP with L = 1 (bit
  31 = 0, bit 21 = 1) matches. Stepping `caspa x0, x1, x2, x3, [x4]` (0x48607c82) at EL0 with MDSCR.SS and PSTATE.SS
  gives ESR_EL1 = 0xca000061 (EC 0x32, EX = 1) where EX must be 0. A debugger using EX to detect exclusive
  sequences mishandles it.
- **Fix:** LDXR/LDXP exactly: `(i & 0x3f80_0000) == 0x0800_0000 && bit(i, 22) && (bit(i, 31) || !bit(i, 21))`.
- **Verification:** confirmed (test); LDXR (EX = 1) and CASP (EX = 0) are right.

### 10. virtio: a queue stalls after a reset with unread stale records ahead of a large chain (low)

**Fixed** in dd10b4c: the backend sets `SIGNAL_DEVICE` after a poll that skipped records from before a reset (`web/devices.ts` `poll()`, and the native twin in `core/tests/common/mod.rs`); `tests/devices.test.ts` "poll: records from before a reset are skipped, and the signal word set", `virtio::tests::a_backlog_behind_records_from_before_a_reset_waits_for_the_backends_signal`.

- **Where:** `core/src/virtio.rs:628-631` (the backlog), `:708-711` (retried only in `complete`), `:546-556` (a reset
  leaves `sh.req` as it is).
- **Sequence:** the driver resets while the request ring holds unread records; the new driver's first chain doesn't
  fit, so `backlog` is set and the early return skips writing `avail_event`; the backend reads the stale records and
  skips them, posts no completion, so `SIGNAL_DEVICE` never comes and `complete()` never retries; under EVENT_IDX
  `vring_need_event(avail_event = 0, …)` is false, so the driver never notifies that queue again.
- **Reach:** the ring fills only with big indirect chains (blk: ~10 chains of 126 segments), and the reset must land
  in realtime mode before the backend read them.
- **Fix:** `set_status(0)` retries the backlog, or the backend signals after skipping stale records, or a backlog
  writes `avail_event`.
- **Verification:** confirmed (test) for the core's side; plausible for the timing in a browser.

### 11. virtio: a reset leaves the negotiated features in `DevShared.features` (low)

**Fixed** in dd10b4c: `set_status(0)` clears `sh.features`; `virtio::tests::a_reset_clears_the_negotiated_features`.

- **Where:** `core/src/virtio.rs:546-556`.
- **What happens:** `ctx.features()` is documented as 0 before FEATURES_OK but keeps the old driver's bits until the
  next negotiation; the net backend's `flap()` (`web/devices.ts:491`) takes non-zero as "under a driver".
- **Verification:** confirmed (test).

### 12. xHCI: a snapshot loses a walk waiting for room (`Ep::more`, `Xhci::more` not saved) (low)

**Fixed** in dd10b4c: `Ep::more` saved, `Xhci::more` restored from it (snapshot state version 4, older states refused); `xhci::tests::a_snapshot_keeps_a_walk_waiting_for_room`.

- **Where:** `core/src/xhci.rs:1922-1977` (save), `quiet()`/`saveable()`.
- **What happens:** with no TD in flight but ≥ 256 events pending (the guest's handler hasn't run), the walk waits on
  `more`; `quiet()` and `saveable()` are true, so a snapshot can be taken; after the restore `more` is false and
  nothing walks the rest of the ring until the guest rings that doorbell again.
- **Verification:** confirmed (test): 400 transfer events unbroken, 318 after a restore at that point. Rare: events
  must pile up past `WALK_TDS`.

### 13. xHCI: 1024 TDs held by backends make every idle parallel vCPU spin (low-medium; performance and liveness)

- **Where:** `core/src/xhci.rs:1384-1388` (the walk sets `more`), `:1695` (`due()` returns 0 while `more`),
  `core/src/vm/parallel.rs:~413`, `web/vcpu-worker.ts:115`.
- **What happens:** once `tags.len() >= MAX_TDS` the walk stops with `more = true` and `due()` is 0 until a TD
  completes (bulk or interrupt IN TDs waiting for data on WebUSB devices). In parallel mode each vCPU in WFI exits
  IDLE with `min(deadline, due - ns) = 0`, the worker's `Atomics.wait(…, 0)` returns at once and the vCPU loops:
  every idle vCPU burns a host core while the device stays quiet. `tick` needn't run again until a completion, which
  calls `complete()` anyway; only the `WALK_TDS` and event-room cases need the next boundary.
- **Verification:** confirmed (test) that `due()` stays 0 across 1000 ticks with 1024 TDs held; the spin follows from
  parallel.rs and vcpu-worker.ts (not run). docs/usb.md describes the bound, not its idle cost.

### 14. Smaller items (plausible, not tested unless said)

**Fixed** (0e8130d, dd10b4c): `vm_run_cpu`'s bound (an out-of-range vCPU returns `exit::STOP`), `boot()`'s checked arithmetic, `vm_clock_skip`'s doc, the `TIMER_STEPS` comments, `shm_sel` in the snapshot. Open: AFFINITY_INFO's counters, the idle exit's nanoseconds, CRCR while a command is held.

- **`vm_run_cpu`** (`core/src/lib.rs`) doesn't bound `cpu`: an out-of-range index panics where `vm_cpu`,
  `vm_exit_cpu` and `vm_counters` return null.
- **`boot()`** computes `kernel_pa - text_offset`, `kernel_pa + 0x38` and `pa + len` with arithmetic that panics on
  overflow in debug builds (the inputs are the host's or the Image header's; release wraps).
- **AFFINITY_INFO** calls `power_par(t)` through `plat_of(t)`, bumping vCPU t's lock counters from another thread
  with `add`'s load-then-store: counts can be lost (atomics, so not UB).
- **The idle exit's nanoseconds** (`((t - now) * 1e9 / frq) as u64`) truncate for deadlines ~2^60 ticks away: the host
  wakes early, harmlessly.
- **`vm_clock_skip`** is documented "from any thread"; in round-robin it takes the lock while another thread may hold
  `&mut Vm` in `vm_run`, formally an aliasing violation. The doc should say "round-robin: between runs", as
  `vm_wake`'s does.
- **The `TIMER_STEPS` comment** says a timer is seen at most 4096 steps late; the check runs between chunks of up to
  `CHUNK` (32768) steps.
- **`shm_sel` (virtio) isn't in the snapshot:** only a snapshot between the SHMSel write and the SHMLen read notices.
- **xHCI CRCR CA/CS while a command is `held`** (fence mode): the Ring Stopped event goes out and the held
  completion arrives after it. Needs a backend stalled ≥ 5 s.

## Performance

None measured in Chromium; each needs `bench/run.ts` A/B on the dev VM before anyone claims a number.

### P1. The nG list (1024) overflows long before the 16,384-entry TLB fills: whole-TLB flushes at ASID switches

- **Where:** `core/src/mmu.rs:59` (`NG_SLOTS = 1024`) and `flush_ng` (`:219-224`).
- **What happens:** `ng_len` counts every nG fill, refills of a slot included, not distinct live entries. Once a
  process has made more than 1024 nG fills since the last ASID switch, the next switch (or `TLBI ASIDE1`) calls
  `flush_all`: a 2 MiB memset of entries, 128 KiB of `blk`, both transfer-cache generations bumped, and every global
  kernel entry dropped. The TLB went from 4,096 to 16,384 entries today (8b422b0, "The TLB is 16,384 entries…") with
  `NG_SLOTS` unchanged since 2026-11-01, so a process now keeps far more than 1024 nG entries alive, and most switches
  away from a non-trivial process probably take the full flush, undoing the "keep global entries" gain (docs/cpu.md:
  misses 3.61M → 1.07M).
- **Cheaper alternative:** an nG bit per slot in the existing `blk: [u8; …]` array (a spare bit); on overflow scan
  that 128 KiB and drop only the nG slots, keeping the globals and skipping the 2 MiB memset. Or size `NG_SLOTS` with
  the TLB.
- **To check first:** count `flush_all` calls from `flush_ng` (`Tlb::stats`) in Alpine's userspace run, before and
  after.

### P2. Vector FCVTL/FCVTN (single↔double) send zero lanes to the helper; docs/jit.md says they don't

- **Where:** `core/src/jit/emit/float.rs:2480-2510` (the `FCVTL | FCVTN if d && !bit(i, 29)` arm).
- **What happens:** FCVTL tests `lanes_in(ta, false, 1)` (normal lanes only) through `all_lanes`, which ANDs in FPOK,
  so `fcvtl v0.2d, v1.2s` calls the helper when a lane is ±0 or ±∞, and when FPSR.IXC is clear, though widening is
  exact and raises nothing. FCVTN tests its source with `lanes_in(rn, true, 1)`: a zero double lane goes to the
  helper too. The scalar `FCVT` accepts all of these. docs/jit.md ("FCVT single↔double, scalar and vector
  (FCVTL/FCVTN): widening is exact without FPOK for a zero, normal or infinite operand; narrowing takes … a normal
  or zero operand") is true of the scalar form only; the code's comment ("normal operands") is accurate.
- **Effect:** array conversions with zeros (audio, numeric code, padding) pay a helper call an instruction.
- **Fix:** the scalar rule lane by lane (no NaN, FZ's denormal test, no FPOK for widening; `zero_lanes` ORed in for
  narrowing).
- **Verification:** confirmed (test), counting helper calls through a one-word JIT/interpreter harness: FCVTL with a
  zero lane 1, an infinite lane 1, IXC clear 1, normal lanes with IXC set 0; FCVTN with a zero lane 1, normal 0;
  scalar `fcvt d0, s1` with zero 0, IXC clear 0. The results always matched the interpreter.

### P3. Structure loads and stores in the interpreters: 12-25× slower per byte than LDP Q

- **Where:** `core/src/interp/ldst_fp.rs` `multiple` (`:170-212`) and `single_structure`.
- **What happens:** each element is its own bus access with a u128 shift and OR: 64 one-byte accesses for
  `ld1 {v0.16b-v3.16b}`. Measured natively (release, flat bus): `ld1 {v0-v3}.16b` 445 ns, `ld4 .16b` 380 ns,
  `ldp q0, q1` 17.8 ns. The JIT compiles these inline (`jit/emit.rs:1150`); the block interpreter has no handler
  (`exec_at_op`) and the debug interpreter (an armed watchpoint) takes this path: only cold or interpreted code pays.
- **Possible fix:** 8 bytes at a time when `selem == 1` (memory order is the register's byte order); de-interleave
  the rest after the read.

### P4. Double FMUL/FDIV/FSQRT compute Inexact exactly even when IXC is already set

- **Where:** `core/src/fp.rs:1218-1229` (`exact_product_f64`), `:1233-1318` (`fast2`, `fast_sqrt`).
- **What happens:** the interpreter's fast path finds Inexact with a u128 multiply and a variable u128 shift
  (`__multi3`, `__lshrti3` in wasm). Every `Fpu` is made by `Fpu::with_fpsr`, seeded with FPSR.IXC
  (`interp/float.rs:44`, every `simd_fp.rs` handler): IXC is cumulative, so the check could be skipped whenever
  `self.flags & IXC != 0`, which is nearly always once a program has done one inexact operation. Interpreter tiers
  only (FP code in cold blocks, `jit` 0/4, the FP guest).

### P5. Smaller JIT items

- **ADRP** (`jit/emit.rs:725-729`): `(ENTRY + base + here) & !0xfff + imm << 12` is an `i64.and` with a `-4096`
  constant and a second add; the page offset of the block's VA is fixed at compile time (aliases of a PA keep it in a
  4 KiB page), so it's `ENTRY + K`, which TurboFan could fold with the following `add :lo12:`. ~5 wasm bytes and two
  ops an ADRP; check that it holds for region members in other pages before relying on it.
- **BR/BLR/RET reload the PC they just stored** (`jit/emit.rs:1017-1023` with `indirect` at `:1261`): teeing Xn into
  ADDR at the branch would skip the `i64.load PC` the transfer-cache probe waits on (assumes V8 doesn't forward the
  store; not checked with `--print-wasm-code`). 10-40 transfers a thousand instructions; the backlog's evidence
  says the stalls there are mostly cold code, so likely small.
- **Vector FMIN/FMAX test both operands for NaN** (`jit/emit/float.rs:1740`, `minmax`): wasm's `fmin`/`fmax` return a
  NaN whenever either operand is one (V8 on x86 and arm64), so without FZ one `r == r` on the result does: one compare
  and one AND fewer for FMAX/FMIN/FMAXNM/FMINNM and their pairwise forms (llvmpipe's clamps). Under FZ the
  denormal tests stay, but the two FZOK branches could be one.
- **The emulated double FMA re-shuffles a by-element factor ~7 times** (`float.rs:2052-2170`, `factor(c)`): one local
  would save ~12 lane ops an `FMLA Vd.2D, Vn.2D, Vm.D[i]`, on hosts without fused `madd` only.
- **`Cache::invalidate`** (`jit/mod.rs:845-852`) runs `pending.retain` and a loop over every table for each dropped
  key, under the lock: O(keys × 512) an IC on a page with code. **`PageIndex::file`** re-files a linker a cross-page
  IC removed (its page list still holds it): duplicates pile up until a prune or flush. Neither worth a loop yet.

### P6. TLBI by VA scans the whole TLB while a 1 GiB block of that half is live

- **Where:** `flush_va` (`core/src/mmu.rs:350-367`): with any 1 GiB-block entry of the VA's half live, a TLBI scans
  16,384 indices × 8 slots (131K checks); with 2 MiB blocks, 4K checks (near-permanent in the high half, where the
  kernel's 2 MiB mappings live). The backlog's "a TLBI by VA a 16 KiB scan" covers the transfer-cache part only.

### P7. The round-robin loop reads the clock twice an iteration

`xhci_tick` calls `self.ns()` before checking there's an xHCI, then `lines()` calls `now()`: in realtime a host
`now_ms` call an iteration. Round-robin isn't the page's path.

## An oracle caveat

QEMU 8.2's FJCVTZS with FPCR.FZ = 1 and a positive denormal input sets Z (`1e7e0061`, d3 = 0x000000047971f7f2, FPCR =
0x1c00000: QEMU Z = 1, webpc Z = 0). The Arm pseudocode (`FPToFixedJS`: Z only for an exact conversion of a value
whose fraction is all zero) and the M4's corpus (`jscvt.fjcvtzs.0373`) agree with webpc: mind it when qemu is the FP
oracle.
