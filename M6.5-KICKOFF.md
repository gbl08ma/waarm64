Start milestone **M6.5** of webpc: the crypto extensions. The M4 and every real arm64 server run
AES, PMULL, SHA1 and SHA256 in hardware. The guest sees none of them yet: the decoder knows the
encodings, the interpreter treats them as UNDEFINED, and `ID_AA64ISAR0_EL1` advertises only LSE
atomics and CRC32 (`core/src/interp/sys.rs`). M6.5 implements them in both tiers, fast enough to be
worth advertising. Read PLAN.md §1 (guest ISA), §2 "JIT ABI", "FP semantics" (the exactness rules
carry over) and "V8 and our code", §7 M6 ("Progress") and M6.5; `bench/interp/REPORT.md` "M6 loop 4"
(integer NEON → SIMD128: `TBL` as `i8x16.swizzle`, the NEON-only crypto paths the guest uses today).
CLAUDE.md's conventions apply; `scripts/ci.sh` must pass at every commit. Same way of working as
M5 and M6: short loops (one slice, one commit, a short report each), and continue unless something
needs my decision.

## Why not the Web Crypto API
Settled, so don't reopen it. The instructions are single rounds and bare multiplies: `AESE` is one
round (AddRoundKey, SubBytes, ShiftRows) without a key schedule, `SHA256H` is four rounds of the
compression function from the state in the registers, and `PMULL` is a carry-less multiply.
`crypto.subtle` only does whole operations with its own key schedule and padding, it has no ECB or
round primitive, and it's asynchronous, while the vCPU runs synchronously inside one wasm call.
The helpers are core wasm, called from JIT code as wasm imports, so they never cross into JS. A
paravirtual crypto device is out too: userspace would need AF_ALG, which Linux 7.2 deprecated after
Copy Fail (CVE-2026-31431).

## Decisions already taken
- **Advertise only if faster.** With the ID register fields set, OpenSSL and the kernel leave their
  NEON-only paths (`vpaes` on `TBL`, GHASH on the 8-bit `PMULL`, the scalar and NEON SHA-256), which
  run inline since M6 loop 4. If our instructions don't beat those under the JIT, they stay
  implemented, tested and unadvertised, and the report says by how much they fall short.
- **Constant time in every tier.** No secret-dependent memory indices or branches: no T-tables,
  no table-driven S-box in the interpreter, no early exits on data. I expect little
  security-critical work in this guest, so treat this as cheap insurance, not the milestone's
  driver. If it costs a lot somewhere, show me the number instead of dropping it.
- **Our own code**, from FIPS 197, FIPS 180-4 and the Arm pseudocode (the Sail model is a readable
  reference). Nothing ported from OpenSSL, the kernel or QEMU. Techniques from papers are fine:
  Hamburg's vector-permute AES and BearSSL's `bmul` are ideas, not code; credit them in
  `THIRD_PARTY.md` all the same.

## Goal (PLAN.md §7 M6.5)
AES, PMULL (8- and 64-bit) and SHA1/SHA256 correct in the interpreter and the JIT, with the
tiers' steps identical; `openssl speed` measured with the extensions on and off; advertised only if
on beats off.

## Loops (order is a suggestion; the numbers decide)
0. **The bar.** `openssl speed -elapsed` for `aes-128-gcm`, `aes-256-gcm`, `aes-128-cbc`, `sha1`,
   `sha256` in the guest under the JIT, on today's NEON-only paths. OpenSSL isn't in any image yet:
   add it to M6's userspace image (`images/build.sh alpine-user`: `USERLAND_PKGS`, pinned, and
   `images/alpine/user/`; built in Alpine's own arm64 container), as a phase chosen on the kernel
   command line (e.g. `webpc.phase=crypto`), **not** in `alpine_user_jit`'s default run, which
   has a ~30 s budget and a step constant in CI (`ALPINE_USER_STEPS`, which moves once when the
   image gains the package). Run it in **realtime** mode, as `--only coremark_vm_jit` does:
   `openssl speed` times itself with the guest clock, which deterministic mode derives from
   steps. Keep each algorithm short (`-seconds 1`, one or two block sizes). **The Alpine boot
   benchmark itself doesn't change.** Record the helper histogram of the run, too (how much of the
   NEON path is still helpers: 8-bit `PMULL` is a candidate).
1. **Reference semantics:** `core/src/crypto.rs` (AES SubBytes/ShiftRows/MixColumns and their
   inverses, the SHA1 choose/parity/majority rounds, SHA256's Σ/σ, carry-less multiply) and the
   interpreter handlers, the 64-bit `PMULL` included. Unit tests with known-answer vectors (FIPS
   197 appendix C, FIPS 180-4's examples, NIST CAVP samples, GCM's GHASH vectors) driven through
   the instructions, i.e. a whole AES-128 block from `AESE`/`AESMC` with a key schedule in the
   test. Corpus groups for each instruction generated on the M4 (`tools/corpus/run.ts`, the
   generator learns the encodings), the decoder sweep's expected differences updated
   (`core/fuzz/src/check.rs`: the v8.0 crypto instructions leave `NOT_OURS_PREFIX` and the
   `pmull64` exception), QEMU as the second oracle.
2. **Switchable advertising:** a `VmConfig` field that sets the ISAR0 fields (AES = 2, SHA1 = 1,
   SHA2 = 1), off by default. It's a host ABI change, so the ABI version bumps; design note in
   PLAN §2 first. It gives the test kernel below its CE drivers, and the benchmarks on/off at the
   system level (`OPENSSL_armcap` only covers userspace).
3. **JIT through the helper:** corpus through the JIT (forced and stress), `tests/jit-diff.test.ts`
   classes for the new instructions, lockstep. Now the kernel test: a test kernel (the Buildroot
   fragment plus the arm64 CE crypto drivers and the crypto self-tests, the full variant; check
   the Kconfig names against 6.18, since self-tests and `lib/crypto`'s KUnit suites were
   reorganized recently) that boots with advertising on, under the interpreter and the JIT, and
   passes every self-test and KUnit case.
4. **Fused AES rounds inline:** `AESE`+`AESMC` and `AESD`+`AESIMC` on the same register become one
   emitted round (the pair ends nothing: an `AESE` alone, or one whose `AESMC` targets another
   register, is two instructions). Two SubBytes candidates, both with `i8x16.swizzle` only
   (never `relaxed_swizzle`, whose out-of-range lanes aren't deterministic): the S-box as 16
   swizzles of 16-byte slices, and Hamburg's GF(2⁴) nibble inversion. Measure both; keep the
   faster one. Check the machine code (`tools/v8code.ts`): one `TBL` per swizzle on arm64.
5. **`PMULL.1Q` and GHASH:** the 64×64→128 carry-less multiply as integer multiplies with holes
   (four 32×32 products per 64-bit half or Karatsuba, whichever measures faster), inline in the
   JIT if the helper call dominates GCM. Look at what Chromium ships of wasm's wide-arithmetic
   proposal (`i64.mul_wide_u`), but don't depend on it. `PMULL`/`PMULL2` 8-bit inline if loop 0's
   histogram shows it.
6. **SHA1 and SHA256** inline only if the histogram asks: four rounds per instruction make the
   helper call cheap relative to its work.
7. **The decision and the table:** `openssl speed` on/off (medians and IQR, Chromium, this host).
   No QEMU or native rows: peer comparisons ended with M6's exit table (PLAN §5 "Comparison
   targets"); M6.5 compares webpc with itself. If on beats off for AES-GCM and SHA-256, advertise
   by default; then re-baseline the boots in the same session and record their new step counts
   (the kernel picks its CE code, so they change once: `tests/boot-node.test.ts`'s Alpine,
   Alpine userspace, device-test and LTP constants and `tests/browser.test.ts`'s). If off wins
   anywhere, report it and ask me.

## Validation per loop
As in M6: unit tests per emitter shape, the golden corpus through both tiers (forced and stress),
jit-diff classes seeded with the FIPS vectors' states and random ones, lockstep (CI's 20M; 300M at
the end of each loop that touches semantics), the Node boots with exact steps (unchanged until
advertising is on; the multi-hour JIT-stress runs aren't routine since M6, PLAN §4), and **planted bugs** the tests must catch: a MixColumns column swapped, one
S-box entry wrong, a PMULL carry propagated, a SHA256 σ rotation off by one, a fused round taken
when `AESMC`'s register differs. Every bug found gets a regression test.

## Numbers
`bench/run.ts` in Chromium on this host only. Medians and IQR, the committed JSON behind every
written number, differences under ~5% are noise unless repeated. Keep the `oracle` VM idle while
benchmarking.
