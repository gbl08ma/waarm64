# V8 and our code

What V8 (Chromium 153 and Node 26 on Linux arm64, the M4 VM) makes of the core and of the JIT's
modules, and the rules that follow. Read machine code in Node (`tools/v8code.ts`: a guest under
the JIT with `--print-wasm-code`, filtered by function name; or `perf` with `--perf-prof`,
[benchmarking.md](benchmarking.md) "Profiling"); measure in Chromium (its Linux build has no
disassembler). Numbers: `bench/interp/REPORT.md` "M6 loop 0" onwards, `bench/spike/REPORT.md`.

## Costs that shaped the design

- **Module compile + instantiate** ~46 µs for a one-block module, then ~3 µs for its first call
  (V8 compiles lazily with Liftoff): batching pays. Synchronous `new WebAssembly.Module` in a
  worker is fine (M0 spike).
- **Calls:** a wasm → wasm import call ~2.2 ns; a `call_indirect` through the table 3.5 ns
  monomorphic, 13–16 ns cycling over 16 targets on x86_64, **2.5 ns on the M4** (so dispatch
  overhead shows more on x86_64). One dispatch per block costs about as much as interpreting one
  instruction, which is why linking matters.
- **Tiering:** new code runs under Liftoff; V8 tiers a function up to TurboFan after ~13M "bytes
  executed" (`--wasm-tiering-budget`, charged at returns, tail calls and back-edges). Alpine's JIT
  time is two-thirds Liftoff code (a flat tail of ~4000 lukewarm functions): lowering the budget
  to 2M would save ~8% of its boot, but it's not something we can set for users, and padding
  functions to spend the budget faster costs more than it saves. **Fewer, larger modules** is the
  lever we have ([jit.md](jit.md) "Compile policy").
- **Liftoff zero-fills a function's locals at every call** when it has more than 12 besides its parameters (half
  its 24 cache registers on arm64) or any not i32/i64 (f32, f64, v128); with 12 or fewer integer locals it fills
  nothing (they start as constants). The fill writes every local's slot (8 bytes, a v128's 16): straight `stp xzr`
  up to 96 bytes, past that a loop of 4-byte stores, ~0.23 ns a turn (two turns a local) on the M4 VM: a call with 13
  i64 locals costs 8.2 ns against 2.0 with 12 (`bench/boot/results/perf26/tools/fillcost.mjs`). The same code in
  Chromium 155's and 157's V8 (`liftoff-compiler.cc` `SpillLocalsInitially`, `FillStackSlotsWithZero`). Half the
  JIT's functions fill, 42 turns each, and doubling that cost Alpine's boot 2.8% and its userspace 1.7% on the Mac
  (`bench/boot/REPORT.md` "PERF loop 26"): what fewer locals would buy ([backlog.md](backlog.md)). TurboFan doesn't
  fill; unused declared locals cost only Liftoff's fill.
- **The wasm code GC** frees the Liftoff code TurboFan replaced (and wrappers), not dead modules' code, which goes
  with the module. It starts once that dead code passes 64 KB plus a tenth of the process's committed wasm code, every
  isolate reports the code on its stacks, and the last to report frees it under the engine's mutex: so its work
  follows the tier-ups, not the module count. It no longer stops the vCPUs: Firefox's churn screen frees up to
  16,000 objects at once with no vCPU stall of 50 ms (`bench/boot/REPORT.md` "The wasm code GC today, and larger
  batches in a browser"). `--trace-wasm-code-gc` prints each GC (the renderer's stdout, under `DEBUG=pw:browser`).
- **In a large code footprint indirect tail calls cost what direct ones don't** (M8,
  `bench/boot/results/m8-warm/tools/chain.mjs`: 37 against 18–22 ns a transfer at 32,000 functions; a module-local
  table didn't help, 35 ns); imports of another module's functions are as cheap as direct calls. In Firefox 26% of a
  busy vCPU stalled on a guest function's first instruction, 83% of it after a `return_call_indirect`: fetching cold
  code, not mispredicting.
- **A wasm `return` is predicted where a `return_call_indirect` to the guest's return address isn't**: guest calls
  as wasm calls and their `ret`s as wasm returns (at most 64 deep) gave +10% busy MIPS on the Mac host and +11% in
  the dev VM in Firefox ([jit.md](jit.md) "Calls"). October's measurement in the VM, where the stall only moved into
  the callers' bodies, was the VM's code-size distortion plus a flush. **A dedicated worker's stack** leaves ~425 KB
  under our dispatcher (Chromium 155, arm64: ~5,300 frames of an 80-byte JS function); a Liftoff frame of a JIT
  function with 32 v128 locals took ~270 B (`bench/boot/REPORT.md` "The host stack that host calls take").
- **`new WebAssembly.Module(bytes)` validates the whole module even on a cache hit** (~6 µs a KB on the M4): pass
  compiled `Module` objects between workers (postMessage shares the code) rather than bytes for a second compile
  ([jit.md](jit.md) "Sharing").
- **TurboFan-only and default tiering agree on steady-state JIT code**; default tiering starts
  ~10% slower for its first ~20 ms. Old "TurboFan-only is slower" observations didn't reproduce on
  a quiet host.

## Bounds checks

- **Linux arm64 has no wasm trap handler:** V8 reserves guard regions but bounds-checks every
  access explicitly (load the size, compare, branch), in Chromium and Node, as on Android. Chrome
  on macOS and on x86_64 uses guard pages. The checks are up to **27%** of the integer guest here
  (`--no-wasm-bounds-checks`, a diagnostic only). Numbers from this host include a cost that
  macOS and x86_64 users don't pay: **47% of the userspace benchmark** (the Mac host's Chromium
  runs it in 14.6 s, and in 21.5 s with `--wasm-enforce-bounds-checks`, as this VM does:
  `bench/boot/REPORT.md` "the same builds on the Mac host"; `bench/run-mac.sh` measures there).
- V8 checks a group of accesses to one base once, but after a call or across branches checks each
  access again, and has no range analysis for masked indexes (`i32.and`). In this V8 build, loads
  through the vCPU base go unchecked and stores are checked.
- A constant address below the memory import's declared minimum needs no check (below 32 KiB it's
  one `str x, [membase, #imm]`). **The `Cpu` at a constant address was tried twice**
  (placement-averaged): integer +6.5–7%, CoreMark +4% once and −1 to −10% the second time, EL1
  MMU-on −3.6% (register pressure). Not kept.
- **A growable shared memory reloads its size before every checked access** (another thread may
  grow it) after any call; a fixed-size one (the importing module declaring initial = maximum, on a
  memory grown to that maximum) loads it once per function: in CoreMark's hottest region 29
  reloads → 2, code 2192 → 1704 bytes. **Kept since M8** ([abi.md](abi.md) "A fixed-size memory"):
  `bootVm` sizes the memory up front with a heap reserve, and JIT modules import exact limits.
  The userspace benchmark 6.9% faster in this VM's Chromium, Alpine's boot 7.2%, Buildroot's 5.6%;
  no difference on the Mac host (`bench/boot/REPORT.md` "a fixed-size memory"). The core itself runs on a copy of
  its module that imports the memory with exact limits ([abi.md](abi.md) "A fixed-size memory"), which measured no
  difference: the userspace benchmark −0.5% in six alternated rounds that overlap, Alpine's boot the same; the block
  interpreter's hot function's TurboFan code is 0.7% shorter (`bench/boot/REPORT.md` "M8: the core with exact memory
  limits"): its loads are unchecked here (above), so only its stores' reloads go, a small part of the core's 8–19%
  of the hot phases.

## The placement effect

**Where guest data falls relative to the `Cpu` changes a hot loop's speed by up to 40% on the M4,
with byte-identical JIT code**: the integer guest runs at ~2500 or ~3750 MIPS depending only on
the `Vcpu`'s address or a sub-page offset of guest RAM; CoreMark at ~1200 or ~1500 (Node;
Chromium splits at other placements). A hardware aliasing effect (the VM exposes no PMU to say
which unit). **Rule:** the small guests run at eight guest-RAM placements, each a fresh core, and
report one median per placement; **never rank two builds on one placement or one heap layout.**
The boots touch enough data to average it out.

## Spills and branch hints

V8's wasm calls have no callee-saved registers, so TurboFan spills every value live across a call
at its definition if any path calls: the load/store slow paths and helper exits cost the hot path
spills. **Branch hints** (on by default in Chromium 153) put the cold side in deferred code, where
the spills go: integer guest +9%, EL1 guests +61–83%, CoreMark +7%. Rule in [jit.md](jit.md)
"Emission".

## Module reuse between boots

V8 reuses a module's compiled code when a module with the same bytes is still alive.
Deterministic boots emit the same modules each time, so a boot ran fast or slow depending on
whether the previous boot's modules had been collected (Buildroot 710 vs 920 ms; TurboFan-only 630
vs 3000 ms). **The boot benchmarks force a GC before each boot** (a first boot's behavior); a VM
rebooted in the same page does get the reuse.

## Threads that never return to their event loop

A vCPU worker runs `vm_run_cpu` in a loop and sleeps in `Atomics.wait`, so tasks posted to its thread never
run. Blink's C++ heap (Oilpan) sweeps in 5 ms tasks there (`CppGC.SweepInLowPriorityTask` ran once in a whole
Firefox session); its garbage then waits for V8's next major GC, whose start finishes the sweep on the vCPU in one
go (`V8.GC_HEAP_ENSURE_SWEEPING_COMPLETED` in "unified heap" mode > `CppGC.SweepFinish`): 100-800 ms of the
thread's own CPU, a few times a session, the longest stalls Firefox's pages session had. Something on Blink's side
of `new WebAssembly.Module` allocates there, and so does `postMessage` with a transfer; `performance.now()` and
`Atomics.wait`/`notify` don't, and the module objects dying with a flush don't feed it. **Each vCPU worker returns
to its event loop every 100 ms** (web/vcpu-worker.ts `yieldMs`; while idle by `Atomics.waitAsync`): no stall of
100 ms or more since (`bench/boot/REPORT.md` "M8: V8's GC on the vCPU threads"). What's left there is the wasm code
GC: the isolate that frees the dead code (50-75 ms of CPU) holds every other vCPU's `ReportLiveCodeForGC` for as long.

Tracing it: `--trace-startup` writes protobuf unless `--trace-startup-format=json`; Oilpan's events need the
`cppgc` and `disabled-by-default-cppgc` categories; events carry `tdur` (the thread's CPU time), which tells work
from waiting. Each worker's `performance.timeOrigin + now()` can differ from another's by hundreds of ms (the
timeline's rows against the vCPUs' `enteredAt`: ~400 ms on the dev VM), so join per-thread clocks through an event
both sides saw.

## Core code (not JIT code)

- The FP guest runs 36% faster under TurboFan-only because V8 inlines compiler-rt's u128 shifts
  (`__lshrti3`, `__ashlti3`) into `fp.rs` there and not under dynamic tiering (inlining follows
  Liftoff's call-count feedback). Inline FP in the JIT took the hot paths out of `fp.rs`.

## Host noise

Host load on the Mac doesn't move the VM's vCPUs to slower cores (measured), but the host's clock
state moves a run by up to ~8%, and a whole run can land at half speed. **Compare builds in one
session, alternating, and check the interpreter's number in the same JSON** (JIT changes don't
touch it) to see the host's state; treat a single slow run as suspect and repeat it.
