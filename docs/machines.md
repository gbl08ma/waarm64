# Machines, disks and snapshots

A **machine** is the page's unit: named, stored in the browser, with its vCPUs, RAM, display, up to 16 disks, its
network adapters, its USB devices, its shared folders and its own snapshots. This page is the model and its rules:
what is stored where, how a disk is identified, the overlay's generation, the disk sources (blank, ramdisk, stored),
snapshots checked by the machine's shape and restored without destroying a disk's state, and definitions in and out.
What the Home page shows and does is [frontend.md](frontend.md) "Machines in the browser", "The Home page" and
"A stored machine's snapshots"; the block device, the overlay's format and stored disks' code are
[devices.md](devices.md) "blk"; network adapters and connections are [networking/adapters.md](networking/adapters.md), USB
[usb.md](usb.md) "The page", shared folders [shares.md](shares.md). Loose ends are
[the machines issues](https://github.com/gbl08ma/waarm64/issues?q=is%3Aissue+state%3Aopen+label%3Amachines). The section numbers are the ones the code's comments cite.

## 1. The rules (the user's, 2026-10-17)

1. **Machines are the unit.** A machine has a name (generated by default: "Brisk Heron"), vCPUs, RAM, the display
   mode, an ordered list of disks, network adapters, and the rest of its settings. Users create, edit, duplicate,
   delete, export and import them on the Home page.
2. **Up to 16 disks** (§4.1), each **read-only or read-write**. A read-write disk writes into an **overlay** in OPFS,
   or, for a stored disk, into the disk itself (rule 12).
3. **Overlays belong to a base disk, not to a machine:** named variants of the same base that any machine attaching
   that base can choose from, one running machine at a time per overlay (its Web Lock). Users name, switch, delete,
   create empty ([New empty](ui:disks:Disks.newEmpty)) and export them.
4. **Disk sources:** an HTTP URL; a file from the user's computer, read where it is; a file **copied into the
   browser** (the user is told it duplicates a file they likely keep, in storage they can't easily see); a **blank**
   disk of a chosen size; a **ramdisk** of a chosen size in the host's memory.
5. **The ramdisk** is empty at every boot, the guest's own reboot included; a snapshot and a suspended copy hold it
   (a restored machine finds the disk it had mounted). Its memory is taken lazily and given back when the guest
   trims (§4.3). A box makes one the guest's swap, turned on at boot with nothing done inside (§4.3 "As swap").
6. **Exports** of disks and overlays: the changes only (a qcow2 over the base) or the whole disk (qcow2 or raw),
   compressed or not, chosen in the Export wizard's two steps (frontend.md "Your own disk").
7. **Snapshots belong to a machine and are checked against its shape** (§5.1), not against one disk. Several per
   machine, kept in the browser or downloaded; a file can be imported or restored at once. **Editing a machine is
   allowed and orphans the snapshots its change invalidates**; the Snapshots tab shows which, and one action deletes
   them all.
8. **Restoring a snapshot never destroys a disk's state:** where an overlay isn't as the snapshot left it, the restore
   writes the snapshot's blocks into a **new overlay** (a fork) and attaches it; where it is, it writes nothing.
   "As it left it" is a **generation counter**, never a hash of a large file (§3.3).
9. **A machine's definition** (its shape: a small file; disk files are picked again, checked by identity) is what
   goes in and out (§6). A machine with its overlays and snapshots as one bundle isn't built.
10. **URL disks** are checked when added (§4.2); what a host must give, chunked images and the block cache are
    [remote-disks.md](remote-disks.md) and devices.md "Over HTTP".
11. **A stored disk can take an overlay in place** ([Merge into the disk](ui:disks:Overlays.mergeButton)): the overlay's blocks are written into the
    stored disk, and **every other overlay of that disk is deleted** (they were over the old bytes); the
    confirmation lists them. A blank disk takes one too (§4.4 "A blank disk's overlay merged").
12. **A stored disk can be written in place**, as an option per attachment: no overlay, the guest's writes go into
    the stored disk (§4.4).
13. **No compatibility with the page before machines:** its overlays, Suspend files and snapshot files (those from
    before the device order of §4.1 are refused: the old order isn't mapped). Nobody used the deployed page then.

The page around them (the user, 2026-10-17):

14. **Disks and snapshots are managed only on the Home page** (and the wizards it opens). The toolbar keeps quick
    actions: **[Snapshot](ui:toolbar:Toolbar.snapshot)** (one click, kept in the browser under the time: a panic button, renamed later), **Load
    snapshot** (the latest five, a file, all of them), Start/Restart, **[Power off](ui:toolbar:Toolbar.powerOff)**, Suspend.
15. **The Home page is a page, not a modal** (no dialogs over dialogs): it takes the machine's place; a machine's
    settings, disks, network, USB, shared folders and snapshots are tabs.
16. **Add a disk is a wizard:** the kind of source first, each explained, then its details.
17. **Import changes is a disk's**, beside its Export (into a new overlay, which the disk switches to). A stored
    machine has no Reset disk (New empty is it, and keeps the old overlay); only a transient machine's Disks tab has
    one. Opening a disk image is the Home page's (From a disk image…), with the drop and the first-run message's
    button. The toolbar's **Machine** menu is only a transient machine's (a stored one's size is its Settings).
18. **The page is Svelte throughout**, with a desktop application's look (frontend.md "The page's code", "The
    toolbar", "Dialogs and the message bar").

Since decided (the user, 2026-10-17):
- A 3D machine on a browser without WebGL2 runs 2D, which is another shape (the guest really sees other devices),
  so its 3D snapshots show as orphaned there. The tests' `?display=simple` runs are another shape too.
- The transient machines' overlays keep their single names (§2).

## 2. The model

| Thing | What it holds | Where |
|---|---|---|
| **Machine** | id, name, vCPUs, RAM MiB (and `ramSplit` when set by hand), display (2D/3D) and Vulkan beside 3D, the JIT cache budget (`jitMiB`), the keyboard layout, the network adapters and their connections (networking/adapters.md), the USB controller (`usb`) and remembered USB devices (`usbDevices`), the mouse, touchscreen and clock switches, clipboard sharing (`clipboard`, off by default: plans/clipboard.md §5), shared folders (`shares`, the switch; `folders`, the attached folders with their own Read-only; `sharesMount` and `sharesPath`, how the page mounts them in the guest: shares.md §1), the attachments in slot order with the overlay chosen per read-write one | IndexedDB `machines` |
| **Disk** (a base) | id, kind (`url`, `file`, `stored`, `blank`, `ramdisk`), name, size, the identity (§3.1), the kind's data: a URL; a `FileSystemFileHandle` (IndexedDB can hold one, JSON can't); the hash where something computed it | IndexedDB `disks` |
| **Attachment** | the disk, read-only or not, written in place or not, the overlay chosen, the virtio serial (`waarm64-<attachment id>`, answered to `GET_ID`) | in the machine |
| **Overlay** | id, name, the base's id and identity, generation (§3.3), created, modified, bytes, its own size and grow mark when grown (§4.5); its `data`, `map`, `meta` and `base` files | OPFS `overlays/<id>/`, its record in IndexedDB `overlays` |
| **Variable store** | the EFI flash bank (1 MiB), **per machine** (its boot entries are the machine's, e.g. after an install from an ISO onto a blank disk) | OPFS `machines/<id>/flash` |
| **Snapshot** | id, name, created, size, the shape and its hash, the pins (§5.1); the `WAARMSNP` file | OPFS `machines/<id>/snapshots/<id>`, its record in IndexedDB `snapshots` |
| **Suspended copy** | a snapshot without the overlays' blocks (§5.3) | OPFS `machines/<id>/suspend` |
| **Stored disk** | an imported image in the overlay's sparse block format (§4.4), with a generation and what it holds (`DiskRecord.bytes`: read at its import, after a run written in place or a merge, and once at the page's opening for a record from before it was kept) | OPFS `disks/<id>/` |
| **Connection** | a tailnet or tailcat, the browser's (networking/adapters.md) | IndexedDB `connections` |
| **Folder** | a shared folder, the browser's: a folder on this computer (its directory handle) or a folder in the browser, a name, Read-only (shares.md §2.1) | IndexedDB `folders`; a folder in the browser's files in OPFS `folders/<id>/` |

- **IndexedDB for records, OPFS for bytes** (`web/app/store.ts`, IndexedDB `waarm64`, ids of 12 hex digits). A record
  is written after its bytes and deleted before them, so a crash leaves unreferenced files, never a record without
  its files. `Store.sweep` removes id-named files under `overlays/`, `machines/*/snapshots/`, `disks/` and
  `folders/` without a record, and waits for writers first (`Store.writing`, a shared Web Lock); the page doesn't call
  it yet ([#155](https://github.com/gbl08ma/waarm64/issues/155)), so those files stay. What the page's start does remove
  (`Store.dropCutFills`) is a cut-off import's or Import changes' `disks/<id>` or `overlays/<id>`: one still marked
  as filling (devices.md "blk"), checked under its own lock taken only if free (a running job holds it, and clears
  the mark before it lets go) and with no record naming it, which is safe beside other tabs and their jobs.
- **Without OPFS** (Firefox's private windows, where `getDirectory` throws a SecurityError; Node): `hasOpfs`
  (`web/overlay.ts`, one probe per context) sends the store to memory (records and files, for the page's life) and the
  overlays, variable stores and suspended copies to the memory of the context that opens them (the machine's worker,
  for its run), and the URL disks' block cache is off. A machine opened from a disk runs; nothing outlives the tab,
  and the message bar says so ([This browser doesn't let the web app keep anything (in a private window, for example): what the machine writes to its disks, its snapshots and the machines you make last only until this tab is closed.](ui:machine:messages.noStorage)). What reads OPFS from the page directly (a kept
  snapshot's download, restore or move, the overlays' sizes, a folder in the browser) isn't adapted
  (`tests/no-opfs.test.ts`).
- **Several tabs:** a running machine holds the Web Lock `waarm64-machine:<id>` (beside its overlays' own), and a
  `BroadcastChannel` tells other tabs to read the records again (`onChange`). What needs the machine off (attaching,
  detaching or reordering disks, a change of shape) is refused while it runs, in this tab or another (`isRunning`),
  with a message to power it off. What isn't in the shape is changed at once, running or not: a network adapter's
  connection, a shared folder attached or detached (the 9p root is a listing the server makes), USB devices. Shared
  folders have their own locks (`waarm64-folder:<id>`: one writer, or several readers; shares.md §1). A start takes the
  machine's lock before it opens the disks, and only if it's free (`ifAvailable`): a second tab of a running machine
  (the page opens the last machine by default) says at once that it runs in another tab, with Retry, instead of
  waiting out the overlay's lock (10 s) for `disk-in-use` (tests/page-open.test.ts). A restore takes it earlier,
  before its commit attaches its forks (`Runner.own`), and its start keeps it (§5.2 "A restore cut off or refused part
  way").
- **Storage:** the Home page's storage bar shows `navigator.storage.estimate()`, and its info icon opens
  [Storage in this browser](ui:machines:StorageDetails.title): what is used of the quota, then what each overlay,
  machine (variable store and snapshots), stored disk, the remote disks' block cache and Vulkan's shaders take (each
  directory's files' sizes; `storageReport`). Those are a part of what the origin holds, so a count that agrees is at
  least their sum; when `estimate()`'s usage is short of it (past 1% or 16 MiB: `countBehind`) the bar gives the sum
  alone, the icon is a warning and the dialog gives the three numbers apart (tests/page-modal.test.ts). Chromium's
  count has been seen at 1.1 GB with 20 GB of files in the profile's `File System` directory, a stored disk's data
  (2026-11-15, ungoogled-chromium on localhost, with an 11 GiB quota and 978 GB free; the cause isn't known).
  `estimate()` counts the origin's other storage buckets (the remote disks' cache) too. The page asks for `navigator.storage.persist()` the
  first time something is stored (without it the browser may evict the origin's data under pressure); while the
  browser hasn't granted it, the storage bar offers [Protect from automatic deletion](ui:machines:StorageBar.storage.persist),
  which asks again, with a tooltip saying what it means, and while this tab's machine runs with the guest agent,
  [Free unused disk space](ui:machines:StorageBar.storage.trim): the guest trims its filesystems and the overlays are
  compacted ([devices.md](devices.md) "Disk space handed back"; the storage-full notice below has it done too). A guest's
  write the storage refuses (over the quota: OPFS's sync handles come back short or throw `QuotaExceededError`)
  fails with `IOERR` after the remote disks' kept blocks give way (`releaseStores`), and the page says the storage
  is full with `estimate()`'s numbers (devices.ts `storageFull`, a notice), once until a write lands again and at
  most once a minute (overwrites of held blocks still land while it's full); the machine runs on, though a guest's
  filesystem may abort on its own refused writes (Debian's ext4 does at times: read-only, then EIO for anything not
  cached, until a restart) (tests/page-quota.test.ts lowers the quota with `Storage.overrideQuotaForOrigin`). Chromium's sync
  handles past the quota come back short in some contexts and throw `QuotaExceededError` in others (off the record a
  refused write returns 4294967288, an error code as its count); the overlay, the block cache and the snapshot writer
  take each as a refused write (`shortOnFull`, a count that isn't the request's): a thrown one used to leave the overlay's
  taken slots neither mapped nor free, and a compaction after a trim then moved one as block 0's (the guest's first block
  read as zeros). A guest's zeroing (it may make a leaf of the overlay's map) goes the same way as its write; a discard writes only into the map's leaves there are (in place), so it needs no room. The overlay's map
  entries that fall short are written back as they were and taken back in memory (`putMap`), so the overlay reads what
  its files say (once its map was written in part, a reopened overlay read another block's bytes); an overlay whose
  making was refused throws the same full storage, and its next opening makes it (a part of its base's identity used to
  be recorded, and every later opening refused as another image's).
- **The storage full outside a guest's disk writes** says so with the same numbers, as the cause under what failed:
  `disks:overlay.storageFull.numbers` ("full, X used of Y", or without numbers where the browser gives none) under
  [Couldn't save the snapshot](ui:snapshots:worker-snapshot.notSaved), [Couldn't suspend the machine](ui:machine:worker-snapshot.suspend.failed),
  a restore's [The disk's changes couldn't be written to this browser's storage.](ui:snapshots:snapshot.storageFull), a
  stored disk's import or merge ([The disk can't be written to this browser's storage.](ui:disks:stored.writeFailed)), Import changes… and a
  snapshot file's import ([Couldn't import {{file}}](ui:snapshots:snapshot-import.notKept)). Each first gets the remote disks'
  kept blocks out of the way (`makeRoom`, web/diskcache.ts: every image's cache, as the page's Clear, those a running
  machine reads given up by its device worker) and tries again (a kept snapshot's and a suspended machine's writer
  `fileWriter`, a snapshot file's import; the rest a refused block's write through `withRoom`, web/overlay.ts): off
  the record the browser refuses writes far below the quota `estimate()` reports, which the cache's budget comes from
  (remote-disks.md "Off the record"). The numbers are `estimate()`'s:
  off the record, and under a lowered quota, they say less is used than the browser refuses at
  (tests/storage-full.test.ts checks them against `estimate()`, and each writer's room, in Chromium without a guest).
- **Transient machines:** the tests' query parameters (`?machine=debian`, `?disk=`, `?disk2=`, `?ncpus=`, `?ram=`)
  make a machine that is never stored. A stored machine's size and devices are its record's, unless the address
  says otherwise for the run (`?ncpus=`, `?ram=`, `?usb=1`, `?mouse=0`, …: docs/frontend.md "What a machine runs
  with"): the address is over the record, never written to it, and the run's snapshots carry the shape it ran with
  (§5.1). Its overlays keep their single names (`waarm64-debian`, `waarm64-buildroot`,
  `waarm64-disk-<hash>` for `?disk=`), which the sweep never touches; its suspended copy is beside its overlay.
- **Opening a disk the old way stays:** a file dropped on the page or opened (From a disk image…, the first-run
  message's button) makes a stored machine for it, named after the file, or opens the machine that attaches it;
  `?disk=<url>` stays transient (the tests').

## 3. Identity, and what changed

### 3.1 A base's identity

Cheap, and recorded at attach: a file's name, size and modification time; a chunked image's manifest `id` and size
(`{kind: 'url', chunked, bytes}`: its content, not its URL, so the same image hosted anywhere is the same disk, and a
template's pins and a definition's disk match wherever it's served from; the bytes are checked against it as they're
read: devices.md "A chunked image"); another URL's path and size, plus its `ETag` or
`Last-Modified` where the server sends one; a stored disk's id; a blank disk's id and size. A chunked image's disk
added before content ids keeps the identity it was made with (its path, the manifest's `id` as its `etag`): nothing
migrates it, and adding the same URL again finds it (`knownDisk` tries both forms). A file or URL added again, opened or dropped is
the disk the browser already has with that identity (`machines.ts` `knownDisk`), so its overlays come back with it.
A definition's URL disk (an import, a store's demo) is that disk only at the same URL: the record says where it's
read from, so another store's definition naming an image's id can't decide where ours reads it (nor a mirror that
later goes away); a new record has the same identity, so the shape still matches. A definition's blank or ramdisk
disk always gets a record of its own (its identity's `id` is hashed in the shape, never taken as a record id), and
identities are checked by kind (`definition-check.ts`).
The SHA-256 (`hashSource`, web/changes.ts, ~640 MiB/s in Chromium) is computed only where one is needed: a re-picked
file whose cheap identity differs (§6) and a changes file's base. Two different files with the same name, size and
date are the same disk to the page.

### 3.2 Re-granting a file

A `FileSystemFileHandle` kept in IndexedDB needs `requestPermission({mode: 'read'})` from a click in each session, and
it is a path, not the file: Chromium keeps a moved file's grant (`queryPermission` says `granted`) and `getFile()` throws
NotFoundError, and another file put at its place reads as that one. So a file disk's file is checked before anything
reads it (web/app/file-access.ts `reach`): its grant, asked with a bound (`GRANT_WAIT_MS`: web/app/grants.ts, docs/shares.md
§1; a grant a click gave in this session isn't asked again, `PageMachine.allowedFiles`, since Chromium may grant and then
leave the question unanswered), then the file read (a byte) and its size against the identity's. Each way it can fail
has its words under "[This web app can't read *name*](ui:disks:file-access.cantRead)" (`disks:file-access.*`): no handle
(`nohandle`), no grant yet in this session (`prompt`), no answer (`unanswered`), refused (`refused`), not where it was
(`missing`: moved, renamed, deleted, its drive not connected), unreadable (`unreadable`), and another size at its place
(`changed`: replaced, and the overlays would read as garbage over it).

**At a start** (`filesNeedingUser`, web/app/run/problems.ts `needsUser`) the machine waits in the message bar, which says
why and offers, one disk a click (a prompt or a picker takes the click's activation):
- "[Allow and start](ui:disks:problems.allowAndStart)" where the browser's grant may help (no grant, no answer,
  refused): `requestPermission`, called before any await. A refusal, an error and an answer that doesn't come within
  `GRANT_WAIT_MS` are said (`file-access.unansweredAllow`: seen on a user's Linux
  Chromium, where Allow and start did nothing, as for a host folder); a late grant starts the machine if the bar still
  offers it. Granted, the file is read before the start goes on.
- "[Choose *name* again and start](ui:disks:problems.repickAndStart)", always: the browser's file picker
  (`showOpenFilePicker`, a handle granted by the pick). The file is checked to be the disk's (below); the record keeps
  its id, name, identity, overlays and attachments and takes the new handle (web/app/disks.ts `replaceFileHandle`).
- "[Select and start](ui:disks:problems.pickAndStart)" for a disk with no handle (a definition's, or one opened through a
  plain file input where the browser has no `showOpenFilePicker`): the same, through the picker where there is one (the
  disk then keeps a handle), else the plain input (for this session only).

**A job that reads the base** checks it first (web/app/areas/file-actions.ts `ready`): an export of an overlay or of the
page's disk (before the save picker, whose file would be emptied for nothing), and Import changes into an overlay (its
hash is checked against the base). One that can't read it says so as its failure, with
[Allow access](ui:disks:file-actions.allow) where it may help and [Choose *name* again…](ui:disks:file-actions.repick);
after either, the user runs the job again. A merge reads no file base (stored and blank disks only), and the disk
surface's job only reads a file it may read without asking (frontend.md). **The Disks pane** (Home) shows a file disk
whose file can't be read for a reason past a grant not given yet, with
[Choose the file again…](ui:disks:DisksPane.repickFile) and, where it may help, [Allow…](ui:disks:DisksPane.allowFile).

**A file chosen again** (web/app/file-access.ts `samePick`) is refused, with words, when its size isn't the identity's
(`other.size`), when the disk keeps a hash (a definition's) and its hash differs
(`other.hash`), or when its image's disk size (a qcow2's header, else the file's
size) isn't the disk's (`other.image`). The same name and date with the size is
the disk's file, as `knownDisk` takes it. A file of the right size and image with another name or date can't be told
from the disk's own by what the record keeps (its cheap identity, §3.1: no hash of a sampled region): the user is asked
([Another name or date](ui:disks:file-actions.otherFile.title)), and taken, it stands for the disk's file under the
disk's identity (its overlays apply over it). Drops give handles too (`DataTransferItem.getAsFileSystemHandle`), as
the picker does: the Add a disk wizard's, Open disk…'s and From a disk image…'s (web/app/areas/disk-actions.ts `open`).

### 3.3 The overlay's generation

Each overlay has a `generation`: a u64 in its `meta` file, and in its record. **The device worker bumps it, durably,
before the first change of an opening** (a write, a discard or a zeroing; a flag per opened overlay: one more small
OPFS write per boot, not per request), and the page copies it into the record when the machine stops. So "the overlay
is exactly as it was at generation g" is two integers compared; nothing is hashed. An opening that only reads leaves
the generation as it was. A stored disk has one too (§4.4).

**The epoch:** writes after a snapshot in the same session must move the generation, or a restore would keep an
overlay that changed after the snapshot. The device reports the generation while the machine is paused for the
snapshot and sets its next change to bump again. A restore that writes an overlay (a fork or a replace) sets its
generation past the old one, never back to a pinned one; a fork's is 1.

A suspended copy whose pins no longer match is stale by construction (§5.3), so no code has to drop it when the disk
changes; the drop-before-run discipline of the page before machines is kept besides (frontend.md "Snapshots").

## 4. Disks

### 4.1 Many disks

- **16 disks at most** (`shape.ts` `MAX_DISKS`). The page's machine has other transports (rng, keyboard, tablet, up
  to four network adapters, gpu, snd, the mouse, the touchscreen, the clock, 9p, clipboard sharing's agent, the notify socket) of the core's 32
  (`virtio::MAX_DEVICES`); 16 disks leaves room for devices to come without making a stored machine that used every
  slot one that a newer page can't make.
- **Slots** (`shape.ts` `slots`): the other devices first, in a fixed order, then the disks; a new device kind joins
  only on machines that have it, so older machines' shapes don't move. The notify socket (`vsock`, devices.md), on every
  firmware machine, is the one after the disks, so it moved none of them, and outside the shape's hash. The tests' transient machines take the same
  order (their guests find their root by UUID or as `vda`, the first disk). A snapshot's header lists the kinds in
  that order (frontend.md "Snapshots", `devices`).
- **Attaching, detaching, reordering or flipping read-only needs the machine off:** virtio-mmio has no hotplug and
  the DT is fixed at boot. The guest names disks by slot (`vda`, `vdb`…); the serial gives it
  `/dev/disk/by-id/virtio-waarm64-…`, which survives a reorder.
- **Boot order** is the firmware's: EDK2 tries the disks in its variable store's order, then in slot order. The
  variable store being the machine's (§2) is what makes an installer work: an ISO read-only and a blank disk,
  install, detach the ISO, boot the installed disk. That flow has no test: Alpine's ISOs lack the UEFI bootloader's
  packages (`grub-efi`, `dosfstools`) and would need the network or a package disk.
- One device worker serves every disk. In realtime mode URL disks' reads run in parallel without blocking it
  (devices.md "Over HTTP"); deterministic runs read them one synchronous request at a time, so several URL disks add
  their waits there.

### 4.2 Sources

- **URL:** added through a check the page runs at once (`web/app/urlcheck.ts`: a HEAD, a range, a suffix range,
  `Content-Range` exposed), which names what fails and what the server needs: HTTPS, CORS for the page's origin with
  `Content-Range` exposed and `Range` allowed in preflights, range requests ([remote-disks.md](remote-disks.md)). The
  check is the wizard's, not the boot's.
- **File:** a handle (`showOpenFilePicker`, a drop), remembered (§3.2); read with `FileReaderSync` in the device
  worker.
- **Stored in the browser:** a file copied into OPFS (streamed, with progress, in `web/app/disk-worker.ts`; the
  confirmation says what it will take, that it duplicates the file, and that the browser's storage is where it goes)
  and converted on the way (§4.4). It never needs picking again and can be merged into and written in place. A
  `File` a page builds from one `ArrayBuffer` of ~384 MiB or more (`new File([bytes])`) can't be read at all in
  Chromium 153, on the page's thread too (`NotReadableError`; 360 MiB reads), so its import fails at offset 0
  (`disks:stored.imageUnreadable`); built from parts of 64 MiB, or fetched, 512 MiB reads (2026-11-24, x86_64, a
  temporary profile and a persistent one alike). A file the user picks is read from disk and has no such limit: a test
  or a tool that makes a large image in a page makes it in parts.
- **Blank:** a size (in MiB, GiB or TiB, up to `MAX_RESIZE`'s 8 TiB, the largest a disk grows to); read as zeros (a `zero` source), always read-write, so it always has an overlay. Its export is
  the whole disk only ("changes only" over nothing means nothing).
- **Ramdisk:** below.

### 4.3 The ramdisk

- **Owned by the device worker** and gone with it (`web/ramdisk.ts`): every boot, the guest's reboot included (a
  reboot is a new machine worker), starts from an empty disk. Writable in itself: no overlay.
- **Lazily allocated:** Chromium on Linux commits a large `SharedArrayBuffer`'s or a wasm memory's pages on first
  touch, so allocation alone would cost nothing for an empty disk; what it can't do is **give memory back** when the
  guest deletes and trims (no `memory.discard` in browsers). So the disk is **1 MiB chunks**, made on a chunk's first
  write and dropped when a DISCARD or WRITE_ZEROES covers it whole; a missing chunk reads as zeros. The disk takes
  DISCARD, so `fstrim` or a `discard` mount returns the memory. No 4 GiB limit; a map lookup per request.
- **A tab's ArrayBuffers share one pool of 8 GiB** (measured 2026-10-24, Chromium 153 in the dev VM: 8191
  `SharedArrayBuffer`s of 1 MiB, 4095 of 2 MiB, the same beside a 1 GiB wasm memory; wasm memories aren't in it).
  An 8 GiB ramdisk of chunks in buffers used it up, and from then on every allocation in the tab threw `RangeError:
  Array buffer allocation failed`: the guest's writeback hung in D state and the page logged an error every 5 s. So a
  worker's ramdisks keep at most `SAB_BUDGET` (4 GiB) in buffers of their own; past it a chunk is a 1 MiB slot in a
  shared wasm memory of up to 4 GiB, grown a chunk at a time (address space reserved for the disk's size, at most
  4 GiB a memory). Those slots go back to the ramdisk when dropped (its next chunk takes one) but never to the host (a
  wasm memory doesn't shrink). A wasm memory per chunk isn't a way out: a tab gets ~125 of them (each reserves
  ~8 GiB of address space). A chunk that can't be had at all fails its write with IOERR, and the device worker's
  `notice` puts it on the page's message bar. An 8 GiB ramdisk filled to the brim, ext4 and raw, left the guest
  answering.
- Shared memory, so the snapshot writer reads the chunks without a copy through the device worker.
- The machine's memory check (`hostMemoryGiB`) counts the ramdisks' sizes (what they may grow to).
- A snapshot holds its chunks (`DISK` frames, as an overlay's blocks), a suspended copy too (the ramdisk isn't in
  OPFS); a restore hands the new chunks to the device (`BlkSpec.ramInit`).

**As swap.** A ramdisk's **swap** box in the machine's disks (`Attachment.swap`, ramdisks of 40 KiB and up; in the
shape, §5.1, and carried by definitions) makes it the guest's swap with nothing to do inside:
- At every start the device worker writes a swap area's first page over the empty ramdisk (`BlkSpec.swap`, the label;
  `web/ramdisk.ts` `swapHeader`: `mkswap`'s version 1 page, byte for byte, with a fresh UUID, the label
  `waarm64-swap<n>` by the swap ramdisks' slot order, and `SWAPSPACE2` at 4 KiB). A restored ramdisk is the snapshot's
  chunks (`ramInit`), untouched: the restored guest has its swap in them.
- The guest gets an `fstab.extra` systemd credential in SMBIOS type 11 (`web/app/guest-swap.ts`, through
  `opt/waarm64/oem-strings` as the units of [frontend.md](frontend.md) "What the page sets in the guest"):
  `LABEL=waarm64-swap<n> none swap sw,nofail,discard 0 0`, which `systemd-fstab-generator` reads with /etc/fstab
  (systemd 254+: Debian 13 and Arch; Debian 12 ignores it and boots without the swap). `discard`: the kernel trims
  what it frees (and the whole area at `swapon`, past the first page), so the chunks go back to the host as the guest
  stops needing them. `nofail`: a guest with pages larger than 4 KiB doesn't find the signature and boots on.
- It isn't spill memory: every swapped page runs guest code (the kernel's swap path, virtio-blk) where a spill memory
  is a load ([spill-memories.md](spill-memories.md)). It suits a user who wants the kernel's LRU to decide what stays.

### 4.4 Stored disks: their format, merging, writing in place

- **The format is the overlay's** (`data` and `map`, 4 KiB blocks, zeros without a slot, the map in leaves of 4 MiB
  made as ranges are written: devices.md "blk") over nothing: a stored disk is a sparse, writable block store
  (`web/stored.ts`). A stored disk from before leaves (a flat map) is read as it is under its overlays and converted
  by its first writable opening's first change (writing in place, a merge into it). An imported qcow2 is converted on the
  way in (compressed clusters inflated, zero and unallocated ones left out), a raw image too (zero blocks left out).
  The import writes its store unordered and flushes it at its end, marked as filling until then; the disk's record
  comes after, so an import cut off is never a disk, and the page's next start removes its files (§2, devices.md
  "blk"). So a stored disk takes no more than its data, and the same code reads, writes and exports it. Debian's published
  image (a ~400 MB compressed qcow2) stores as 1,043 MB, estimated beforehand at 1,212 MB from the qcow2's
  allocated clusters (`storedEstimate`); its import took ~94–140 s in a cloud session. Keeping the file as it is was
  the alternative: a qcow2 can't be written in place (our qcow2 code reads, and writes whole files, never allocates
  in one), so it loses merging and writing in place.
- **The blk device writes through `WritableDisk`** (web/overlay.ts: `write`, `zero`, `discard`, `flush`, and
  `written`/`block`/`zeroed` for exports and snapshots); nothing above it assumes a base underneath. A stored disk
  opened for writing is the same block store over zeros, so **writing in place needed no new device code**, only
  the attachment's choice. Ticking Read-only clears it (the box is hidden then); an attachment marked both (a record
  from before) is read, not written: the device, the snapshots' bases (§5.1) and the record's refresh after a run all
  take written in place as `inPlace && !readOnly`.
- **Locks:** under overlays a stored disk is read with read-only sync access handles under a shared Web Lock, so
  several machines can use it at once; writing it in place or merging into it takes the lock exclusively.
- **A stored disk has a generation** (§3.3) as an overlay has; writing in place bumps it.
- **Merging an overlay into its stored disk:** the machines using the disk are off: a merge holds every machine that
  attaches the disk off for its length (their machine locks, each only if free: web/app/machine-hold.ts
  `holdMachines`), and is refused while one holds its own ([{{machines}} uses this disk and is running. Power it off
  first.](ui:disks:merge.running_one)): a start takes its machine's lock before it reads the record and keeps it to the
  run's end (`Runner.own`), and its worker opens the overlays only in its disk phase, so the overlays' file locks alone
  let a start or a restore under way (another tab's) open an overlay the merge deleted, made anew with no record naming
  it. The start reads its records again once it holds the lock (`Runner`'s `#openDisks`): read before, they may name
  what a merge or a delete took away (tests/merge.test.ts, tests/page-restore.test.ts). Delete overlay holds off the
  same way the machines that have the overlay chosen or whose restore that never loaded names it, and for a restore's
  fork every machine that attaches its disk (a restore attaches an earlier fork again: `deleteOverlayAsked`). A start
  held off by Delete overlay, a resize or Import changes says that its disks are being changed, not that it runs
  elsewhere (`holdMachines` holds a second lock beside the machine's: `heldOff`). The confirmation names
  the other overlays that will be deleted and the snapshots it orphans. Then: the other overlays are deleted, the
  disk's generation is bumped and its `meta` names the overlay being merged, the overlay's blocks are written into
  the disk (its zero blocks as zeros), the overlay is deleted, the marker removed (`mergeOverlay`), and only then the
  overlay's record. Interrupted, or failed partway (the storage full), the disk finishes the merge at its next opening
  (`resumeMerge`: writing the same blocks again is harmless) before anything reads it, or at the next Merge into the
  disk of the overlay: its record kept, the sweep keeps its files, and deleting it is refused (`disks.overlayMerging`:
  part of it is in the disk already). A machine's start finishes it before it opens any overlay (`Devices.open`): the
  machine that has the overlay chosen would otherwise hold that overlay's lock while the merge waits for it. A start
  while a merge runs (in this tab or another) is refused at once ([An overlay is being merged into one of the
  machine's disks. Wait for the merge to finish, then Retry.](ui:machine:worker-errors.diskMerging.cause)): the start
  finds its machine held by the merge (`Runner.own` says the merge, not another tab: `mergingInto`), and the worker
  holds each of its stored disks' merge lock, shared and only if free, until its disks are open
  (web/stored.ts `holdAgainstMerges`: its own check), so a merge asked for meanwhile finds the machine's lock held or
  its overlays in use (tests/stored.test.ts). The merge first undoes the
  held machines' restores that never loaded (§5.2 "A restore's records"), as their locks' owner. An overlay a restore's
  fill was cut off in (still marked), or one that a restore that never loaded of a machine that doesn't attach the disk
  any more still names, isn't merged ([A snapshot's restore into the overlay {{name}} didn't finish, so it holds
  nothing to merge. Nothing was deleted.](ui:disks:merge.cutOff)): it reads as empty, or is that restore's, and the
  merge would only delete the disk's other overlays (tests/merge.test.ts). A merge of
  another overlay of the disk meanwhile is refused before it deletes anything ([A merge of the overlay {{name}} into
  this disk didn't finish, and part of it is in the disk already. Use Merge into the disk on {{name}} again to finish
  it, or start a machine on the disk. Nothing was deleted.](ui:disks:merge.otherMerging)): it would delete the one being
  merged. An overlay that can't be opened any more (gone, or its deletion, a file at a time in OPFS, cut off)
  has had its blocks copied, and what is left of it is deleted.
- **A blank disk's overlay merged** (`web/app/merge.ts`; the user's QA, 2026-11-18: an overlay a resize on a machine
  made, §4.5, had no way into its disk): an overlay **nothing was ever written to** (its generation 0, read from its
  `meta` under the merge's lock) grows the blank disk to the overlay's size and is deleted; the disk stays blank, its
  identity keeps the size it was made with (as a stored disk's does), so its other overlays still fit it and stay, and
  a machine that had it chosen gets an empty one at the new size at its next start (its guest sees the same disk: its
  snapshots stay); refused while a machine runs over any overlay of the disk (those without a size of their own see
  the new size), as a resize is. An overlay **written to** makes the blank disk a stored disk of its blocks at the overlay's size
  (`convertBlank`: the stored disk's merge job into a block store that starts empty, then the record says `stored`
  with a stored disk's identity and the overlay's grow mark); its other overlays are deleted, as above, and the machines
  that attach it see another disk (their snapshots orphan by the shape); then the overlay's record goes and the
  machines that had it chosen are left without one. A copy that fails (the storage full) leaves the overlay as it was
  (its blocks, its record, its machines' choice), and the half-made block store is removed. The copy keeps the
  overlay's files (`keep`); after it the machines that had it chosen are left without it, then the disk's record says
  stored, then the overlay's record goes and its files: cut off before the disk's record, the disk is still blank and
  the overlay holds what it held (the next conversion starts over); after it, the overlay's record may stay beside the
  stored disk, unchosen (tests/merge.test.ts). The confirmation (`mergeEffect`) says which, the size, the overlays deleted and the
  snapshots it orphans (for a grow: those of machines whose guest would see the disk at another size); under the
  merge's lock, a merge that is no longer the one confirmed (another how or size: the overlay written meanwhile, by a
  machine in another tab; or an overlay to delete the confirmation didn't list) is refused
  ([The disk's overlays changed since you were asked (in another tab, or by a machine). Look again and merge it
  again.](ui:disks:merge.changed)).
- **Writing in place and snapshots:** a disk written in place has no earlier state to fork from. A kept snapshot pins
  the disk's generation and restores it only while it matches; otherwise a file carrying the whole disk forks it into
  an overlay, and one without is refused with the reason. **A downloaded snapshot can't be self-contained** without
  a copy of the whole disk, so saving one asks whether the whole disk goes in (its size said) or not (the file then
  restores only onto this disk at this generation). A suspended copy works as with overlays. The attachment's UI says
  that writing in place gives up forking and overlays' variants.
- **Exports** of a stored disk are whole-disk ones (qcow2 or raw, compressed or not); "changes only" applies to its
  overlays. A qcow2 of a stored disk (or of an overlay over one) reads only the blocks the store (and the overlay)
  holds, its leaves walked (`Source.held`), so a disk grown to a TiB that holds a few GB reads those; a raw one is
  the whole size by nature.

### 4.5 Growing a disk

Writable disks aren't qcow2 files: an image is a read-only base under an overlay, and a stored disk is the overlay's
format itself (§4.4). So growing one is a size in a record, and for an overlay in its `meta` too (the user's design,
2026-11-14). The page's [Resize…](ui:disks:Disks.resize) (frontend.md "The Home page": the Disks pane's stored disks,
ramdisks and overlays, a machine's Disks tab) opens one dialog over these. A machine's writable attachment with no overlay
chosen yet (its first start would make one) is resized through the one it makes: `resize(store, { machine, attachment },
size)` makes an empty overlay at `size` ("Changes", as the start names it; marked from the disk's size with the box),
chooses it, under the machine's lock (no files to lock yet), and only that machine's disk grows (`resizeCosts`); an
overlay made meanwhile (a start) is resized as itself.
- **An overlay** (over a URL, file, blank or stored disk) has a **size of its own** (`OverlayRecord.size`, and the
  u64 at 32 in its `meta`, which the device worker reads at its opening: devices.md "blk"); absent, or a 32-byte
  `meta` from before sizes: none. Per overlay, not per disk: overlays are a base's named variants (rule 3), and a
  blank disk's identity holds its size.
- **A stored disk's** and **a ramdisk's** size is their record's, grown (`DiskRecord.size`); their identity keeps
  the size they were made with (an overlay's `base` file records it, so a grown stored disk keeps its overlays). A
  stored disk's block store needs nothing: blocks past its old end read as zeros, and its map grows as they're
  written. A URL's, a file's or a blank disk itself doesn't grow; its overlays do.
- **What the guest sees** (`sizeSeen`, web/app/disk-size.ts): through an overlay, the larger of its own size and its
  disk's; read-only, written in place or a ramdisk, the disk's. The shape's disk size is that (`shapeOf`'s
  `overlays`, the page's `shapeNow` and `about` pass the records), and so is the start's (`StartDisk.size` where it's
  past the source's, then `BlkSpec.size`: the device's capacity, and the overlay opened at it over a smaller image,
  reading zeros past its end). **So a resize orphans the snapshots** of the machines whose disk grows, as any shape
  edit does (rule 7), and a suspended copy no longer resumes.
- **Grow only, whole sectors, its machines off** (web/app/resize.ts): `resizeCosts(store, target, size)` says what a
  resize does, for the confirmation: the size now, the machines whose disk grows (an overlay's: those that have it
  chosen; a stored disk's or a ramdisk's: those that attach it, unless their overlay is as large already), those of
  them running, and their kept snapshots made at the size now (orphaned by it). `resize(store, target, size, { grow })`
  refuses (`MsgError`s, `machines:resize.*`) a size that isn't larger or isn't a multiple of 512 (`SECTOR`: the blk
  device's sector, and QEMU's rule for a qcow2's virtual size), a URL, file or blank disk itself, a machine using it
  running, and the overlay's or stored disk's lock held (a machine the records don't show running, an export, a merge:
  the lock Merge into the disk takes); it then writes an overlay's `meta` (`writeOwnSize`, a writable stream: from the
  page) and its record, or the disk's record, under that lock, reading the record again once it holds the lock (a merge
  that forgot the overlay meanwhile isn't undone; a rename stays). A ramdisk has no files to lock: its machines' locks
  are taken instead (each only if free, as a start takes it), so none starts while its record changes. An overlay's
  record refused after its `meta` was written puts the `meta` back; cut off between the two (a tab closed), the next
  `refreshOverlay` takes a `meta` past its record into it (the device opened it at that size). A stored disk's first
  resize keeps the size it was made with (`DiskRecord.made`: its identity doesn't hold it).
- **An upper bound:** `MAX_RESIZE` (8 TiB) refuses a larger size (`resize.tooLarge`). It is the qcow2 export's: our
  4 KiB clusters and QEMU's largest L1 table (32 MiB) make 8 TiB the largest qcow2 `qemu-img` opens (8 TiB + 1 GiB
  is refused). The overlay's map no longer bounds it (it grows with what's written: devices.md "blk"); what an
  opening keeps for the size alone is the top table, 4 bytes per 4 MiB (8 MiB at 8 TiB). The slots (u32: 16 TiB of
  written blocks), the blk device's capacity (u64 sectors) and JS numbers (2^53) go past it. (256 GiB before the
  two-level map: the flat map was 4 bytes per 4 KiB block in memory, 1 GiB per TiB.)
- **The grow mark** (`GrowMark`, `{ from, to }`, on the overlay's or stored disk's record, not an attachment's:
  whichever machine boots it next does it): `grow` sets it (`from` stays the size before the first resize the guest
  hasn't followed), a resize without it clears it, `growMark`/`clearGrowMark` read and clear it, `growFailed` notes a
  failure on it (`failed`: the next one clears it). A ramdisk gets none (empty at every start). A stored disk's mark is
  followed only by the guests that see the disk's size (written in place, or through an overlay smaller than it): one
  whose overlay was grown past it saw no change, and its answer would clear the mark for the others. The run's agent follows
  it (`growsOf`: the stored machine's marked disks, their serials and sizes): GROW at each agent's HELLO, the mark
  cleared by a final GROWN and the answer said once (devices.md "A disk grown", "The page's side").
- **What follows the size:** a restore's fork takes the size the snapshot had (its record's `size` and its `meta`,
  written by the page when it makes the fork, so an export or a start after a failed restore sees it too; the worker
  writes it again with the blocks); an earlier fork is reused only at that size (one grown since is another disk);
  exports open the overlay with its `meta`, so a whole disk's qcow2 or raw
  is the grown size and a changes-only qcow2 may be larger than its backing file; Import changes takes a changes file
  larger than its base (the base's hash still decides) into an overlay of that size; Merge into the disk of a grown
  overlay grows the stored disk first (its mark with it), so a merge resumed at the next opening copies at that size.
- **A fork keeps a standing mark** (the rule, 2026-11-15): a restore's new fork takes the grow mark of the overlay the
  snapshot pinned when that mark still stands and the snapshot was taken past its `from` (`{ from, to: the snapshot's
  size }`). A mark that stands means no run since the resize got the guest's GROWN, so a snapshot taken at the new size
  is of a guest whose partition was still the old one; its restored guest needs the grow as much. Taken before the
  resize (at `from`), the fork is at the old size and needs none. The resized overlay keeps its own mark (its blocks are
  still the old partition's). A reused fork keeps what it has. A stray mark is harmless: the agent's grow is idempotent
  (NOTHING, "already fills").
- **Variants keep the attachment's size** (the rule, 2026-11-15; §5.1: the size is in the shape): [New empty](ui:disks:Disks.newEmpty) makes
  the new overlay at the size the attachment's guest saw (`newEmptyOverlay`), marked to grow from the disk's size (its
  base's partition doesn't fill it), so switching to a fresh variant orphans nothing; changes imported (Import changes…)
  go into an overlay at least that large too (`keepSize`, marked from what the changes hold). A switch to an existing
  overlay can't change that overlay's size (other machines may use it, and its own partition table is its own), so a
  switch the guest would see at another size asks first, naming the snapshots it orphans (`sizeOrphans`,
  `switch-asked.ts`), as Import changes does for changes of a larger disk. Merging and deleting an overlay are asked
  already (their confirmations name what goes); a machine left without an overlay gets an empty one at the disk's
  size at its next start.
- **A stored disk's changes files** (Export's changes only, from its overlays): the base hash covers the disk as it was
  made (`made`), or up to the end of the last block it holds where that is further (web/changes.ts `hashedSize`,
  `baseHash`, both the export's and the import's). So growing a stored disk keeps its changes files importable (its
  bytes past the old end read as zeros, which a hash at the old size already said), while writing past its old end (in
  place, a merge) changes the hash, as any write to it does. A disk never grown hashes its whole size, as before.
- **A definition** (§6) carries a grown overlay's size (`overlaySize`, `grownSize`; at most `MAX_RESIZE`, or the
  definition is damaged), and a grown stored disk as the size it was made with (`size`, the image another browser picks)
  with the size its writable attachment sees as `overlaySize`: the imported machine's attachment
  gets an empty overlay at that size, marked to grow (`withGrownOverlay`), so its guest sees the same disk and grows its
  base's last partition into it at its first start with the agent.

## 5. Snapshots

The file's format, what the core saves and the page's toolbar and header fields: [platform.md](platform.md)
"Snapshots", [abi.md](abi.md), frontend.md "Snapshots"; the Snapshots tab: frontend.md "A stored machine's snapshots".

### 5.1 The shape and the pins

- **The shape** (`shape.ts` `shapeOf`) is a canonical JSON of what the guest sees: vCPUs, RAM (and the memory
  split), the display (2D or 3D: different devices) and Vulkan, the transports in slot order, each disk's size,
  read-only flag, serial and base identity (and `swap: true` for a ramdisk the guest uses as swap, §4.3), the CPU features (`cpu`), the network adapters' MACs (left out for one adapter at the default MAC). **A feature that
  came later joins only when it's on** (the USB controller as `usb: true`; the mouse, the touchscreen, the clock,
  9p and clipboard sharing's `agent` as transports on machines that have them), so machines made before it keep their hash; `sha3` among the CPU
  features is left out of the hash for the same reason (the features after it, ABI 59's, are in it). Its SHA-256 is the **shape hash** (`shapeHash`). Names, the
  overlay chosen and writing in place aren't in it. Nor is the automatic split of the RAM (`ramSplitMiB`), only a split
  set by hand: it moved once, on 2026-11-21, when memory 0's ceiling went from 3071 to 3072 MiB (spill-memories.md
  "Sizes"). A machine of more than 3071 MiB on the automatic split boots with the new layout, and its snapshots from
  before then keep their hash but refuse to restore (the page says the memory differs: 3071 MiB then, 3072 now); a
  machine of 3071 MiB or less, or with a split set by hand, is as it was. The machine's JIT cache budget (`jitMiB`, when set) rides in the
  shape **outside the hash**: the guest doesn't see it and a state restores under any budget, so lowering it after a
  crash orphans nothing. The snapshot header carries the whole shape, so a snapshot file can make its machine.
- **The pins** (`SnapshotDisk`, web/snapshot.ts): per writable disk, its path (`overlays/<id>`, or `disks/<id>` for
  a disk written in place) and generation, the blocks the file carries, and `ram` for a ramdisk; the page maps
  paths to records.
- **The shape a snapshot carries is the one its run had:** the record with the size and devices the address gave
  the run, if it gave any (`?ncpus=`, `?mouse=1`…: frontend.md "What a machine runs with"; the start's `about`), the
  display it ran with and the page's CPU features. "Now" below is the same rule on the page as it is opened.
- **Orphaned:** a kept snapshot whose shape hash differs from its machine's now (the user changed RAM, added a
  disk, turned shared folders on…, or it was taken under an address that changed the machine and the page is opened
  without it). Pins don't orphan a snapshot: a moved-on overlay is what the fork is for. An overlay's own size does
  (§4.5): a resize, or a switch to an overlay of another size, orphans the snapshots made at the size before; both ask
  first, naming them. The Snapshots tab says what
  differs (`shapeDiff`, from the two shapes), and offers [Create a machine like it](ui:snapshots:Snapshots.like) (`machineLike`: a new machine
  from its shape, disks the browser has attached again by identity, blank disks and ramdisks made again, files picked
  again; at the sizes the snapshot had: a grown overlay's as an empty overlay at that size, marked to grow; a ramdisk
  grown since as another of the old size; a stored disk grown since refused, as it can't be seen smaller) and [Delete orphaned snapshots](ui:snapshots:Snapshots.deleteOrphaned).
- **Unrestorable** (the user's QA, 2026-11-18: a snapshot found unrestorable only at its restore wastes storage): a
  kept snapshot that **no change to the machine can make restorable** shows as orphaned too, with its reason, before
  any restore. The lists (the Snapshots tab, Load snapshot) and the restore (`planRestore`) judge with one function
  (`lost`, web/app/snapshot-lost.ts; web/app/snapshots.ts `unrestorable` and the restore's refusal put it in their words),
  over the stored disks' generations **read from their files** (`diskGenerations`: each disk's `meta`, a few bytes,
  readable while a machine holds the disk open for writing), which the lists read when shown and every 2 s while they are
  (`watchGenerations`). Not from the disk records: a record lags its files while a machine writes the disk in place
  (the first write moves the files' generation; `refreshStored` reads it into the record at the run's stop), so a
  list judged from the records said nothing during the run that moved the disk, while the restore, reading the files,
  refused it (the user's QA, 2026-11-18; tests/page-unrestorable.test.ts, tests/unrestorable.test.ts "agree"). The
  causes, all permanent:
  - **a disk written in place that moved on**, the snapshot without the whole disk (a kept one never has it): its pin's
    generation isn't the disk's. A generation only grows, so the bytes it pinned are gone. While the generation still
    matches, an attachment no longer written in place restores through a fork that holds nothing over the unchanged
    disk (it used to be refused: that cause could be undone, and is gone). Nothing makes this unknowable beforehand;
    an open list is at most one read (2 s) behind a guest's next write.
  - **a stored disk it was taken over** (read-only, or under an overlay) **written in place or merged into** since:
    the snapshot's overlay blocks, or what a read-only guest cached, are over other bytes. The page records the stored
    disks' generations at each start (`basesOf`: a running machine holds them open, nothing moves them while it runs)
    into the run's `about`, the snapshot's header (`bases`) and a kept snapshot's record; a restore (`planRestore`) and a
    resume (`sameOverlays`) refuse one whose disk moved (before, the restore forked over the new bytes). Snapshots from
    before `bases` aren't checked.
  - **another core's snapshot format** (`coreVersion`, against `SNAPSHOT_VERSION`, web/snapshot-file.ts, which
    tests/snapshot-plan.test.ts pins to the core's): a page updated with a new format reads none of the old (platform.md
    "The snapshot file"). A record from before `coreVersion` counts as format 6. The restore checks the header's before
    it stops the machine (`snapshot.otherVersion`), as the worker does again at the start.

  What can be undone stays the shape's orphaning: a setting or a disk changed back, the address's parameters, a
  browser without WebGL2. What isn't a cause: an overlay deleted or merged away (a kept snapshot carries its blocks and
  forks), a disk deleted (refused while attached; a detach is a shape change). Not detected: a URL disk's image
  replaced under the same path and size without an `ETag` or `Last-Modified` (its identity can't tell). The toolbar's
  Snapshot on a machine with a disk written in place says, in its tooltip and its notice, that the snapshot restores
  only until that disk is written again (frontend.md "A stored machine's snapshots").

### 5.2 Save, keep, restore

- **Keep or download:** a kept snapshot is the same file as a downloaded one (self-contained: the overlays' blocks
  are in it), written by the worker into `machines/<id>/snapshots/<id>`, its record written after. So a kept snapshot
  downloads as it is. Keeping many snapshots of a machine with a big overlay costs that overlay each time; sharing
  blocks between them isn't built ([#175](https://github.com/gbl08ma/waarm64/issues/175), if the sizes measured ask for it).
- **Restore** (a kept snapshot, or a file restored at once): refused before anything is touched when the shape hash
  differs (the notice points to Create a machine like it). Then per writable disk (`planRestore`, web/app/snapshots.ts; the page
  passes the plan to the worker as `start.plan`): the attached overlay is the pinned one at the pinned generation →
  **keep** (nothing written: the restore is RAM and state); otherwise → **fork**: a new overlay named after the
  snapshot gets its blocks and is attached (at the size the snapshot had: §4.5), and the old overlay stays as it was
  (an overlay written by a restore is over zeros: a disk whose size isn't a multiple of 4 KiB has a last block shorter
  than the overlay's, whose write reads the rest). The confirmation says which disks
  fork, and offers to **replace** instead (the snapshot's blocks take the attached overlay's place; what was written
  since is lost), for an overlay no other machine has chosen (below, "Other machines"). A
  ramdisk takes the snapshot's blocks. Transient machines have no plan: a restore replaces their overlays.
- **How a replace is made** (`planRestore`'s `replaceKeeps`, web/app/restore-room.ts; #156): where the storage has room
  for the snapshot's blocks beside what is there (`estimate()`'s quota less usage, at least the blocks every fork and
  replace of the restore write, a tenth more and 64 MiB; where the browser says nothing, there is), a replace is a
  fork whose step says so (`replaced`): a new overlay takes the blocks, and once the snapshot loaded the overlay it
  replaced is deleted (with the machines that could open it held off but this one, `deleteOverlayAsked`'s `owner`)
  and the fork takes its name and is no snapshot's fork; cut off part way, it is undone as a fork, so the disk is as it
  was. Where the replaced overlay can't be deleted then (another machine chose it since, one of the machines that could
  open it runs), both stay: the fork named after the snapshot. Without that room the attached overlay itself is
  emptied and filled (`into`), which needs room only for the snapshot's blocks, and the question says that a replace
  that stops part way starts the disk from its image ([Keep the overlay {{list}} as it is and restore into a new
  overlay? Replacing it will lose what the machine wrote since the snapshot. The browser's storage hasn't room to keep
  it until the restore is done, so a replace that stops part way starts the disk from its
  image.](ui:snapshots:snapshot-restore.restore.keep.tight_one)). Decided once, when the restore is planned, for the
  question and the commit alike. Keeping the replaced overlay always (a replace refused for want of a fork's room)
  was rejected: a replace is what the user picks to need less than a fork. The page's own disk, Import changes onto
  it and transient machines still fill in place (devices.md "blk").
- **An attachment written in place since a snapshot taken under an overlay** (the shape doesn't include writing in
  place, so the snapshot isn't orphaned): the machine runs on the stored disk itself, not on the overlay its record
  still names, so that overlay is neither kept (the snapshot's RAM would land on the stored disk without the overlay's
  blocks) nor offered to replace or filled as a template's fresh one. The disk forks (or attaches an earlier fork
  again), and the attachment is under an overlay again (its undo puts it back in place). Once the stored disk was
  written in place since, the snapshot is refused by its `bases` (§5.1); this rule covers the runs that never wrote it
  and the restore before any run (PERF loop 86; tests/unrestorable.test.ts "written in place since").
- **The plan is made twice:** once for the confirmation, while the guest may still run, and again once the machine
  has stopped (`commit`): a disk the guest wrote to in between forks then (the replace answer holds only for the
  overlays the confirmation named: one switched to another overlay meanwhile forks). The worker refuses a **keep** whose overlay isn't the one the disk's device runs on (the plan names it: `overlays/<id>`, or `disks/<id>` written in place) or isn't at the generation the plan names
  ([A disk this snapshot was to keep as it is was written to after the restore was planned, so the snapshot no longer fits it. Nothing was changed. Restore the snapshot again.](ui:snapshots:snapshot.keptMoved)), so the snapshot's RAM never lands on a disk that moved on.
- **A fork into a fresh overlay:** on a machine's first restore (a template's, §6.1), where the attached overlay
  never took a write (its files' generation 0, or read as empty: a first restore undone; at the snapshot's size: the
  overlays the page made for the machine) and no other machine has it chosen, the fork's blocks go into it (named after the snapshot and marked as its
  fork once it loaded) instead of a new overlay beside it, and
  nothing is asked: it holds nothing to lose (`pristine`, `planRestore`'s `fresh`; tests/template.test.ts). A restore
  the user asks for leaves an overlay they made as it is.
- **Repeated restores don't pile up forks:** a restore that would fork attaches an earlier fork of the same snapshot
  whose generation hasn't moved since (still 1), at the snapshot's size, instead (**reuse**); never one whose fill
  was cut off, one another machine has chosen, nor one a restore that hasn't loaded names, as what it made or as what
  its undo goes back on (below).
- **A restore cut off or refused part way** (a closed tab, the storage full, a damaged file, a disk that didn't open
  after the fill): the page commits the restore (its forks made and attached) before the worker opens any overlay,
  which it does only in the disk phase, after the check pass and the RAM's; the fill marks its overlay (devices.md
  "blk", "Crash and refusal") and anything that opens it before the mark is cleared takes it as empty. Until the worker
  says the snapshot loaded, the restore is one that never loaded, and the machine's next load undoes it, whether it was
  cut off before the fill or refused after it: so the machine starts on its disks as they were, except that an
  overlay a replace or a template's first restore wrote into reads as empty (what it held was replaced), unless
  another machine wrote it since. How, below
  ("A restore's records"). The worker's message says which: a refusal before any disk was written ([The machine
  isn't running, and its disks are as they were. Start boots {{machine}} normally, and Load snapshot… tries another
  file.](ui:snapshots:worker-errors.notLoaded.cause)), one once the disks were being written that deleted none of their
  own changes (only new forks took part of the snapshot: [The machine didn't start, and its disks hold none of the
  snapshot's changes. Start boots {{machine}} normally.](ui:snapshots:worker-errors.notRestored.cause)), and one that
  did ([The machine didn't start. The changes the restore was replacing were deleted, so the disks that held them start
  from their images. Start boots {{machine}} normally.](ui:snapshots:worker-errors.notRestored.emptied); the plan's
  `fork` marks an overlay that holds none of the disk's own changes, a new fork or a template's fresh overlay, and the
  fill's refusal of any other carries `emptied`, whatever refused it: the file, the storage full, a
  disk that didn't open, said under those words, web/app/worker-errors.ts `explain`). Retry after a restore's failure (its commit's,
  its start's before the snapshot loaded: the disk in use, a file disk's permission; or the record of its load
  refused) restores the snapshot again (`Runner.again`), on the records as the undo leaves them; it isn't a boot.
  The disk phase takes every target overlay's lock before it empties any: one open elsewhere refuses the restore with
  all the disks as they were. A kept overlay grown since the plan (a resize in another tab: its own size, or the disk's
  record, past the size the snapshot saw) is refused as one written since (`snapshot.keptMoved`).
- **A restore's records** (web/app/snapshots.ts `commit`, web/app/snapshot-undo.ts; the rules' table is
  tests/restore-records.test.ts). One record holds a restore that hasn't loaded: its machine's, in `restoring`
  (web/app/restore-step.ts `RestoreStep`), one step per attachment it changed. No overlay record carries a mark of its
  own, so only that machine's load, start or `loaded` acts on it, and another machine that has one of its overlays
  chosen never does.
  - **The steps:** `fork`, a new overlay made and attached (with what the attachment had: `before`, its overlay or
    written in place); `reuse`, an earlier fork of the snapshot attached again (with `before`); `into`, the attached
    overlay written into (a replace without room for both, or a template's fresh overlay), with the generation its
    files had at the commit. A `fork` with `replaced` is a replace with that room: the replaced overlay is its `before`.
  - **The commit** (under the machine's lock, which the restore takes before it and its start keeps to the run's end:
    `Runner.own`) writes the machine's record once, its attachments switched and `restoring` set, onto the record as
    the store has it then (one read and write, `Store.updateAmong`: another tab's write to its other fields meanwhile
    stays, and the other machines' records are read in the same transaction: below, "Other machines"): that write is
    the commit. It gives the restore a **fill token** (`newId`), in each step and each write of
    the worker's plan, which the fill writes into each overlay's `meta` with its mark (below, "Other machines"). A new fork's record is made after it, under the id the step names: cut off between, the next load finds
    the step and goes back, with no fork to delete. Nothing else is written: a reused fork's and an overlay written
    into's records stay as they are.
  - **`loaded`** (the worker's, before the vCPUs run: web/app/run/restore-loaded.ts) clears `restoring` and
    `restoreFirst` in one write: from then on everything the restore attached is the machine's. The vCPUs wait for
    the page's answer (`recorded`, sent once that write settled; web/app/worker-post.ts `postLoaded`), so the guest
    writes nothing before it: a guest resuming the disk requests in flight at the snapshot wrote within microseconds,
    which cleared the fill's token before a refused record could be undone (PERF loop 86). Refused (the storage
    full), the run is stopped and the page says so ([The snapshot loaded, but the browser's storage refused to record that the machine's disks are now the snapshot's. The machine was stopped, and its restore is undone as one that didn't finish. Retry restores the snapshot again.](ui:snapshots:restore-loaded.notRecorded.cause)): the restore is
    still one that never loaded, as a whole (the guest never ran), and its Retry restores it again. After the write, a
    template's fresh overlay is named after the snapshot and marked as its fork (`fork`, its generation one past the
    commit's; one read and write of its record, as every writer of an overlay's fields: the run's refresh at its stop,
    a rename, a resize's size and grow mark), which only spares a later restore a fork if it fails; and a replace's
    fork (`replaced`) deletes the overlay it replaced and takes its name (above, "How a replace is made").
  - **The undo** (`undoCutRestores`, at the machine's next load or start, under its lock taken only if free, so a
    restore under way here or in another tab is left alone; a page reading the records again waits for its own last
    run's lock to go: `MachineLock.settled`; a start that boots undoes as the lock's owner, `#openDisks`; the record
    read again under the lock and written in one read and write, so another tab's edit meanwhile stays): `fork`, the
    attachment back on `before` (unless switched to another overlay since; also when the fork was deleted meanwhile,
    by Delete overlay or a merge), and the fork deleted after the record is written where nothing else has it (below:
    cut off between, or kept, it stays, unattached, an overlay like another, whose fill mark or generation tells
    whether it holds the snapshot); `reuse`, the attachment back on `before`, the fork kept as it was (a later restore
    attaches it again); `into`, left attached, and marked as a cut-off fill (`markCutFill`: read as empty at its next
    opening, its generation moved on) only where its `meta` still carries the restore's token (the fill opened it and
    nothing wrote it since), before the record says it's done; else as it is (the fill never opened it: a refusal before
    the disk phase; or another machine wrote it since). An earlier overlay deleted since: none (the
    next start makes an empty one). A step whose overlay is open elsewhere (another tab's job or machine: an overlay
    that carries the token, to mark; a fork that no other machine has, to delete) stays, as it is, for the next load;
    until then the machine neither boots nor restores again ([A restore of this machine that didn't finish is still to
    be undone, and one of the disks it wrote to is open in another tab or window of this web
    app.](ui:snapshots:snapshot-undo.pending)). A fork another machine has chosen holds nothing up: only this
    machine's attachment goes back.
  - **Other machines** (the rules since PERF loop 84; tests/restore-records.test.ts "review 1" to "review 9"): an
    overlay can be shared (Duplicate copies a machine's attachments with their overlays, and the Overlays dialog lets
    any machine of the disk choose any of its overlays), and nothing stops another machine from choosing one, running
    on it or copying a machine while a restore of that machine hasn't loaded. So:
    - **A restore changes no other machine's disk.** It writes into an overlay (a replace, a template's fresh
      overlay) only where no other machine has it chosen and no restore that hasn't loaded names it (as what it made,
      wrote into or goes back on: `taken`, web/app/snapshots.ts); otherwise that disk forks, and the confirmation
      offers no replace for it. It attaches an earlier fork again only on the same terms. Both are checked again at
      the commit, in the transaction of its write (`Store.updateAmong`: every machine's record read with it), so a
      machine that chose the overlay, or a copy made with it, after the commit's survey refuses the commit with nothing
      written ([Another machine started using the overlay {{overlay}} while the restore was getting ready, so the
      restore changed nothing. Retry restores the snapshot into a new overlay instead.](ui:snapshots:snapshots.takenMeanwhile)),
      and a replace holds only for the overlay the question named, still attached.
    - **An undo moves only its own machine's attachments, and empties or deletes only what it can prove nothing else
      wrote.** The proof is the fill token: the commit's id, which the worker's fill writes into each overlay's `meta`
      with the fill mark, before it deletes anything of it (web/overlay.ts `openOverlay`'s `fresh`), and which the
      first change of any later opening clears with its generation's bump (devices.md "blk"). An overlay written into
      is read as empty only while it carries the token; a fork is deleted only while no other machine has it chosen
      or names it, and it is either never opened (generation 0) or carries the token. Anything else stays as it is,
      an overlay like another: a fork another machine chose (running, stopped, or one it wrote and left), an overlay
      another machine wrote after the fill. Overlays and steps from before tokens carry none, so their undo never
      empties or deletes anything. A limit: a tab still on a page from before PERF loop 84 (open across that deploy)
      writes a meta of 48 bytes at its first change, which leaves the token in place, so its machine's writes to an
      overlay a pending restore names don't clear the proof; it takes such a tab running a machine on another machine's
      pending fork, and that restore undone after, and it ends with the tab's reload.
    - **A copy is of what the undo leaves.** Duplicate of a machine whose restore hasn't loaded gives the copy, for
      each fork the restore made or attached again, what that attachment had before (`before`; none where that
      overlay was deleted since, as the undo); an overlay written into is the copy's too (the undo's token rule decides it for both, by who wrote it last).
    - **What it costs:** a restore that would have replaced a shared overlay forks (the storage of a fork); a fork
      another machine took stays after its undo (the user's to delete); a cut-off fill whose fork another machine
      opened first is emptied by that opening and stays, empty, named after the snapshot.
  - **Who else reads it:** an earlier fork that any machine's `restoring` names (or goes back on) is never attached
    again (`earlierFork`); Delete overlay holds off the machines whose `restoring` names the overlay, as a fork or as
    `before` (their undo would name it as it's deleted); a merge, which holds off every machine that attaches its disk,
    undoes their restores first, as their locks' owner, and refuses an overlay that a machine not among them still
    names (`disks:merge.cutOff`). Nothing else writes it: every other writer of a machine's record changes only its own
    fields, onto the record as the store has it, in one read and write (`Store.update`: an IndexedDB transaction): a
    settings save (`updateMachine`, whatever its draft read), the Disks tab's attach, edits and switches (from the
    Home page's copy), a connection, a shared folder, the USB devices, a start's new overlays, a deleted overlay's
    detach. Before (PERF loop 84's review 5), a read that came before the commit or `loaded` and a put after it brought
    back a restore that had loaded (its next load deleted the fork the guest ran on) or dropped one to undo.
  - **Records from before** (loops 77–80, never deployed): an overlay's `restoring: true` and `fork.before` are read as
    nothing; such a cut-off restore stays as it was left.
  - **Why one record** (PERF loop 82): loop 80 kept a mark on each overlay a restore wrote (`restoring`, with
    `fork.before`), written one record at a time before the machine's and cleared one at a time after `loaded`. Its
    review found that a mark no record owned was acted on by whichever machine attached the overlay (another machine's
    load moved that machine onto the first one's earlier overlay), that the clearing missed what it didn't write (a
    reused fork stayed marked, so a restore that loaded was undone at the next load), that a commit or a clearing cut
    off part way left marks no undo reached or undid half a restore, and that a replace's mark couldn't tell a fill
    that ran from one that never did (a refused restore emptied the user's overlay). The machine's record is written
    once at the commit and once at `loaded`, and the undo of an overlay written into compares its generation with the
    commit's. Its review (PERF loop 84) found that the generation is moved by any opener that writes, not only the fill,
    and that overlays are shared between machines: a replace's undo emptied what a copy of the machine wrote, an undo
    deleted a fork another machine had chosen and written, and Duplicate copied a pending restore's fork without its
    undo. The rules for other machines (above) and the fill token came of it.
- **On the records as they are:** the page reads the machine's records again before it plans a restore of a machine
  that is off, and again once it has stopped (the Home page or another tab may have changed them while the
  questions were open: the shape is checked again then); `commit` plans on the record and disks the store has then and
  writes back that record with its attachments' overlays changed, never the one the page planned on, and the start
  opens the record the commit wrote (tests/page-restore.test.ts).
- **Import a file** copies it into the machine's snapshots after the header check (one of another shape is kept,
  orphaned).
- **A template** (`template: true` in the header, set only by `tools/snapshot-template.ts`, never by the page): its
  restore has the guest agent renew the guest's identity (devices.md "A template's identity").
- The page's header is format 2: a stored machine's `name`, `shape`, `shapeHash`, URL disks' `urls` and the stored disks' generations under it (`bases`, §5.1 "Unrestorable"), and the pins
  in `disks`; `web/snapshot-file.ts`'s container and the core's state are as for any snapshot.

### 5.3 Suspend

A snapshot in the machine's `suspend` slot, without the overlays' blocks (they're in OPFS) and with the ramdisks'.
It resumes only while every pin matches (the worker compares each overlay's generation, `overlayMeta`, and the stored
disks' under them, the header's `bases`: §5.1 "Unrestorable"); a start drops
it with a note otherwise. Switching an overlay, New empty, a merge, editing the machine or a boot all make it stale
with no code of their own.

**Shared folders and snapshots** (shares.md §6): the 9p device is in the shape, the attached folders aren't, and a
folder's files are never in a snapshot (a host folder is the host's; a folder in the browser is its stored files, as
a disk's base is). A snapshot (a suspended copy too: the same writer) saves the server's fids and nodes by path after closing its write
sessions; a restore asks nothing of the folders until the guest does, and a folder detached since, or a path gone,
answers `ESTALE` on those fids. So attaching or detaching a folder orphans nothing and doesn't make a suspended
copy stale.

## 6. Machine definitions in and out

`web/app/definitions.ts`; the page's side is frontend.md "Machines in the browser".
- **[Export the definition](ui:machines:MachinePane.exportDefinition):** `<name>.waarm64-machine.json` (`waarm64-machine`, a version): the machine's settings (shared
  folders as `shares`, `sharesMount` and `sharesPath`, never the folders), the adapters' MACs (no connections), the

- **Import a definition:** a new machine (the name made unique, the same shape). A disk the browser has by identity is
  attached again; URL, blank and ramdisk disks come back as they were; an `overlaySize` gives the attachment an empty
  overlay at that size, marked to grow (its base's partition doesn't fill it: the guest grows it at its first start; a
  grown stored disk the browser doesn't have comes back as its image at the size it was made with, under such an
  overlay); file disks, and stored disks the browser
  doesn't have, are picked at the machine's first start (the same flow as a handle without permission, §3.2): a
  picked file of another size is refused; one with the same name, size and date is taken; one that differs is hashed
  against the definition's hash when it has one (refused if it isn't); otherwise the user is asked, and taking it

### 6.1 A machine from a template

`web/app/template.ts` (the demos' first start, decisions.md "Demos"; the store's page clicks it: frontend.md "The
demo store"): a definition imported as above (`fetchDefinition`: its disks' relative URLs resolved against
the definition's own URL, so a site moves whole), the template snapshot (a chunked file: `fetchChunked`, each piece
checked against its hash) kept as the new machine's first snapshot, and the record marked `restoreFirst: <its id>`.
The machine's first start (`PowerActions.startOpened`, or Start after a page that didn't start it) restores that
snapshot instead of booting, with no question (`SnapshotRestore.first`): the shape is the definition's (its disks'
identities and serials), so it matches; the pins, by slot, fork onto the machine's fresh overlays (none yet: new
ones; a fresh one: that one, §5.2). It runs within `exclusively` (a Start meanwhile starts nothing beside it). The
mark stays until the snapshot loaded (the worker's `loaded`: `restoreLoaded`), so a first start cut off or refused
before that restores the snapshot again at the next start, its restore undone in between (§5.2;
tests/page-template-first.test.ts); a commit that fails (the storage full) is said with Retry, which restores it
again, the mark kept; so is a fill refused after it began (the storage full, a disk that didn't open): a fresh overlay
holds nothing to lose, its plan marks it a fork's (§5.2), and its refusal isn't a snapshot that can't load here; a snapshot that can't be restored (another
shape: said) boots the machine instead, the mark cleared, and so does one that can't load once the start is under way (`SnapshotRestore`'s boot instead,
said as [{{machine}} started from power on: its demo's saved state couldn't be restored in this browser.](ui:snapshots:snapshot-restore.firstBooted)): a 3D or Vulkan template whose 3D fails
to start in this browser (the GPU worker's `failed`: the machine runs 2D, another shape, and the snapshot never reaches
the worker), or the worker refusing it (a `snapshot` problem, which a first start doesn't leave to the user's Start).
Either way what its restore wrote is undone at the boot's start, as a restore that never loaded (§5.2): the fresh
overlay, never marked as the template's fork (that comes only with `loaded`), reads as empty once the fill wrote it,
a new fork goes, so a later restore of the template forks anew rather than taking a booted disk back as its blocks, and "started before" doesn't find the demo unchanged. Afterwards it's an ordinary machine: its overlay, Suspend, and the template
kept as a snapshot to go back to. The page's hook `window.__waarm64FromTemplate(definition, snapshot)` (`?hooks`) is
bench/demo's click; tests/template.test.ts the identity and the plan in Node.

### 6.2 Version 2, demos and stores

**Version 2** of the definition (`DEFINITION_VERSION`, what an export writes) is version 1 plus an optional `demo`, a
demo's card: `id` (lowercase letters, digits and dashes: what `?id=` and "started before" use), `summary` (plain
text, the store's data, not the catalog's), `thumbnail?`, `download` (the bytes a visit fetches: the publish tool
checks it), `view` (`serial` or `screen`), `snapshot?` (`{manifest, id}`: the template's chunked file and its content
id; none: a cold boot), `network?` (`"demo"`: the first adapter on the demo network, which needs `machine.network`),
`room?` (`"global"`: the second adapter on a room connection of the machine's own on the global public room, which
needs two adapters, `machine.macs`: [networking/rooms.md](networking/rooms.md) "A demo's room"),
`replaces?` (the ids of the versions before: a machine made from one is "an older version of this demo"),
`template?` (`true`: New machine offers it as a template too, §6.3). What a card
needs from the browser is the machine's own fields (`display: "3d"` for WebGL2, `vulkan` for WebGPU, `ramMiB`), not a
`needs` of its own that could disagree with them. **Version 1 still reads** (the reader takes both; a `demo` in a
version 1 file is left out): nothing migrates, and an older page refuses version 2 by its version. Checks live in
`web/app/definition-check.ts`: each field as an import needs it, a URL disk with its URL (http, https or relative),
and a damaged definition's error names the field at fault (`machine.ramMiB`, `disks[0].url`, `demo.view`). Fields the
page doesn't know are ignored, so a later page's additions within a version still read; the publish tool refuses them
(a typo in a store's source).

**A store** (`web/app/demo-store.ts`, decision 15) is one file, `{type: "waarm64-store", version: 1, name?, demos: [...]}`,
each demo a whole version-2 definition with a `demo`; relative URLs (disks, snapshot, thumbnail) resolve against the
store's URL (`resolveUrls`). A single definition's URL is taken where a store's is (`parseStore` tells them apart by
`type`): a store of that one demo, the definition's URL its store. A demo the page can't read (a later version,
damaged, not a demo, an id seen before in the store) is left out and listed in `skipped` with its error, so a store
with a newer demo still shows the others; the store itself unreadable (unreachable, a status, not JSON, not a store,
another version) is a `MsgError` (`machines:demo-store.*`). `OUR_STORE` is `https://disks.waarm64.com/store.json`.

**A demo's machine** (`machineFromDemo`, web/app/template.ts): its snapshot fetched first, its manifest once (a 404 is
`machines:template.gone`, "this demo's files are gone"; a manifest whose `id`, or its hashes' content id, isn't the
card's is refused: the site was republished meanwhile; one larger than the card's `download`, or than `MAX_TEMPLATE`,
1 GiB, is refused before a piece is fetched, since a store that isn't ours could name one hosted piece ten thousand
times) and its pieces by that manifest (each kept as a Blob as it comes, which Chromium may keep on disk; the first
failure aborts the others; `signal` aborts them all: the demo's pane on the store's page gone); then §6.1's machine, marked
**`fromDemo: {store, id}`** (the store's URL as fetched, absolute: another host's store with the same id is another demo), and its first adapter on the demo network when the
card asks (`withDemoNetwork`, web/app/net-demo.ts), its second on a room of its own when it asks (`withDemoRoom`). The snapshot is kept under the machine's id before its record is
stored, and the record is stored once with all its marks (`importDefinition`'s `finish`, which runs before any record
is written: the disks, overlays and machine are written after it, at once, so a tab closed during the snapshot's copy
leaves only files the store's sweep takes): any failure (the download,
the storage full, the demo connection) leaves no machine and none of the disks or overlays the import made, so trying
again makes one machine. `demoMachines` finds this browser's machines from a card (`mine`: "started
before", the most recently changed first) and from the versions it replaces (`older`). `fromDemo` isn't in the shape or
a definition; a copy drops it (the card would open a copy that starts cold, off the demo network: a copy is the user's
own machine) and `restoreFirst` (the template is a snapshot of the original, not of the copy). A download cut off
partway is `machines:template.cutOff`; the storage full when the snapshot is kept, `machines:template.full`. The store's page, which makes
these machines: [frontend.md](frontend.md) "The demo store". Tests: tests/demo-store.test.ts (Node), tests/demo-open.test.ts (Node), tests/page-template-first.test.ts (a store's
demo made and restored at its first start in Chromium; a 3D template whose 3D fails booted instead).

### 6.3 Templates under New machine

[New machine](ui:machines:MachinesNav.newMachine) opens a dialog (`NewMachine.svelte`; frontend.md "The Home page"):
**[Empty machine](ui:machines:NewMachine.empty)** (the default settings, no disks: what New machine always made) and,
**[From a template](ui:machines:NewMachine.templates)**, our store's demos marked `demo.template: true`
(`demo-store.ts` `templatesOf`, in the store's order, by their name and summary; no thumbnail or download size: a
template cold-boots, so its download is the disk's reads, not a number the card has), so a new machine needs no disk image of
the user's own. A template is the demo's definition without its `demo` (`template.ts` `templateDefinition`,
`machineFromStoreTemplate`): its machine and disks (the URL disk at the store's URL, the same disk record as the demo's
by identity, an overlay of its own; its adapters with MACs of their own, as an empty machine's, not the recipe's fixed
one, which two machines from the template on one network would share), and nothing of the demo: no template snapshot (a cold boot from power on, nothing
downloaded first), no demo network (the adapters without a connection, as any new machine's), no `fromDemo` (its card
doesn't find it as started before: it's the user's own machine, as a demo's copy is). The flag is opt-in, the store's
author's choice per demo: a demo made to show one thing (a game, a 3D test) or a second demo of the same image isn't a
starting point, and a store from before the flag offers none. tools/demo-site.ts carries it to the store and refuses
it when not a boolean. The store is read each time the dialog opens: while it loads, when it can't be read (said, with
[Try again](ui:machines:NewMachine.retry)) or offers none, Empty machine still works. Only our store's templates are
offered (`OUR_STORE`; `?store=` is the store page's alone). Tests: tests/demo-store.test.ts (which are offered, the
machine made), tests/page-demos.test.ts (the dialog in Chromium: a template to a cold start; the store down).

## 10. Ahead

- **The preloaded image** (PLAN.md, proposed) and **the demos** (DEMO track) are machines from a template (§6.1): a
  chunked image known by its content and a template snapshot restored onto fresh overlays.
- **A catalog** of hosted images would be a list of such machine definitions.
- **The embedding API**'s VM configuration would start from the machine definition and its shape.
- **Exporting a whole machine** (a bundle: the definition, its overlays as changes files, its kept snapshots and,
  optionally, its stored disks) isn't built ([#174](https://github.com/gbl08ma/waarm64/issues/174)).
