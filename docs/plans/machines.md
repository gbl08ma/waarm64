# Machines, disks and snapshots (M8 phase D, its start; confirmed 2026-10-17, `M8-MACHINES-KICKOFF.md`)

The page today runs one machine whose disk is a session's choice: a `DiskChoice` (`{url?, file?, overlay}`), one
overlay per disk (named by a hash of its identity, `diskOverlay` in web/app/machine.ts), the EFI variable store and the
Suspend file in that overlay's directory, and a second disk only for tests (`?disk2=`, read-only). This plan makes
**machines** first-class: named, stored in the browser, each with its vCPUs, RAM, any number of disks and its own
snapshots, managed in a modal. It is the start of phase D (PLAN.md §3), before the preloaded image, the catalog and
the embedding API, none of which it conflicts with (§10).

## 1. Decisions (the user, 2026-10-17; §4.4's stored-disk format and snapshots of disks written in place confirmed too)

1. **Machines are the unit.** A machine has a name (generated by default), vCPUs, RAM, the display mode, an ordered
   list of disks and, later, network adapters (several: a later milestone). Users create, edit, delete, export and
   import them in a modal (Svelte is approved for it, PLAN.md M8's frontend decision).
2. **Up to 16 disks** (§4.1: room kept for more devices without making a machine that uses them all unloadable), each **read-only or read-write**. A read-write disk writes into
   an **overlay** in OPFS.
3. **Overlays belong to a base disk, not to a machine**: named variants of the same base that any machine attaching
   that base can choose from (one running machine at a time per overlay: its Web Lock). Users name, switch, delete,
   create empty ("start fresh") and export them.
4. **Disk sources:** an HTTP URL; a file from the user's computer; a file **copied into OPFS** (the user is told it
   duplicates a file they likely keep, in storage they can't easily see); a **blank** disk of a chosen size; a
   **ramdisk** of a chosen size in the host's RAM.
5. **The ramdisk** is empty at every boot, the guest's own reboot included (simpler than keeping it: the device
   worker owns it, §4.3); a snapshot holds it (a restored machine finds the disk it had mounted). Its memory is
   allocated lazily (the user knows Chromium on Linux does: nothing to measure); chunks are for giving memory back.
6. **Export** of disks and overlays as today: the changes only (a qcow2 over the base) or the whole disk (qcow2 or
   raw), compressed or not.
7. **Snapshots belong to a machine and are checked against its shape** (§5.1), not against one disk. Several per
   machine, kept in OPFS or downloaded; a file can be imported into OPFS or applied at once. **Editing a machine is
   allowed and orphans the snapshots its change invalidates**; the snapshots view shows which are orphaned and has one
   action that deletes them all.
8. **Restoring a snapshot never destroys a disk's state**: where an overlay isn't as the snapshot left it, the restore
   writes the snapshot's blocks into a **new overlay** (a fork) and attaches it; where it is, the restore writes
   nothing. Detecting "as it left it" is a **generation counter**, never a hash of a large file (§3.3).
9. **Export a machine's definition** first (its shape: a small file; disk files are picked again on import, checked
   by identity); **export a machine** (with its overlays and snapshots, a bundle) later. The UI names them apart.
10. **Remote disks stay their own track** (docs/plans/remote-disks.md: the chunked format and how a user gives its URL
    still need discovery). Here: a URL source with a check of the server and the requirements stated (§4.2).
11. **A stored disk can take an overlay in place** ("merge into the disk"): the overlay's blocks are written into the
    stored disk, and **every other overlay of that disk is deleted** (they were over the old bytes); the confirmation
    lists them. No export and re-import needed.
12. **A stored disk can be written in place**, as an option per attachment: no overlay, the guest's writes go into
    the stored disk (§4.4).
13. **No compatibility** with today's overlays, Suspend files or snapshot files: nobody uses the deployed page yet.

## 2. The model

| Thing | What it holds | Where |
|---|---|---|
| **Machine** | id, name, vCPUs, RAM MiB, display (2D/3D), the attachments in slot order, the selected overlay per read-write attachment | IndexedDB `machines` |
| **Disk** (a base) | id, kind (`url`, `file`, `stored`, `blank`, `ramdisk`), size, the identity (§3.1), the kind's data: a URL; a `FileSystemFileHandle` (IndexedDB can hold one, JSON can't); a stored file's OPFS path | IndexedDB `disks` |
| **Attachment** | the disk, read-only or read-write, the virtio serial (`GET_ID`, from the attachment's id) | in the machine |
| **Overlay** | id, name, the base's id and identity, generation (§3.3), created, modified, bytes; today's `data` and `map` | OPFS `overlays/<id>/`, its record in IndexedDB `overlays` |
| **Variable store** | the EFI flash bank (1 MiB): **per machine** now (its boot entries are the machine's, e.g. after an install from an ISO onto a blank disk) | OPFS `machines/<id>/flash` |
| **Snapshot** | id, name, created, size, the shape hash, the pins (§5.1); the `WEBPCSNP` file | OPFS `machines/<id>/snapshots/<id>`, its record in IndexedDB `snapshots` |
| **Suspended copy** | a snapshot in the machine's `suspend` slot (§5.3) | OPFS `machines/<id>/suspend` |
| **Stored disk** | an imported image in the overlay's sparse block format (§4.4), with a generation | OPFS `disks/<id>/` |

- **IndexedDB for records, OPFS for bytes.** A record is written after its bytes and deleted before them, so a crash
  leaves unreferenced files (swept at start: anything under `overlays/`, `machines/*/snapshots/` or `disks/` without a
  record), never a record without its files.
- **Several tabs:** a Web Lock per machine while it runs (beside the overlays' own), and a `BroadcastChannel` that
  tells other tabs' modals to reread. Editing a running machine is refused (it says to power off), also from another
  tab (the lock).
- **Storage:** the modal shows `navigator.storage.estimate()` and what each overlay, snapshot and stored disk takes,
  and asks for `navigator.storage.persist()` the first time something is stored (without it the browser may evict the
  origin's data under pressure). A full quota today reaches the guest as `IOERR` (backlog: the overlay's quota); the
  page should say so when it happens.
- **The tests' query parameters stay** (`?machine=debian`, `?disk=`, `?disk2=`, `?ncpus=`, `?ram=`): they make a
  transient machine, never stored. Tests run in fresh profiles anyway.
- **Opening a disk the old way stays:** a file dropped on the page, Open disk… or `?disk=<url>` with no machine
  selected makes a machine for it (named after the file) and boots it.

## 3. Identity, and what changed

### 3.1 A base's identity

Cheap, as today, and recorded at attach: a file's name, size and modification time; a URL's path and size, plus its
`ETag` or `Last-Modified` where the server sends one (remote-disks §4.1's content identity replaces this for chunked
images); a stored disk's id; a blank disk's id and size. The SHA-256 (`hashSource`, ~640 MiB/s in Chromium) is
computed only where one is needed: a re-picked file whose cheap identity differs (§6), a changes file's base, and in
the background for a stored disk (once: it never changes).

### 3.2 Re-granting a file

A `FileSystemFileHandle` kept in IndexedDB needs `requestPermission({mode: 'read'})` from a click in each session
(backlog "Remember the chosen disk"): Start asks for it, for every file disk of the machine at once if Chromium
allows (else one prompt each). Drops give handles too (`DataTransferItem.getAsFileSystemHandle`). A file that moved or
changed (the handle fails, or its name, size or date differ) is a disk to pick again, checked as in §6.

### 3.3 The overlay's generation

Each overlay has a `generation` (a u64 in a small `meta` file beside `data` and `map`, and in its IndexedDB record).
**The device worker bumps it, durably, before the first write of a session** (a flag per opened overlay; one more
small OPFS write per boot, not per request), and the page updates the record when the machine stops. So "the overlay
is exactly as it was at generation g" is a comparison of two integers; nothing is hashed. A snapshot pins each
read-write disk's overlay id and generation (§5.1). A machine that ran without writing leaves the generation as it was.

This replaces Suspend's discipline of dropping the copy before any machine runs on the overlay (frontend.md
"Snapshots"): a suspended copy whose pins no longer match is stale by construction (§5.3).

## 4. Disks

### 4.1 Many disks

- **16 disks at most** (the user, 2026-10-17). The page's machine uses up to six other transports (rng, keyboard,
  tablet, gpu, snd, net) of the core's 32 (`virtio::MAX_DEVICES`), so 26 would fit today; 16 leaves room for devices
  to come (more network adapters, a console, 9p, input) without a stored machine that used every slot becoming one
  that a newer page can't make. Slots are given in a fixed order: the other devices first, then the disks, so a new
  device kind is appended after them only on machines that have it.
- The device list is built from the attachments (it replaces `normalKinds` in web/app/worker.ts); a snapshot's
  header lists the attachments, not kinds alone.
- **Attaching, detaching, reordering or flipping read-only needs the machine off:** virtio-mmio has no hotplug and the
  DT is fixed at boot. The guest names disks by slot (`vda`, `vdb`…); the serial gives it `/dev/disk/by-id/virtio-…`
  that survives a reorder.
- **Boot order** is the firmware's: EDK2 tries the disks in its variable store's order, then in slot order. The flash
  store being the machine's (§2) is what makes the installer flow work: an ISO read-only and a blank disk, install,
  detach the ISO, boot the installed disk. That flow is a page test (§9).
- One device worker serves every disk, and an HTTP disk blocks it per read (remote-disks §1): several HTTP disks add
  their waits, and input and the display wait behind them. Remote-disks R4 (asynchronous reads) is what removes that;
  until then, the modal says that a URL disk is slow.

### 4.2 Sources

- **URL:** added through a check the page runs at once (HEAD, a range, a suffix range, `Content-Range` exposed: what
  `bench/results/local/cors-probe.ts` does), which names what fails and what the server needs (HTTPS, CORS for the
  page's origin with `Content-Range` exposed and `Range` allowed in preflights, range requests: remote-disks §3, with
  the Caddy snippet). The check is the URL form's, not the boot's.
- **File:** a handle (`showOpenFilePicker`, a drop), remembered (§3.2).
- **Stored in the browser:** a file copied into OPFS (streamed, with progress; the confirmation says the size, that
  it duplicates the file, and that the browser's storage is where it goes) and converted on the way (§4.4). It never
  needs picking again, a machine bundle (§6) can carry it, and it can be merged into and written in place.
- **Blank:** a size; read as zeros (a `zeroSource`), always read-write, so it always has an overlay. Its export is
  the whole disk only ("changes only" over nothing means nothing).
- **Ramdisk:** below.

### 4.3 The ramdisk

- **Owned by the device worker** and gone with it: every boot, the guest's reboot included (a reboot is a new
  machine worker today, `rebooting` → `restart()` in main.ts), starts from an empty disk. Writable in itself: no
  overlay.
- **Lazily allocated** (Chromium on Linux commits a large `SharedArrayBuffer`'s or a wasm memory's pages on first
  touch): an empty ramdisk costs nothing. What allocation alone can't do is **give memory back** when the guest
  deletes and trims (no `memory.discard` in browsers). So: **1 MiB chunks** (`SharedArrayBuffer`s, made on a chunk's
  first write, dropped when a DISCARD or WRITE_ZEROES covers the whole chunk; a missing chunk reads as zeros). The
  disk takes DISCARD (devices.md "blk"), so `fstrim` or a `discard` mount returns the memory. No 4 GiB limit; a map
  lookup per request (checked with fio against one buffer, as bench/io: kept if within noise).
- Shared memory, so the snapshot writer reads the chunks without a copy through the device worker.
- The machine's memory check (`hostMemoryGiB`) counts the ramdisk's size (what it may grow to).
- A snapshot holds its chunks (the `DISK` frames, as an overlay's blocks), a suspended copy too (the ramdisk isn't in
  OPFS); a restore makes the chunks again.

### 4.4 Stored disks: their format, merging, writing in place

- **The format is the overlay's** (`data` and `map`, 4 KiB blocks, zeros without a slot: devices.md "blk"), over
  nothing: a stored disk is a sparse, writable block store. An imported qcow2 is converted on the way in (compressed
  clusters inflated, zero and unallocated ones left out), a raw image too (zero blocks left out). So stored disks
  take no more than their data (Debian's image: ~1 GB of data from a 400 MB compressed qcow2; the confirmation says
  what it will take, estimated from the qcow2's allocated clusters), and the same code reads, writes and exports them.
  Kept as the file is (a qcow2 can't be written in place: our qcow2 code reads, and writes whole files, never
  allocates in one) was the alternative; it loses merging and writing in place.
- **The blk device writes through `WritableDisk`** (web/overlay.ts: `write`, `zero`, `discard`, `flush`, and
  `written`/`block`/`zeroed` for exports and snapshots); the overlay is its only implementation today, and nothing
  above it assumes a base underneath. A stored disk opened for writing is the same block store with no base, so
  **writing in place needs no new device code**, only the attachment's choice (`overlay` or `in place`).
- **A stored disk has a generation** (§3.3) as an overlay has; writing in place bumps it.
- **Merging an overlay into its stored disk:** the machines using the disk are off (its lock); the confirmation names
  the other overlays that will be deleted and the snapshots it orphans (those pinning the disk's generation or any
  of its overlays). Then: the other overlays are deleted, the disk's generation is bumped and a `merging` marker
  (the overlay's id) written, the overlay's blocks are written into the disk (its zero blocks as zeros), the overlay
  is deleted, the marker removed. Interrupted, the disk resumes the merge at its next open (writing the same blocks
  again is harmless) before anything else may use it.
- **Writing in place and snapshots:** a disk written in place has no earlier state to fork from. A kept snapshot pins
  the disk's generation and restores only while it matches (otherwise it's stale, marked as orphaned are, and
  deletable); a suspended copy works as with overlays. **A downloaded snapshot can't be self-contained** without a
  copy of the whole disk: Save snapshot offers either the whole disk in the file (its size said) or none (the file
  then restores only onto this disk at this generation). The attachment's UI says that writing in place gives up
  forking and overlays' variants.
- **Exports** of a stored disk as today's whole-disk ones (qcow2 or raw, compressed or not); "changes only" applies
  to its overlays.

## 5. Snapshots

### 5.1 The shape and the pins

- **The shape** is a canonical JSON of what the guest sees: vCPUs, RAM, the display (2D or 3D: different devices),
  the transports in slot order, each disk's size, read-only or not, serial and base identity, the CPU features
  (`cpu`), whether there's a network card. Its SHA-256 is the **shape hash**; the header carries the whole shape, so a
  snapshot file can make its machine (§5.2).
- **The pins:** for each read-write disk, the overlay's id and generation.
- **Orphaned:** a stored snapshot whose shape hash differs from its machine's current one (the user changed RAM,
  added a disk…). Pins don't orphan a snapshot: a moved-on overlay is what the fork is for. The snapshots view marks
  orphaned ones, says what differs (from the two shapes), and has **Delete orphaned snapshots** (all, one
  confirmation with the total size), and per snapshot **Make a machine like it** (a new machine from its shape,
  disks picked again where they're files).

### 5.2 Save, keep, load

- **Save snapshot** offers **Keep in the browser** (a name; into the machine's snapshots) or **Download**. Both
  write today's file (self-contained: the overlays' blocks are in it), so a kept snapshot can be downloaded later as it
  is. Keeping many snapshots of a machine with a big overlay costs that overlay each time; sharing blocks between them
  (copy-on-write per snapshot) is later, if the sizes measured ask for it.
- **Restore** (a kept snapshot, or a file applied directly without being kept): refused before anything is touched
  when the shape differs (it offers to make a machine like it). Then per read-write disk: **pin matches** (the attached
  overlay has the snapshot's id and generation) → nothing is written, the restore is RAM and state only; **otherwise**
  → a new overlay named after the snapshot gets its blocks and is attached, and the old overlay stays as it was. The
  confirmation says which overlays fork, and offers **replace instead** (the old overlay's changes since are lost: it
  says how much), for a user who doesn't want the fork. A ramdisk takes the snapshot's blocks.
- **Repeated restores don't pile up forks:** a restore that would fork checks for an overlay forked from this
  snapshot whose generation hasn't moved since the fork, and attaches that one instead.
- **Import a file** into the machine's snapshots (copied into OPFS after the header check), or apply it at once.
- The header's `machine`, `disk` and `devices` fields give way to the shape and the pins (format 2 of the page's
  header; `web/snapshot-file.ts`'s container and the core's state are unchanged).

### 5.3 Suspend

A snapshot in the machine's `suspend` slot without the overlays' blocks (they're in OPFS) and with the ramdisk's.
Valid while every pin matches; a start resumes it if so, and drops it with a note if not. Switching an overlay,
Reset (now: a new empty overlay, or deleting one) and editing the machine all make it stale with no code of their
own.

## 6. Machine definitions in and out

- **Export a machine definition:** JSON (`webpc-machine`, a version), the machine's settings, its attachments, and
  each disk's kind and identity (a URL as is; a file's name, size, date and hash where known; a stored disk's identity
  and hash; a blank's or ramdisk's size). No overlays, snapshots or file contents.
- **Import:** a new machine (the name kept, made unique); URL, blank and ramdisk disks come back as they were, file
  and stored disks are listed to pick: a picked file with the same name, size and date is taken; one that differs in
  any is hashed against the definition's hash when it has one (the user can take it anyway, which is a different
  disk's identity: its overlays won't apply).
- **Export a machine** (later): a bundle with the definition, its overlays (as changes files), its kept snapshots and,
  optionally, its stored disks.

## 7. The modal

Svelte, compiled by `tools/serve.ts` and `tools/dist.ts` as type stripping is (no build step). One dialog, **Machines**:
- **The list:** each machine's name, size, disks and state (running, suspended, off); new, duplicate, delete, import
  a definition.
- **A machine:** settings (name, vCPUs, RAM, display), **Disks** (add from a source, reorder, read-only, detach; per
  read-write disk its overlays: new empty, rename, switch, delete, export), **Snapshots** (kept ones with orphaned
  marked, restore, download, delete, delete orphaned, import a file), export the definition. What needs the machine
  off says so and offers to power it off (as Save disk does today).
- **Storage:** the estimate, the biggest items, the persistence state.
- The header's buttons shrink to the running machine's actions (Start, Restart, Suspend, Save snapshot, Save disk),
  which act on the selected machine.

## 8. What changes outside the page

- `web/devices.ts`: `zeroSource`, the ramdisk (chunks), a stored disk opened for writing in place, the overlay's generation bump, the
  serial in `GET_ID`; `DeviceSpec` `blk` takes a source kind instead of `url`/`file`.
- `web/overlay.ts`: overlays by id under `overlays/`, `meta`, the generation, fork (a copy of the blocks), rename,
  merge into a stored disk; the import of a qcow2 or raw file into the block store;
  `removeOverlay`, `overlayBytes` and the exports on any overlay, not only the running machine's.
- `web/snapshot.ts`: the pins, the fork-or-nothing restore, the ramdisk's blocks.
- `web/app/worker.ts`, `protocol.ts`: `start` takes a machine definition (resolved: sources, handles, the overlays
  chosen) instead of `machine`, `disk`, `disk2`; the flash store by machine.
- New: `web/app/store.ts` (IndexedDB and OPFS: records, the sweep, the `BroadcastChannel`), `web/app/shape.ts` (the
  canonical shape and its hash), the Svelte components.
- No core change (the slots exist; `GET_ID` exists); no ABI change; no step count moves (the tests' guests keep their
  devices).

## 9. Loops

One slice, one commit, a short report each. `scripts/ci.sh` at each; `scripts/ci-debian.sh` at each loop that touches
the page, disks or snapshots (all of them from L1).

- **L0, the model:** `store.ts` and `shape.ts`, DOM-free, unit-tested (the sweep after a crash between bytes and
  record, the shape hash's stability and what changes it, two tabs through `BroadcastChannel`). No UI.
- **L1, many disks and two sources:** the worker builds devices from attachments (16 disks at most), the serials,
  `zeroSource`, the ramdisk in chunks (fio against one buffer; memory given back after `fstrim`). Tests: Debian with
  three disks (a blank one formatted and mounted, a ramdisk empty after `reboot`, a read-only one); the installer
  flow (Alpine's or Debian's ISO read-only, a blank disk, install, detach, boot it).
- **L2, overlays and stored disks:** overlays by id, the generation (planted: the bump left out, so a moved-on
  overlay looks unchanged), named variants, new empty, switch, delete, rename, export; Load changes into a new
  overlay; the flash store by machine. Stored disks: the import (qcow2 and raw; the bytes read back equal the file's),
  merging (planted: an interrupted merge not resumed), writing in place, their exports against `qemu-img compare`.
- **L3, Svelte and the modal:** the compile step in serve and dist, the machine list and editor, disks and overlays,
  remembered file handles and their re-grant, the URL check, stored disks, the storage view. The old drop-and-boot
  path on top.
- **L4, snapshots:** keep or download, import, apply, delete, orphaned and delete-orphaned, make-a-machine-like-it,
  disks written in place (the generation pin; the whole disk in a downloaded file or not);
  the fork-or-nothing restore (planted: a fork skipped when the generation differs); Suspend on the pins. Debian's
  page snapshot tests move over.
- **L5, definitions in and out:** export, import, re-picking files by identity and hash, in a fresh profile.
- **L6, exit:** docs (frontend, devices, platform's snapshot notes, testing), the backlog, PLAN.md; numbers: the
  restore with matching pins against a fork (Debian), a snapshot's size and save time against today's.

## 10. With the rest of phase D

- **The preloaded image** becomes a built-in machine: a URL disk and a snapshot fetched with the page, restored with
  pins that match a fresh overlay (generation 0) so nothing is forked. It needs remote-disks' content identity (a URL
  path can't tell a new image from the old one: §3.1) and remote-disks' speed for the first boot's reads.
- **The catalog** is a list of such machine definitions.
- **The embedding API**'s VM configuration starts from the machine definition and its shape.
- **Network adapters** join the machine and the shape (several: a later milestone); today's single card is one
  attachment of a kind `net`.

## 11. Record: the cloud session (2026-10-17)

Built in a Claude Code cloud session (x86_64, 4 vCPUs, Playwright's Chromium 141), loops L0–L5 in order, each pushed;
the dev VM's pass (full CI, Chromium 153, the numbers) is `M8-MACHINES-HANDOVER.md`. Where the build differs from the
sections above, or settled what they left open:
- **The slots** (§4.1) are the other devices first in a fixed order (rng, keyboard, tablet, net, gpu, snd), then the
  disks; the tests' transient machines take the same order (their guests find their root by UUID or by `vda`, the
  first disk, either way). The snapshot header's `devices` lists the kinds that way.
- **Overlay paths:** a stored machine's are `overlays/<id>`; a transient one's keep their single names
  (`webpc-debian`, `webpc-buildroot`, `webpc-disk-<hash>` for `?disk=`), and the sweep touches only id-named files.
- **The generation's epoch** (§3.3 left it implicit): writes after a snapshot in the same session must move the
  generation, or a restore would keep an overlay that changed after the snapshot. The device reports the generation
  while the machine is paused for the snapshot and sets its next change to bump again. A restore that writes an
  overlay (a fork or a replace) sets its generation one past the old one, never back to a pinned one; a fork's is 1.
- **Pins are paths** (`overlays/<id>`, or `disks/<id>` for a disk written in place) with the generation, the blocks
  the file carries and a ramdisk flag (`SnapshotDisk`); the page maps them to records.
- **A suspended copy** is checked against its pins (the worker compares each overlay's generation) and the old
  drop-before-run discipline is kept besides.
- **Reads of a stored disk under overlays** use read-only sync access handles under a shared Web Lock (several
  machines at once); writing it in place or merging takes it exclusively. Stored Debian is 1,043 MB (estimated 1,212
  from the qcow2's allocated clusters), imported in ~140 s here.
- **The test profile:** an off-the-record Playwright context keeps OPFS in memory with a ~1 GB quota; stored Debian
  doesn't fit, so that test uses a fresh on-disk profile (`launchPersistentContext`).
- **A dropped or opened disk** on the page's own machine makes a machine for it (named after the file) or opens the
  one that attaches it; `?disk=<url>` stays transient (the tests').
- **Definitions** re-pick files at the machine's first start (the same flow as a handle without permission), not at
  import.
- **Decided by the user (2026-10-17, in the dev VM's pass):** Save snapshot on a stored machine is a two-choice menu
  in the header (Keep in this browser…, Save to a file…), as §5.2 has it; a 3D machine on a browser without WebGL2
  runs 2D, another shape, so its 3D snapshots show as orphaned there (the guest really sees other devices); the
  transient machines' overlays keep their single names.
- **Not built** (backlog "Machines as the unit, loose ends"): the quota message, a stored disk's background hash,
  `svelte-check`.
